# Рецепт для ИИ-агентов: собрать модель на CanvasDesk через MCP

Эта страница — **рецепт для ИИ-агентов** (MCP-клиентов): как собрать
исполняемую математическую модель на канвасе, не читая исходники
репозитория. Человеку начинать лучше с
[Расчётов и потока значений](calculations.html) и
[Шаблонов нод](templates.html).

**Правило рецепта:** значения между нодами переносятся **только** value-связями
с адресацией портов. Если число можно вычислить из другой ноды — его нельзя
писать руками (хардкодом): оно должно пролиться по связи. Тогда правка одного
стартового допущения пересчитает всю модель.

## Предусловия

1. Запущен CanvasDesk (GUI). Мост `canvasdesk mcp` / `canvasdesk-mcp`
   поднимается сам: handshake не зависит от GUI, при недоступном приложении
   `tools/call` отдаёт isError «CanvasDesk не запущен», а поднявшееся позже
   приложение подхватывается автоматически (reconnect 500 мс).
2. Канонический каталог инструментов — ответ `tools/list` (39 инструментов).
   Рецепт опирается на их схемы; при расхождении текста и схемы права схема.
3. Для установки знаний о CanvasDesk в агента постоянной памяти есть
   [пакет скиллов `skills/`](https://github.com/danku13/CanvasDesk/tree/main/skills)
   (4 скилла: подключение/разведка, сборка, проверка, what-if; тот же
   реестр, контракт синхронности с `tools/list` — тест `skills_*`
   в canvas-mcp). Этот рецепт — человекочитаемая версия того же контракта.

## Шаг 1. Разведка: `canvas_info`, `template_list`, `schemes_list`

- `canvas_info` — что открыто, версия приложения.
- `template_list` — библиотека шаблонов. По каждому шаблону: `params`
  (`default`, `min`/`max`, `unit`) и `outputs` (именованные выходы:
  `name`, `unit`, источник — строка расчёта `line` или формула `expr`).
- `schemes_list` — галерея готовых схем (PRD-0008): если задача похожа
  на «мини-канвас» (бюджет, unit-экономика, ёмкость сервиса), быстрее
  вставить готовую схему `schemes_apply {id, x?, y?}` и править её,
  чем собирать с нуля: один undo-шаг, id ремапятся без коллизий,
   ответ несёт `bbox` (для `viewport_set`) и `flow` с оракулами.

Выберите шаблоны под модель **до** сборки и выпишите имена параметров и
выходов — они понадобятся для адресации рёбер.

## Шаг 2. Ноды: `template_instantiate` и `node_create_note`

- **Стартовые допущения** — текстовая нода `node_create_note`: строки
  вида `имя = значение единица` становятся переменными, строки с формулами
  (`avg_rps = dau * sess * req / 86400 s`) — вычисляемыми. Это единственное
  место, где числа вводятся «руками».
- **Расчётные роли** — `template_instantiate` с `params`: значения вне
  `min`/`max` дадут `E-RANGE`. В батче (шаг 5) params передаются так же.

**Многострочный текст.** В JSON-строке перенос — это настоящий `\n`
(один управляющий символ). Некоторые агенты шлют двухсимвольную
эскапировку `\\n` — приложение нормализует её в перенос толерантно, но
канонический вид — настоящий перенос. Проверка: `flow_recalc` должен
вернуть по ноде столько `lines`, сколько строк вы задумали.

## Шаг 3. Связи: `edge_create` с `kind: "value"`

```
edge_create { from, to, kind: "value",
              fromOutput: "<имя выхода источника>" | fromLine: <номер строки>,
              toParam: "<имя параметра приёмника>" }
```

- `kind` по умолчанию `control` — **визуальная** связь, значение НЕ
  переносится. Для проливания всегда указывайте `kind: "value"`.
- Исток адресуется **по имени**: `fromOutput` — именованный выход шаблонной
  ноды (из `outputs` манифеста, см. шаг 1); `fromLine` — номер строки
  текстовой ноды (адресация живёт при сдвиге строк). Поля взаимно
  исключительны; без обоих многолинейный исток даст `W-AMBIGUOUS-SRC`.
- Приёмник: `toParam` — имя параметра шаблона. Семантика «проливание
  перекрывает локальный параметр»: значение из ребра замещает локальное
  значение параметра приёмника (на карточке оно показывается как
  пролитое, с указанием источника — не как хардкод).
- Имена портов валидируются по снапшотам шаблонов: неизвестный выход/
  параметр → `E-PORT-UNKNOWN`; несовместимая единица → `E-UNIT`;
  второе ребро в тот же `toParam` → `E-DOUBLE-INPUT`; value-цикл → `E-CYCLE`.

## Шаг 4. Проверка чисел: `flow_recalc` и `lineage`

`flow_recalc {}` пересчитывает весь граф и возвращает по каждой ноде:
узловое `value` (+ `unit`), именованные `outputs`, построчные `lines` —
и блок `spilled`: происхождение каждого пролитого в ноду значения (откуда
пришло и в какой параметр). Значения — АКТИВНОГО what-if сценария (те же,
что видит пользователь; база — после `whatif_scenario_activate "База"`).
Блок `autoRows` (FR-050): производные строки приёмников value-рёбер без
`toParam` — путь «Объект.Поле» и значение слота (`unmapped` — значение
не подставлено). Сверяйте числа с ожиданиями модели здесь, а не глазами
по канвасу.

`lineage {node_id, line?}` — дерево происхождения одной цифры (то же,
что окно проверки цепочки у пользователя): по корню спускаетесь до
листьев-констант, `via` даёт рёбра для подсветки. Проза как корень,
`line < 0` и несуществующая нода — isError.

## Шаг 5. Быстрый путь: `graph_apply` (один атомарный батч)

Всю сборку (ноды + params + рёбра) можно сделать **одним вызовом**:

```
graph_apply { operations: [ {op: "node_create_note", ref: "traffic", x, y, text},
                            {op: "template_instantiate", ref: "cdn", template: "...", params, x, y},
                            {op: "edge_create", fromRef: "traffic", toRef: "cdn", kind: "value", ...},
                            {op: "param_set", ref: "cdn", param, value, unit?} ] }
```

- Лимиты: ≤ 256 операций, ≤ 128 новых нод на вызов — превышение ошибка
  уровня вызова.
- `ref` живёт только внутри батча: адресует ноду, созданную ранее в том же
  вызове (forward-ref → `E-NOT-FOUND`, дубликат ref → `E-BAD-OP`).
- **Атомарность:** ошибка любой операции → `{ok: false, op_index, code}`,
  канвас байт-в-байт прежний. Успех → один undo-шаг на весь батч
  (Ctrl+Z откатывает сборку целиком) и автосейв.
- Ответ успеха уже содержит `flow` в формате `flow_recalc` — повторный
  пересчёт не нужен.

## Шаг 6. Финал: `graph_validate`

`graph_validate {}` — обязательный финальный шаг. Ответ:
`{valid: bool, issues: [{severity, code, node_id, edge_id, message}]}`.
**Критерий готовности модели: `valid: true`.**
Коды — стабильный контракт рецепта:

| Код | Severity | Значение | Что делать |
|---|---|---|---|
| `E-CYCLE` | error | цикл value-рёбер | разорвать цикл: value-связи образуют DAG |
| `E-OVERLOAD` | error | утилизация ρ ≥ 1 — очередь растёт неограниченно | мощность узла ниже нагрузки: менять params шага или нагрузку |
| `E-UNIT` | error | единица истока несовместима с параметром приёмника | сверить `unit` выхода и параметра (`template_list`) |
| `E-PORT-UNKNOWN` | error | неизвестный `fromOutput`/`toParam` | имена портов — из манифеста шаблона |
| `E-DOUBLE-INPUT` | error | два value-рёбра в один `toParam` | у приёмника один вход на параметр — вводите агрегат отдельной нодой |
| `W-AMBIGUOUS-SRC` | warning | многолинейный исток без `fromLine`/`fromOutput` | адресовать исток явно |
| `W-UNUSED-SLOT` | warning | позиционный вход `$N` не читается формулой | формула приёмника не ссылается на `$in`/`$N` |

Коды операций `graph_apply` (в ответе `{ok:false, op_index, code}`):
`E-BAD-OP` (форма/поля), `E-NOT-FOUND` (ref/id/шаблон),
`E-PORT-UNKNOWN`, `E-CYCLE`, `E-PARAM-UNKNOWN` (нет строки параметра для
`param_set`), `E-RANGE` (вне min/max).

## Шаг 7. What-if: проверка сценариев без правки модели (FR-017)

После валидной базы можно отвечать на вопросы «а что если трафик ×2?» —
подмены живут в сценарии и **не меняют** `.canvas`, пока вы явно не
примените их.

- `whatif_set_override {node_id, line, expr}` — подмена строки `line`
  текста ноды (нумерация с 0; строки `имя = значение`). Режим и сценарий
  поднимаются автоматически (неявный «Сценарий MCP»); именованный сценарий —
  `whatif_scenario_create {name}` (лимит 3).
- `whatif_set_param {node_id, param, value}` — sugar для шаблонных нод:
  находит строку `param = …` сам.
- `whatif_deltas {}` — дельты активного сценария: по каждой изменившейся
  точке `{base, whatif, delta}` — те же числа, что видны на канвасе
  («было → стало (+Δ)»). Эталон каскада A→B→C с подменой `a = 5 → 20`:
  `{A: 5→20 (+15), B: 10→40 (+30), C: 11→41 (+30)}`.
- `whatif_scenario_activate {name: "База" | "<имя>"}` — переключение;
  файл не трогает. `whatif_scenario_list {}` — сценарии с маркерами
  протухших подмен.
- `whatif_apply {}` — записать подмены в текст нод (один undo-шаг);
  применённый сценарий удаляется. `whatif_reset {}` — сбросить подмены
  активного сценария без Apply.

Правило: сценарий — временный инструмент ответа на вопрос. Постоянные
допущения модели меняйте `param_set`/`node_edit` (шаги 2–5), а what-if
оставляйте неприменённым — файл останется байт-в-байт прежним.

## Типичные ошибки агентов

1. **Literal `\n`**: двухсимвольная эскапировка вместо настоящего переноса
   (приложение нормализует, но канон — перенос; проверяйте `lines`).
2. **Забытый `kind: "value"`**: связь создалась, но значение не течёт —
   дефолт `control`.
3. **Хардкод вместо связи**: число, вычислимое из другой ноды, вписано
   текстом — модель не пересчитается при смене допущений.
4. **Два ребра в один `toParam`** (`E-DOUBLE-INPUT`): разветвление
   нагрузки делается шаблоном-делителем, а не двумя входами.
5. **Несовместимые единицы** (`E-UNIT`): rps не проливается в ms — проверяйте
   `unit` обеих сторон в `template_list`.
6. **Цикл value-рёбер** (`E-CYCLE`): обратную связь «потребитель →
   производитель» моделируйте разрывом (очередь), не ребром.

## Прогоняемый пример: эталон «Instagram MVP» (ADR-0005)

Эталонный сценарий — 12 нод (полное описание и числа:
[ADR-0005](https://github.com/danku13/CanvasDesk/blob/main/docs/adr/adr-0005-instagram-mvp-reference.md)):

| # | Нода | Создание | Параметры |
|---|---|---|---|
| 1 | Трафик-профиль | `node_create_note` | `dau = 1000000`, `sess = 4`, `req = 12`, `peak = 2.5`; формулы `avg_rps`, `peak_rps` |
| 2 | CDN | `template_instantiate` `com.canvasdesk.cdn` | `hit = 60 %` |
| 3 | Балансировщик | `com.canvasdesk.tcp-lb` | доли origin-трафика |
| 4 | API Gateway | `com.canvasdesk.api-gateway` | budget/overhead |
| 5 | Auth | `com.canvasdesk.auth-service` | 15 % |
| 6 | Feed/GraphQL | `com.canvasdesk.graphql` | 60 % |
| 7 | Media | `com.canvasdesk.grpc-service` | 25 % |
| 8 | Кэш | `com.canvasdesk.cache-redis` | `hit = 70 %` |
| 9 | БД master | `com.canvasdesk.db-sql-master` | |
| 10 | БД replica | `com.canvasdesk.db-sql-replica` | |
| 11 | Очередь | `com.canvasdesk.queue-kafka` | |
| 12 | Воркеры | `com.canvasdesk.worker` | |

Цепочки value-рёбер (исток → `toParam` приёмника):

```
1:peak_rps  → 2:rps            6:db_qps       → 9:qps
2:origin_rps → 3:rps           9:replica_load → 10:qps
3:out_gateway → 4:rps          6:events       → 11:produce_rate
3:out_auth    → 5:rps          11:consume_rate → 12:consumed_rps
3:out_feed    → 6:rps
3:out_media   → 7:rps
```

Скелет `graph_apply` (24 операции: 1 текстовая нода + 10 шаблонов + 13
value-рёбер; координаты `x` расставляйте с шагом ~450 по течению слева
направо):

```json
{
  "operations": [
    {"op": "node_create_note", "ref": "traffic", "x": 0, "y": 0,
     "text": "dau = 1000000\nsess = 4\nreq = 12\npeak = 2.5\navg_rps = dau * sess * req / 86400 s\npeak_rps = avg_rps * peak"},
    {"op": "template_instantiate", "ref": "cdn", "template": "com.canvasdesk.cdn",
     "params": {"hit": 0.6}, "x": 450, "y": 0},
    {"op": "template_instantiate", "ref": "lb", "template": "com.canvasdesk.tcp-lb", "x": 900, "y": 0},
    {"op": "edge_create", "fromRef": "traffic", "toRef": "cdn",
     "kind": "value", "fromLine": 6, "toParam": "rps"},
    {"op": "edge_create", "fromRef": "cdn", "toRef": "lb",
     "kind": "value", "fromOutput": "origin_rps", "toParam": "rps"}
  ]
}
```

(остальные 8 шаблонов и 11 рёбер — по таблицам выше; адресация портов —
те же `fromOutput`/`toParam`, текстовый исток — `fromLine` по номеру строки.)

Ожидаемые значения (oracle ADR-0005, допуск ±1 %): `avg_rps` ≈ 555.6,
`peak_rps` ≈ 1389, origin после CDN ≈ 556, auth ≈ 83, feed ≈ 333,
media ≈ 139, чтения БД ≈ 80. Сверка — в ответе `graph_apply`/`flow_recalc`
(блок `flow`).

Проверка воспроизводимости: `param_set`/`node_update_text` на `dau = 2000000`
→ один `flow_recalc` → вся цепочка удваивается без правки связей и формул.

## Чек-лист готовности модели

1. `graph_validate` → `valid: true`.
2. Числа `flow`/`flow_recalc` совпадают с ожиданиями модели (для эталонов
   каталога — с oracle-таблицами ADR-0006 ±1 %).
3. Ни одного хардкод-числа, которое должно было пролиться по value-связи.
4. Любое стартовое допущение меняется **одним** вызовом, и весь downstream
   пересчитывается без правки графа.
