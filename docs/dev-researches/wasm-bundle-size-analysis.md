# Анализ размера wasm-бандла: где экономить (12.25 МБ → цель §8.8 ≤8 МБ raw / ≤4 МБ сжатого)

- **Дата:** 2026-10-03, сессия web-f324f377 (запрос владельца: «нужно проанализировать
  где у нас есть возможность для экономии на wasm бандле»)
- **Объект:** live-бандл Pages main@ece0079, `canvas-web-b99777f7506d48aa_bg.wasm`
  (12 256 156 байт raw, ~4.9 МБ по сети) — тех же пропорций, что и все последние
  деплои (b99777f ≈ c236b3e + FR-093, Δ47 байт)
- **Метод:** разбор wasm-секций и data-сегментов Python-парсером (LEB128/секции/
  md5-атрибуция сегментов к файлам репо; скрипты сессии), Cargo.lock, профили
  сборки, размеры вшитых ассетов. Замеры на выкачанном бинарнике — цифры
  фактические, не оценки.

## 2. Главный резерв №1: 1.82 МБ чистых ДУБЛИКАТОВ в data

Замер: 548 пар сегментов с побайтово одинаковым содержимым (md5), суммарный
«мусор» одной лишней копии — **1 908 940 байт (1.82 МБ, 15.6% бандла!)**.
Крупнейшие пары: 318 412×2, 304 780×2, 304 508×2, 216 633×2, 216 567×2,
65 346×2, 65 340×2, 59 454×2, 21 282×2, 21 216×2, 16 480×2, 16 234×2 …

Причина (по данным Cargo.lock — НЕ дубли версий: все unicode-крейты
одиночные, swash 0.1.19 один): идентичные большие статик-таблицы
(unicode-свойства/скрипты swash/cosmic-text, шрифтовые и прочие константы)
материализуются LLVM'ом в нескольких кодген-юнитах, а
**`lto = "thin"` их не схлопывает** — wasm-opt дубликаты data-сегментов тоже
не дедуплицирует. Классическая проблема wasm-сборок.

**Рецепт №1 (низкий риск, ≈ −1.8 МБ):**

```toml
[profile.release]
lto = "fat"          # было "thin": схлопывает одинаковые константы между CGU
codegen-units = 1    # один CGU — меньше дублей и лучше межкрейтовая оптимизация
```

Цена: рост времени линковки релизной сборки (минуты в CI, кэш
Swatinem/rust-cache смягчает). Рисков для рантайма нет — это линк-время.

## 3. Резерв №2: настройки кодогенерации (code 6.78 МБ)

Сегодня в `[profile.release]` задан только `lto = "thin"` — opt-level
остался дефолтным (3, «скорость»), panic-стратегия unwind, codegen-units
дефолт (16). Для UI-приложения, где кадр ограничен GPU, а не CPU, это
передоз:

| Рецепт | Оценка экономии | Риск |
|---|---|---|
| `opt-level = "s"` (или `"z"`) | −15…−30% code (−1.0…−2.0 МБ) | CPU-пути (layout/шейпинг) становятся плотнее, но медленнее на единицы %; замерить fps на витрине/зуме. При необходимости точечно вернуть opt-level=3 горячим крейтам (`[profile.release.overrides]`… аккуратно: overrides от контейнера) |
| `panic = "abort"` | −5…−10% code (снятие landing-pad'ов unwind) | panic-hook остаётся (сообщение в консоль), но unwind больше невозможен — поведение после паники = жёсткий трап (сейчас и так заканчивается `RuntimeError: unreachable`); `catch_unwind` в коде не используется |
| `strip = true` | ~0 (name-секций в бандле уже нет — wasm-opt вычищает) | нет |

**Итог рецептов №1+№2: реалистично 12.25 → 7.5–9 МБ raw, ~3.0–3.6 МБ gzip.**

## 4. Резерв №3: шрифты (1.86 МБ) — вынос из бинарника

Сейчас 6 ttf вшиты в wasm (CR-009: отдельные статики весов 500/700,
CanvasDeskSymbols — сабсет 21 глифа, MonoOblique — синтез). Все релизы
меняют хеш wasm — шрифты перекачиваются при каждом выкате, хотя сами
не меняются годами.

Варианты (по убыванию соотношения эффект/сложность):

1. **Вынос в статик-файлы `/app/fonts/*.ttf` + fetch до старта**
   (web-sys `fetch` → `load_font_data`): −1.86 МБ из wasm; шрифты кешируются
   CDN отдельно и переживают выкаты (immutable-кеш); загрузка параллелится
   с компиляцией wasm. Цена: асинхронный гейт инициализации TextSystem
   (renderer_launch уже асинхронный — паттерн есть) и «пустой текст» на
   первые сотни мс (или спиннер первого кадра).
2. **Дожать сабсеты** (NotoSansDisplay-Medium/Bold по 326 КБ — это полные
   Latin+Cyrillic+расширения; фактически используемые глифы UI — сотни):
   pyftsubset → −50…−70% на каждый ttf. Дёшево, но требует ведения списка
   глифов (текст i18n/doc известен статически — скрипт в build).
3. woff2 вместо ttf — НЕ вариант: fontdb/cosmic-text парсят ttf/otf;
   распаковка woff2 добавила бы код и зависимость.

## 5. Мелкие резервы (для полноты, в порядке убывания)

- **i18n-строки ~353 КБ**: лениво подгружать неактивный язык (RU вшит, EN —
  fetch при переключении; ~176 КБ). Усложняет i18n-контракт «tr без сети» —
  делать только если сеть уже dependency (после рецепта §4.1).
- **user-docs 155 КБ**: сейчас офлайн-инвариант («без сети и FS», FR-039) —
  осознанно держим; вынос возможен только с сменой инварианта.
- **Иконки (icon_data.rs, растеризованные RGBA в `pub const`)**: монохром
  белый-на-прозрачном — отлично брутлится/гзипится в сети (~×3–4), в raw
  бандле занимает сотни КБ; вынос тем же §4.1-паттерном (один .bin) снимет
  и это. Прежде чем мерить — после рецепта №1 дубликаты исчезнут, цифра
  станет честнее.
- **Крейт-дубли версий** (Cargo.lock: `getrandom` ×3, `ttf-parser` ×3,
  `syn`/`thiserror` ×2 — proc-macro в wasm не попадают; `ttf-parser` три
  версии ~десятки КБ): выравнивание версий — копейки, но гигиенично.

## 6. Сеть: как сегодня жмётся

GitHub Pages отдаёт wasm с ~4.9 МБ transfer (gzip, ratio ~2.4×; brotli на
Pages недоступен для управления — precompressed-файлы игнорируются). После
рецептов №1+№2 ожидаемо ~2.8–3.6 МБ — с запасом под §8.4 «деплой грузится
≤5 с на 25 Мбит/с» даже с учётом +запросов на шрифты из §4.1.

## 7. План (приоритеты)

1. **PR «lto=fat + cgu=1»** — 2 строки в Cargo.toml, замер бандла в
   web_bundle-отчёте CI (§8.8 уже печатается). Ожидание: −1.5…−2 МБ.
2. **PR «opt-level=s (+ panic=abort по решению владельца)»** — замер
   размера + смоук fps (витрина, зум, heaviest-канвас).
3. По решению владельца — вынос шрифтов (§4.1) и, при смене офлайн-инварианта
   доков, остальное из §5.
4. Пересмотреть лимиты §8.8, если после 1–2 останемся выше 8 МБ raw
   (бандл вырос функционально: FR-063 статистика, FR-090 телеметрия,
   FR-092 тач, иконки, схемы) — либо держать бюджет, либо поднять планку
   осознанно.

Все замеры этой сессии воспроизводимы: секции/сегменты парсились
Python-скриптом (LEB128 + md5-атрибуция), отчёт web_bundle.sh в CI печатает
raw/brotli по файлам — следующая итерация просто сравнивает две строки
отчёта.
