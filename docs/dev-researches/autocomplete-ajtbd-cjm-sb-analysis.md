**Дата:** 27.09.2026
**Автор:** агент-сессия (Super Z)

**База:** репозиторий CanvasDesk, commit `299811a`
**Тип:** технический анализ применимости существующей архитектуры к новой продуктовой задаче

## 0. Постановка задачи

Владелец ставит три вопроса по расширению продуктового скоупа гипотезы `inline-ai-autocomplete-hypothesis.md`:

1. **Применима ли архитектура L0/L1/L2 к задаче подсказок по построению аналитических фреймворков** — AJTBD (Agile Jobs-To-Be-Done), CJM (Customer Journey Map), Service blueprint и подобных? Документ прорабатывает автодополнение нод на расчётных схемах (юнит-экономика, capacity-service, runway). Вопрос — расширяема ли концепция на «скелетообразующие» фреймворки, где ноды не вычисляют, а описывают.
2. **Достаточно ли Laya/Jev или потребуется SLM** для нового класса сценариев?
3. **Как формировать RAG-базу знаний, и нужен ли RAG в принципе, или достаточно fine-tuning?**

Анализ ниже даёт ответ на каждый вопрос и сводит их в единую рекомендацию.

## 1. Что в документе есть, а чего нет

### 1.1 Что гипотеза покрывает сегодня

Документ прорабатывает пять сценариев автодополнения `С1–С5`, все — на **исполняемом расчётном графе**:

| Сценарий | Слой | Что предлагает |
|---|---|---|
| С1. Ввод формулы в ноде | L0+L1 | переменные скоупа + шаблон по контексту |
| С2. Вставка данных | L0+L1 | распознавание структуры → шаблон |
| С3. Добавление шаблонной ноды | L1+L2 | кластер связанных нод (`graph_apply`) |
| С4. Пустая нода | L1 (on-demand) | 3–5 вариантов наполнения |
| С5. Пост-коммит | L2 (async) | рекомендации в панели |

Корпус: 62 шаблона (`assets/templates/com.canvasdesk.*`), 11 эталонных схем (`assets/canvas-schemes/com.canvasdesk.scheme.*`), 40+ доменных функций (`mm1`, `mmc`, `erlang_c`, `npv`, `irr`, `cohort_ltv` …). Шаблон — вычислительный: `template.json` с полем `expr` (формула Numi-парсера), параметрами с типами и единицами.

### 1.2 Чего в документе нет

В корпусе **нет ни одного шаблона или эталонной схемы для AJTBD, CJM или Service blueprint** (проверено: `ls assets/templates/ | grep -iE 'cjm|jtbd|blueprint|journey|persona|service'` возвращает 0 совпадений). Гипотеза в текущем виде покрывает только **исполняемое математическое моделирование**; аналитические фреймворки как класс сценариев не обсуждаются.

Раздел 4.1 упоминает JTBD — но **в продуктовом позиционировании** (job-to-be-done формулировки персон: «когда… я хочу… чтобы…»), а **не как тип генерируемого артефакта**. То есть JTBD в документе — это язык описания ценности, не объект построения на канвасе.

## 2. Архитектурная применимость: ответ «да, с минимальной дельтой»

Архитектурные активы, перечисленные в §3 гипотезы, **достаточны** для расширения на AJTBD/CJM/Service blueprint. Нужны точечные дополнения, а не переписывание.

### 2.1 Что подходит «как есть»

**Точка триггера.** `update_hints()` (`app/overlays.rs:1776`) — единый фаннел ввода/вставки/IME. Подсказка «после Awareness обычно идёт Consideration» — это та же `Suggestion { kind: Cluster, payload: { template: "cjm-stage-consideration", edges: [...] } }`, что и в С3. Никаких новых триггеров.

**Вставка кластера.** `graph_apply` (`canvas-scene/src/mcp.rs:1550`) — атомарный батч до 256 операций (создание нод, рёбер, `param_set`, перемещения) с валидацией DAG и одношаговым undo. «Вставить скелет CJM из 5 стадий и 12 тачпоинтов» — это ровно один вызов `graph_apply`. Контракт уже отработан на ИИ-агентах (С5).

**Сериализация контекста.** Подграф 1–2 hop от редактируемой ноды + «шапка» канваса (число нод по категориям, переменные верхнего уровня) — это всё, что нужно L1 для ответа «какую секцию CJM я сейчас строю». Никаких новых проекций: `nodes_list(text=true)`, `edges_list`, `lineage` уже существуют (§9.1).

**Паттерн flow-worker.** `worker.rs` (thread + mpsc + `EventLoopProxy` + double-buffer) — выделенный поток для неблокирующих подсказок. L1 для фреймворков живёт в том же паттерне.

**Ревью-диалог.** Прецедент `autolink_batch` (undo-тегом) — образец для «предложить кластер из 8 нод Service blueprint, пользователь согласился/отклонил/изменил».

### 2.2 Что нужно добавить — дельта

| # | Дополнение | Где | Объём |
|---|---|---|---|
| 1 | **Новая категория шаблонов: `framework`** (без `expr`, со `structure`) | расширение `template.json` schema | Малый: добавить optional-поле `structure: { nodes: [...], edges: [...] }` или сделать «framework» отдельным типом схемы |
| 2 | **Шаблоны AJTBD/CJM/SB** как корпус | `assets/templates/com.canvasdesk.fw.*` (15–25 шт.) | Средний: спроектировать доменную онтологию (стейджи CJM, слои SB, типы job) |
| 3 | **Эталонные схемы фреймворков** | `assets/canvas-schemes/com.canvasdesk.scheme.*` (3–5 шт.) | Малый: JSON-канвас, тот же формат что у unit-economics |
| 4 | **Новые типы вопросов Laya** | `SuggestEngine`-трейт | Малый: `choose_stage`, `choose_touchpoint_type`, `choose_sb_layer` — те же `choice`/`noul`, что и в §10.1 |
| 5 | **Валидатор структурной целостности** (не путать с валидатором формул) | новый модуль в `canvas-core` | Малый: проверка «stage с типом `awareness` не может идти после `advocacy`», «у SB-ноды должны быть front-stage и back-stage соседи» |

**Главное наблюдение:** для AJTBD/CJM/SB **не нужна валидация формул и единиц** — это принципиально упрощает реализацию. Нужна только валидация DAG-структуры и типов нод (есть в `graph_apply`).

### 2.3 Сценарии расширения (отображение С1–С5 → FW1–FW5)

| Гипотеза | Аналог для фреймворков | Что предлагает |
|---|---|---|
| С1 (ввод) | **FW1. Ввод названия тачпоинта** | по мере ввода «отзыв на» — L1 подсказывает типичный пейн-пойнт в этой стадии CJM по эталонной схеме отрасли |
| С2 (paste) | **FW2. Вставка брифа/транскриба интервью** | L1 распознаёт упоминания стадий и тачпоинтов → предлагает разложить на узлы CJM |
| С3 (add node) | **FW3. Добавление стадии CJM** | L2 через `graph_apply` вставляет весь подскелет: тачпоинты + emotions + opportunities для стадии |
| С4 (empty) | **FW4. Пустая нода в SB-слое** | L1 on-demand: 3–5 типичных back-stage процессов для этой front-stage точки |
| С5 (post-commit) | **FW5. Пост-коммит фреймворка** | L2 предлагает дополнить CJM недостающими стадиями по эталону отрасли |

**Вывод раздела 2:** архитектура расширяема. Дельта — 5 пунктов, самый большой — проектирование доменной онтологии (он же — корпус для RAG, см. раздел 4).

## 3. Laya/Jev vs SLM: ответ по матрице §10.2

Документ даёт исчерпывающую матрицу сравнения (§10.2) — она применима к новому классу сценариев почти дословно, с одной важной переоценкой.

### 3.1 L1 (быстрые ИИ-решения): Laya — дефолт

Типы решений L1 для AJTBD/CJM/SB — все **типизированные выборы**:

- `choose_framework`: какой фреймворк уместен (CJM vs JTBD vs SB) по контексту канваса
- `choose_stage`: определить стадию CJM по тексту ноды
- `choose_touchpoint_type`: тип тачпоинта (digital / human / physical)
- `choose_sb_layer`: слой Service blueprint (front / back / support / physical evidence)
- `show_suggestion`: гейтинг показа (порог по `answer_confidence`)

Это **классическая задача System One Models** — выбор из ограниченного множества (5–20 опций) с калиброванной вероятностью. Laya для неё спроектирована, Jev — её коммерческий облачный аналог, SLM — overkill и хуже по калибровке.

| Критерий | Laya локально (421M) | Jev облако | SLM (Qwen3-0.6B и др.) |
|---|---|---|---|
| Латентность L1 | GPU 55–70 / CPU 220–330 мс | 150–200 мс | 50–80 мс (решающие) |
| Калибровка (ECE) | 0.081 (RLCD) | по построению | требует t-scaling |
| Офлайн | Да | Нет (конфликт AGENTS.md) | Да |
| Кардинальность опций | комфортно ~20, потолок ~126/254 | до 255 из коробки | не ограничена, но качество падает |
| Стоимость | $0 | $0.042/MTok (~$0.6/польз./мес) | $0 |
| Зрелость | 9 дней, но 26k звёзд, экосистема 42+ Rust-портов | early access | многолетний класс |

**Вердикт для L1:** Laya локально как дефолт, Jev облако как opt-in для пользователей, готовых отправлять контекст наружу (вариант для команд без локального GPU). SLM не нужен.

### 3.2 L2-лайт (короткая генерация на GPU/NPU): SLM — единственный локальный кандидат

**Главное отличие от расчётных сценариев документа:** для AJTBD/CJM/SB пользователю нужны **текстовые наполнения**, а не формулы. Примеры:

- Сгенерировать формулировку job story: «Когда [ситуация], я хочу [мотивация], чтобы [ожидаемый результат]»
- Сгенерировать типичный пейн-пойнт для тачпоинта «регистрация через SMS» в финтех-отрасли
- Сгенерировать 3 варианта тачпоинта для стадии «Consideration» в e-commerce

Это **короткая авторегрессионная генерация** (20–40 токенов), которая физически невозможна для Laya (non-autoregressive by design) и которая не помещается в 200 мс на CPU, но **укладывается в расширенный допуск 1 с** на GPU/NPU-железе (см. §8.1: 140–350 мс на дискретной GPU для 24 токенов).

Здесь SLM (Qwen3-0.6B, Gemma 3n-E2B, LFM2-1.3B) — **единственный локальный кандидат**. Облачная LLM через существующий MCP-агент (`graph_apply`) — альтернатива, но медленнее и нарушает приватность.

**Вердикт для L2-лайт:** SLM 0.5–1.7B Q4 как **опциональный** путь для пользователей с GPU/NPU; до этого — L2 через MCP-агента на BYO-модели пользователя (как сегодня).

### 3.3 Сводная рекомендация

| Слой | Движок | Обоснование |
|---|---|---|
| L0 | правила + fuzzy | детерминированный, $0, мгновенно |
| L1 | **Laya локально (дефолт)** / Jev облако (opt-in) | типизированные решения с калиброванной уверенностью |
| L2-лайт | **SLM 0.5–1B Q4** на GPU/NPU (опционально) | короткая текстовая генерация (job stories, pain points) — единственное, чего Laya не умеет |
| L2-полный | существующий MCP-агент + BYO-LLM пользователя | кластеры, длинный текст |

**Прямой ответ на вопрос:** для L1 SLM **не требуется** — Laya покрывает все типизированные выборы фреймворков. Для L2-лайт SLM **полезен, но опционален** — это не блокер фазы 1–2, а эксперимент фазы 3 (см. §14 роадмапа).

## 4. RAG vs fine-tuning: что, как и когда

Документ (§11) даёт чёткое дерево решений. Для нового класса сценариев (AJTBD/CJM/SB) стратегия сохраняется дословно, но **корпус для RAG меняется**.

### 4.1 Структура RAG-корпуса для фреймворков

Статическая часть (пересобирается с релизом):

| Блок | Содержание | Объём |
|---|---|---|
| Каталог фреймворков | онтологии JTBD, CJM, SB: стадии, типы тачпоинтов, слои SB, типы job | 3 фреймворка × 10–20 элементов = ~50 документов |
| Шаблоны-схемы фреймворков | готовые скелеты для 5–7 отраслей (e-commerce, финтех, SaaS, медиа, образование, здравоохранение, логистика) | 5–7 схем × 10–15 нод = ~100 документов |
| Типовые тачпоинты и пейны | база паттернов «в стадии X отрасли Y встречаются тачпоинты A, B, C с пейнами D, E» | ~150 документов |
| Каталог job patterns | стандартные формулировки job stories по контексту | ~50 документов |
| Справочник типовых эмоций и метрик | для CJM-полос эмоций и KPI-строк | ~30 документов |
| **Итого статика** | ~380 документов | (плюс 200 документов существующего расчётного корпуса = ~580) |

Динамическая часть (обновляется с канвасом):

- Вставленные тахпоинты пользователя (для личизации)
- Job stories пользователя
- Кэш эмбеддингов нод по `scene.revision`

**Мультиязычность** корпуса (ru/en) — обязательна с первого дня: пользователь пишет формулировки тачпоинтов по-русски, а термины фреймворков — латиницей.

### 4.2 Гибридный ретрив (тот же, что в §9.2)

1. **Лексический** (fuzzy по имени/типу/стадии) — развитие текущего substring-фильтра `template_ui.rs`
2. **Векторный** (multilingual-E5-small / bge-small int8, 5–10 мс CPU, fastembed/candle) — для смыслового матчинга «пользователь пишет про отток клиентов → подсказать retention-стадию CJM»
3. **Структурные эвристики** — аналог `autolink.rs`: «если на канвасе уже 3 тачпоинта одной стадии CJM — предложи следующую стадию»; «если у SB-ноды front-stage есть, а back-stage нет — предложи back-stage»

Финальное ранжирование — **reciprocal rank fusion** + бонусы структурных совпадений; для топ-кандидатов — опциональный L1-реранк через Laya (механизм `predict_shortlist` — готовая реализация L0→L1).

Индекс 380 документов — наивный линейный скан < 1 мс; HNSW не понадобится до десятков тысяч.

### 4.3 Что ретривится в каждом сценарии FW1–FW5

| Сценарий | Что достаёт RAG |
|---|---|
| FW1 (ввод тачпоинта) | типичные пейны стадии по отрасли + функции по префиксу |
| FW2 (paste брифа) | шаблоны фреймворков под структуру текста (CJM, если есть упоминания стадий) |
| FW3 (добавление стадии) | подскелет стадии из эталонной схемы отрасли + шаблоны тачпоинтов, чьи входы тип-совместимы |
| FW4 (пустая нода) | наполнения по lineage соседей + типовые элементы слоя SB |
| FW5 (пост-коммит) | недостающие стадии по эталону + кейсы смежных отраслей |

### 4.4 Когда RAG, когда fine-tuning — стратегия §11 в применении

| Этап | Что делаем | Триггер |
|---|---|---|
| **Этап 1 (фаза 1 роадмапа)** | RAG + правила + few-shot в L1 | старт; корпус мал (~580 документов), обновляется с релизом мгновенно, $0 |
| **Этап 2 (фазы 1–2)** | сбор данных `suggest_shown/accepted/dismissed/edited` + хэш контекста; цель 10–50k событий | накопление данных |
| **Этап 3 (фаза 3, при plateau)** | **fine-tune головки Laya** на замороженном энкодере (Kaggle 2×T4, цикл в ноутбуке); калибровка встроена в RLCD-награду; публикация чекпойнта в HF Hub | acceptance rate перестал расти от правил/промптов |

**Техника fine-tune:** Laya-головка (30–100M параметров) поверх замороженного ModernBERT/mmBERT-энкодера — **не full SLM**. Документированный эффект: 0.362 → 0.766 на typed-decisions. Это **дешевле, прицельнее и калиброваннее**, чем LoRA на Qwen3-0.6B.

**Запасной путь:** LoRA на 0.5–1B SLM (rank 8–32) — только если L2-лайт-генерация (job stories, пейны) признаётся критичной и нужно доменное дообучение генерации, а не выбора. Прецедент: Qwen3-0.6B после SFT — 75.9% BFCL без chain-of-thought.

### 4.5 Прямой ответ на вопрос владельца

- **RAG нужен с первого дня** (фаза 1). Это базовый слой, не опциональный: корпус структурирован и мал, обновляется с релизом, $0, не требует ML-конвейера. RAG доставляет **кандидатов и контекст**, L1 (Laya) ранжирует их с калиброванной уверенностью.
- **Fine-tuning нужен на фазе 3**, не раньше. Триггер — plateau метрик после накопления 10–50k событий accept/dismiss. Техника — fine-tune головки Laya (не full SLM, не LoRA на SLM как основной путь).
- **Альтернатива «только fine-tuning, без RAG»** — нерациональна: fine-tune не решает появление новых шаблонов и отраслевых онтологий (их по-прежнему доставляет RAG), дороже в обслуживании (ML-конвейер vs JSON-каталог), и калибровка вероятностей, встроенная в RLCD, не помогает с **fresh-контентом**.

## 6. Главные выводы

1. **Применимость:** архитектура L0/L1/L2 расширяема на AJTBD/CJM/Service blueprint с минимальной дельтой (5 точечных дополнений, самое крупное — проектирование доменной онтологии). Главные активы CanvasDesk (`graph_apply`, `update_hints`, flow-worker, ревью-диалог, `autolink`) — переиспользуются без изменений.

2. **Laya/Jev vs SLM:** для L1 SLM не требуется — Laya локально как дефолт (типизированные выборы с калиброванной уверенностью). SLM 0.5–1B Q4 — единственный локальный кандидат для L2-лайт (генерация job stories, пейнов), но это опционально и фаза 3.

3. **RAG vs fine-tuning:** RAG нужен с первого дня (фаза 1) — это базовый слой. Fine-tuning — фаза 3, при plateau метрик и ≥10k событий. Техника: fine-tune головки Laya (не full SLM). Альтернатива «только fine-tuning» нерациональна: не покрывает fresh-контент и дороже в обслуживании.

4. **Главный продуктовый риск расширения** — позиционирование. CanvasDesk сегодня — «визуальная система математического моделирования» (`AGENTS.md`, ADR-0007). AJTBD/CJM/SB — не математика. Расширение требует либо (а) расширения позиционирования продукта до «визуальная система моделей и фреймворков», либо (б) вынесения фреймворков в отдельный sub-product с собственным позиционированием. Решение за владельцем.

5. **Что не нужно делать:** строить собственный рантайм-ранкер с нуля (Вариант C из §10.2) — Laya уже даёт открытую платформу для специализации; тратить время на WebLLM до нативных путей; пытаться «натянуть» генерацию текста на Laya (non-autoregressive by design, невозможно).
