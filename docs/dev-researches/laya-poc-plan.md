## 1. Вопрос пилота и границы

PoC отвечает на один вопрос: **закрывает ли Laya сценарии С1–С5 на реальных контекстах CanvasDesk с качеством и производительностью, достаточными для фазы 2.** Формально проверяются два допущения родительской гипотезы:

- **Допущение В** — «контекст канваса достаточно богат, чтобы предложения были релевантны чаще, чем бесполезны»;
- **Допущение Д** — «открытый движок Laya достаточно зрел и точен, чтобы строить на нём продуктовую фичу» (zero-shot базовых чекпойнтов на сложных typed-decisions — 0.362 ≈ random; наш домен не входил в их бенчмарки).

Дополнительно фиксируются **фактические ограничения** (кардинальность опций, качество на русском, поведение confidence) и **производительность** (латентность на реальном железе, RAM, холодный старт) — эти числа напрямую кормят решение о дефолте движка в фазе 2 и пороги гейтинга в продукте.

**Non-goals (что пилот сознательно не проверяет):**

- генерация нового (L2) — вне природы движка (non-autoregressive);
- UI/UX (ghost text, попап, карточки) — измеряется качество решений, не интерфейс;
- интеграция в репозиторий — harness живёт вне кодовой базы, sidecar отдельным процессом, AGENTS.md/wasm-гейты/CI не затрагиваются;
- fine-tune — только как yellow-ветка после гейта (§9);
- web-версия — desktop-контексты; браузерный порт Laya — отдельный эксперимент фазы 2+.

## 3. Архитектура PoC-стенда

Всё вне репозитория CanvasDesk (например, `~/laya-poc/`, собственный git). Python 3.11+, зависимости: `requests`, `rank_bm25`, `numpy`, `psutil` (+ `laya[serve]` в отдельном venv sidecar'а). Никаких изменений в 11 крейтах.

```
~/laya-poc/
├── corpus/                  # снимок данных репо (read-only)
│   ├── templates/*.json     # 62 манифеста (assets/templates на базе d91c619)
│   ├── schemes/*.json       # 11 эталонных схем (assets/canvas-schemes)
│   └── canvases/*.canvas    # реальные канвасы (examples/ + предоставленные владельцем)
├── builder/                 # датасет-билдер (источники А/Б/В)
│   ├── carve.py             # hole-carving по схемам/канвасам → контексты + автоголден
│   ├── synth.py             # синтетика С1–С5 по user stories
│   └── labelpack.py         # пакет для ручной разметки (CSV + инструкция)
├── serialize.py             # схема контекста v0 (§4)
├── shortlist.py             # L0-префильтр кандидатов до ≤20 (правила)
├── baseline_lex.py          # лексический baseline (BM25 + char3 + синонимы)  [заморозка]
├── baseline_l0.py           # эмуляция L0-правил (что выбрали бы правила)      [заморозка]
├── client.py                # HTTP-клиент POST /v1/systemone + батч вопросов
├── runner.py                # прогон: фикстуры × {laya-en, laya-mm, laya-td} × {zero-shot}
├── measure.py               # латентность/RAM (warmup, n≥100, холодный старт)
├── metrics.py               # p@k, MRR, ECE, Wilson CI
└── report/                  # итоговые таблицы, gate.yaml, вердикт
```

**Поток данных:** `corpus → builder → evalset/*.jsonl → (serialize + shortlist) → runner → (laya sidecar :8000 / baselines) → metrics → report → гейт`.

**Плечи сравнения (одинаковые входы):**

1. `random` — нижняя граница (сид фиксирован);
2. `L0-rules` — что выдали бы детерминированные правила (эмуляция фазы 0);
3. `lex-baseline` — BM25 + char-n-граммы + словарь ru/en-синонимов домена;
4. `laya-en` — чекпойнт 421M ModernBERT-large (английский);
5. `laya-mm` — чекпойнт 322M mmBERT (мультиязычный, русский);
6. `laya-td` — чекпойнт 421M typed-decisions;
7. *(опционально)* `jev-cloud` — если у владельца есть early access: reference-верхняя граница класса.

Чекпойнты 4–6 дают ответ на «какой бэкbone для ru-домена» без отдельного эксперимента.

## 4. Схема контекста v0 (что видит модель)

### 4.1. Токен-бюджеты (из документации Laya)

| Параметр | laya-en | laya-mm / laya-td | Наш конфиг |
|---|---|---|---|
| `head_max_len` (бюджет опций вопроса) | 192 | 256 | **512** (поднят: 20 опций × ~16 токенов ≈ 320) |
| Бюджет `state` (сериализация контекста) | ~320 | ~768 | цель ≤ 400 |
| Итого на запрос | ~512 | ~1024 | ≤ 720 + опции |

Вывод: контекст v0 проектируется под **≤ 400 токенов**; больше — не влезает в laya-en без обрезки. Вариант B (JSON-сериализация, как в Приложении А гипотезы) — запасной: ~2× дороже по токенам, включается только если текстовый формат неожиданно провалит smoke-тест (решение фиксируется на Д1).

### 4.2. Формат v0 — компактный текст (не JSON)

Токены экономим сокращением ключей; человекочитаемость сохраняется для отладки.

**Задача `suggest_template` (С3, С4):**

```
[canvas] 14 nodes; cats: ue(9) infra(3) pa(2); vars: revenue=1.2M RUB/mo, users=8000
[node] title="CAC"; editing="траты на маркетинг 350 000 ₽/мес, привлечено клиентов "
[up] "MRR" (ue-mrr) out: mrr
[up] "Маркетинг" (text) out: mkt_spend
[down] "LTV/CAC" (ue-ltv-cac) needs: cac
```
```
POST /v1/systemone
{ "state": { "document": "<текст выше>" },
  "questions": { "choose_template": {
      "type": "choice",
      "instructions": "Which template best fits the node being edited?",
      "criteria": {
        "ue-cac": "CAC — стоимость привлечения клиента; params: spend(RUB), clients",
        "ue-arppu": "ARPPU — выручка на платящего; params: revenue, payers",
        "...": "... (всего ≤ 20 опций shortlist'а)",
        "none": "no template fits" } },
    "show_suggestion": { "type": "noul",
      "instructions": "Is the context specific enough to suggest?" } } }
```

**Задача `match_variable` (С1, С2):** та же секция `[node]`, но `criteria` — переменные скоупа и константы; golden — реальный операнд формулы.

**Задача `suggest_next_nodes` (С5):** контекст расширяется секцией `[down]`/`[scheme]` (какие категории уже представлены), `criteria` — шаблоны-кандидаты кластера.

### 4.3. Поля сериализатора и правила

| Поле | Источник в модели данных | Правила |
|---|---|---|
| `[canvas]` | `Canvas.nodes` агрегаты | счётчики по категориям, топ-5 переменных верхнего уровня |
| `[node]` | `EditingSession`, `Node.title` | текст до каретки, ≤ 120 символов; title; template_id если есть |
| `[up]`/`[down]` | рёбра 1-hop (`Edge`) | title, template_id, outputs/needs; ≤ 4+4, приоритет по связности |
| `vars` | `Env` (резолвенные) | имя=значение+единица, ≤ 8 |
| `criteria` | shortlist (§3) | ≤ 20 опций; `none` обязателен; позиция golden перемешана сидом |

Сериализатор детерминирован: один контекст → одна строка (порядок полей фиксирован) — это условие воспроизводимости и кэшируемости.

## 5. Методика сбора eval-сета

### 5.1. Источник А — «вырезание дыр» из эталонных схем (автоголден)

Механика по шагам:

1. Взять `scheme.json` (11 штук: unit-economics, runway, ab-testing, capacity-service, …).
2. Для каждой ноды, инстанцированной из шаблона: временно удалить её и её рёбра.
3. Сериализовать контекст оставшейся схемы в позиции удалённой ноды (схема v0).
4. Golden = `(template_id удалённой ноды, маппинг её параметров на переменные/константы, рёбра к восстановлению)`.
5. Shortlist = L0-префильтр всех 62 шаблонов (совместимость категорий, связность) до ≤ 20, golden гарантированно включён.

Оценка выхода: 11 схем × 8–15 шаблонных нод ≈ **100–160 контекстов** с бесплатным golden. Дополнительно derive-задачи: для формульных нод — `match_variable` по реальным операндам выражения.

### 5.2. Источник Б — реальные канвасы

`examples/demo-numi.canvas` из репо + канвасы владельца (если предоставит; достаточно 3–5 рабочих файлов `.canvas`). Та же механика вырезания, но golden проходит экспертную проверку (реальные канвасы содержат «шум» — ноды, которые сам автор удалил бы). Оценка: **30–80 контекстов**.

### 5.3. Источник В — синтетика по user stories С1–С5

Скриптованные последовательности: пользователь печатает текст узла (С1 — с типизированными «опечатками» и ru/en вперемешку), вставляет буфер (С2 — CSV/таблица/проза), открывает палитру после шаблонной ноды (С3), оставляет пустую ноду и уходит (С4), завершает схему (С5 — «что дальше»). Golden для С1/С2 размечает владелец; С3–С5 частично автоматизируются (правильный ответ известен из сценария). Оценка: **100–250 контекстов**.

### 5.4. Целевое распределение

| Срез | Доля | Контекстов (при 400) |
|---|---|---|
| По сценариям: С1 / С2 / С3 / С4 / С5 | 25% / 20% / 25% / 15% / 15% | 100 / 80 / 100 / 60 / 60 |
| По задачам: suggest_template / match_variable / show_suggestion / next_nodes | 40% / 25% / 20% / 15% | 160 / 100 / 80 / 60 |
| По источникам: А / Б / В | ~35% / ~15% / ~50% | 140 / 60 / 200 |
| По locale: ru / en / смешанный | 50% / 25% / 25% | 200 / 100 / 100 |

`show_suggestion`-контексты наполовину негативные (контекст пустой/шумный → golden «не показывать») — иначе метрика калибровки бессмысленна.

### 5.5. Формат фикстуры (JSONL)

```json
{
  "id": "A-unit-econ-07-n42",
  "source": "A:scheme.unit-economics",
  "scenario": "C3",
  "task": "suggest_template",
  "locale": "ru",
  "context": "<сериализация v0>",
  "options": [
    {"id": "ue-cac", "desc": "CAC — стоимость привлечения клиента; params: spend(RUB), clients"},
    {"id": "none", "desc": "no template fits"}
  ],
  "golden": {"choice": "ue-cac", "params": {"spend": "mkt_spend", "clients": "…"}, "edges": []},
  "meta": {"difficulty": "medium", "n_options": 20, "seed": 42, "carved_from": "n42"}
}
```

### 5.6. Контроль качества сета

- golden гарантированно в `options` (авто-проверка);
- дедупликация по хэшу контекста (близкие дыры одной схемы могут дублироваться — оставляем ≤ 2 вариации);
- `n_options ≥ 8` (иначе задача тривиальна) — контексты с меньшим числом помечаются и не входят в основную метрику;
- позиции golden в списке перемешаны фиксированным сидом;
- **сплиты dev/test = 60/40**, стратификация по сценарию и исходной схеме; контексты одной схемы не пересекают сплиты (нет утечки);
- разметка В: пакет `labelpack.csv` (контекст, опции, колонка выбора), двойная разметка 10% выборки агентом, согласие ≥ 0.7 по Каппа Коэна, разногласия разбираются с владельцем.

**Переиспользование:** eval-сет становится seed-датасетом yellow-ветки (fine-tune) и фазы 3, а также golden-фикстурами `SuggestEngine` в фазе 2 — вложение не сгорает ни при каком исходе гейта.

## 6. Метрики и протокол измерений

### 6.1. Качество выбора

- **p@1** (golden == top-1), p@3, **MRR@5**, recall@5 — для choice-задач;
- сравнение плеч: random → L0 → lex → laya-{en,mm,td} (→ jev-cloud, опц.);
- Wilson 95% CI на все доли (при n=400 p@1=0.6 CI ≈ ±0.048);
- `param_exact_rate` — доля контекстов, где golden-маппинг параметров точно совпал (вторичная, для С1/С2).

### 6.2. Калибровка и гейтинг

- `show_suggestion` (noul): accuracy, F1 против golden-бит;
- **ECE** (15 бинов, `answer_confidence`): сырой и после temperature-скейлинга, температура подбирается **только на dev**;
- рабочая точка гейтинга: порог confidence, при котором precision ≥ 0.9 на dev → отчёт «какой % показов переживает порог» (show-rate).

### 6.3. Латентность и ресурсы

Методика: warmup ≥ 10 запросов, затем ≥ 100 измерений, клиент однопоточный, `time.perf_counter()` вокруг HTTP-вызова; фиксируются p50/p95/p99, холодный старт (spawn процесса → первый валидный ответ), время загрузки весов; RSS sidecar сэмплируется psutil каждые 100 мс в стационарном режиме; конфиг потоков torch зафиксирован.

| Тир | Железо | Статус в PoC |
|---|---|---|
| T1 | Apple M-серии (laya-apple, ANE) | по доступности владельца; иначе экстраполяция от 4.98 мс с пометкой |
| T2 | десктоп с dGPU (CUDA) | по доступности; иначе от 32.8–39.5 мс |
| T3 | современный ноутбук, CPU 8+ ядер | обязателен |
| T4 | старый CPU 4 ядра / контейнер агента | обязателен |

Справочные ориентиры из публикации: GPU 32.8–39.5 мс, CPU 193–464 мс, Apple NEU 4.98 мс — экстраполяции помечаются «не измерено» в отчёте.

### 6.4. Покрытие и таксономия ошибок

Матрица С1–С5 × {осмысленно, формально, нерелевантно} по каждому сценарию; ошибки классифицируются: (а) не та категория; (б) верный шаблон — неверные параметры; (в) golden пропущен (его не было в shortlist — ошибка L0, не Laya); (г) калибровочный провал (высокая уверенность при неверном ответе); (д) языковой сдвиг (ru-контекст → en-ответ хуже). Slice-отчёты по locale и источнику А/Б/В.

## 9. Гейт и ветки решений

Гейт-пороги пререгистрируются в `gate.yaml` до Д6 (стартовые значения — из §14.1 гипотезы; владелец может откалибровать до старта прогона):

| Метрика | Green | Yellow | Red |
|---|---|---|---|
| p@1 vs лексический baseline | ≥ baseline +10 п.п. и ≥ 0.60 | между | ≤ baseline |
| MRR@5 | ≥ 0.75 | 0.55–0.75 | < 0.55 |
| ECE show/don't-show (после t-scaling) | ≤ 0.15 | 0.15–0.25 | > 0.25 |
| p95 инференса на худшем измеренном CPU-тире | ≤ 500 мс | 500–800 мс | > 800 мс |
| RSS sidecar | ≤ 1.5 ГБ | 1.5–2.5 ГБ | > 2.5 ГБ |
| Покрытие С1–С5 | 5/5 осмысленно | 3–4 | ≤ 2 |

- **Green** → фаза 2 (sidecar в продукте, shortlist R2, ИИ-строки FR-021); RAG — «lite» (R1/R3/R8).
- **Yellow** → fine-tune головки на eval-сете (Kaggle, бесплатно) → перегейт; параллельно RAG-lite.
- **Red** → L1-решения закрыты до накопления данных; фаза 0 + палитра v2; полный RAG-движок как единственный путь L1 — на базе построенного сета.

Частные исходы: «качество green, латентность red на T4» → L1 только на T1–T3-железе с гейтом по hardware-детекту; «ru-слайс red, en green» → смена основного чекпойнта на laya-mm + переразметка акцентов.

## 11. Артефакты пилота
