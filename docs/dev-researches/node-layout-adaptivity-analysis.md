## 1. Постановка вопроса

Владелец сообщил: «300 слишком узко и часто зарезает текст». Анализ ниже фиксирует текущее поведение вёрстки нод по ширине и высоте, отделяет **умышленные продуктовые решения** от **багов**, и формулирует правки.

## 2. Текущее поведение

### 2.1 Width — ФИКСИРОВАННАЯ, не растёт под контент

В `crates/canvas-app/src/app.rs:2096` функция `fit_note_size` — единственный авто-ресайз заметки при редактировании:

```rust
fn fit_note_size(&mut self) {
    ...
    let body_width = (node.width - BODY_PADDING * 2.0).max(0.0);
    let body_h = measure_body_height(&live_text, body_width, ...);
    let needed_h = HEADER_HEIGHT + BODY_TOP_GAP + body_h + BODY_PADDING + expr_footer;
    if needed_h > node.height + 0.5 {
        node.height = needed_h;  // растёт только высота
    }
}
```

Дословный комментарий из кода (app.rs:2087):
> «авто-растягивание по самой длинной строке убрано (правило „перенос даже одной строки“)»

То есть **width не подгоняется под контент по умыслу** — это продуктовая политика «wrap even single line». Height — наоборот, растёт всегда, чтобы не обрезать контент по вертикали.

### 2.2 Дефолтные размеры при создании

| Путь | Константа | Значение |
|---|---|---|
| `Node::text` (новая текстовая нода) | `model.rs:280` | width **260** / height 120 |
| `default_template_width(0..3)` (мало-параметрные шаблоны) | `templates.rs:966` | **300** (правка 2 → **400**) |
| `default_template_width(4..7)` (средние) | — | **360** (правка 2 → **460**) |
| `default_template_width(8+)` (тяжёлые) | — | **400** (правка 2 → **500**) |
| `BODY_PADDING` (внутренний отступ) | `tokens.rs:224` | 10 px с каждой стороны |
| `TABLE_DESC_CLAMP_LINES` (кламп описания) | `tokens.rs:294` | 2 строки |

Эффективная ширина тела = `node.width - 2 × BODY_PADDING` = `300 - 20 = 280 px` (правка 2: `400 - 20 = 380 px`, +36%).

### 2.3 Текст описания клампится на 2 строки

В `crates/canvas-render/src/text.rs:1849` функция `clamp_desc_text` использует бинарный поиск, чтобы найти максимальный префикс, помещающийся в `TABLE_DESC_CLAMP_LINES` (2) при переносе `Wrap::WordOrGlyph`. Хвост обрезается и заменяется на «…», с аффордансом «⋯ целиком ▾» для раскрытия.

На узкой ноде (280 px) длинное описание рубится жёстко — это и есть «зарезает текст», о чём говорил владелец. На новой ширине 380 px вмещается примерно на 35% больше символов в строке → меньше усечений.

### 2.4 Перенос текста — WordOrGlyph

Режим переноса `cosmic_text::Wrap::WordOrGlyph` (text.rs:1598, 1857) — приоритет на границе слов, fallback на границе глифов. На узкой ноде длинные слова (URL, идентификаторы, русские составные термины) ломаются посимвольно, что выглядит неопрятно. На 380 px это случается реже, но не исчезает.

### 2.5 Раскладка схем — FR-071

В `scheme_layout.rs` шаг сетки `CELL_W = max_width + LAYER_GAP` — берётся от максимума ширины нод сцены. При поднятии дефолта ширины новых шаблонных нод с 300 до 400 шаг сетки в **новых** схемах вырастет на ~100 px → сцена станет шире по горизонтали, но зазоры сохранятся (не «прилипание»). Существующие `.canvas` не трогаются.

## 3. Что является багом, что — умыслом

| Поведение | Умысел? | Источник |
|---|---|---|
| Width не растёт под контент | **Умысел** | явный комментарий в `app.rs:2087` |
| Height растёт под контент | Умысел | `fit_note_size` — T7 |
| Описание клампится на 2 строки | **Умысел** | `TABLE_DESC_CLAMP_LINES = 2` |
| Раскрытие полного описания по клику | Умысел | `desc_expanded` в `BodyHit::DescExpander` |
| Длинные слова ломаются посимвольно | Побочный эффект WordOrGlyph | нет альтернативы в cosmic-text |
| Дефолт 300 px для малых шаблонов | **Был умыслом, стал проблемой** | правка 2 — поднят до 400 |

**Главный вывод:** «зарезает текст» — это не поломка адаптивности, а **следствие трёх умышленных ограничений**: width-fixed + 2-строковый кламп + узкий дефолт. Из этих трёх:

- Поднимать width-fixed до авто-widening — против продуктовой политики, требует FR;
- Поднимать кламп с 2 строк до 3–4 — дешёвый компромисс, но раздувает ноды по высоте;
- Поднять дефолтную ширину — **минимальное воздействие, максимальный эффект**. Сделано в правке 2 (300 → 400, лестница целиком +100).

## 4. Что сделано в этой правке

`crates/canvas-core/src/templates.rs`:

```rust
pub fn default_template_width(param_rows: usize) -> f32 {
    let t = crate::NODE_BODY_BLOCK_THRESHOLD;  // = 4
    if param_rows >= t + 4 {  500.0  }   // было 400
    else if param_rows >= t { 460.0  }   // было 360
    else {                    400.0 }   // было 300  ← то, что просил владелец
}
```

Обновлены:
- док-комментарий (контекст решения от 27.09.2026);
- тест `default_template_width_ladder` (6 assert'ов);
- тест `instantiate_applies_manifest_defaults` (один assert + комментарий).

`Node::text` дефолт `width: 260` оставлен без изменений — пользователь явно говорил про 300 (шаблонный путь); простой текст-ноды не касается. Если 260 также окажется узким в дальнейшем — отдельный FR.

## 5. Что НЕ сделано — рекомендации

1. **FR на авто-widening по самой длинной строке** — вернуть опционально, с потолком (например, не шире 600) и под фича-флагом. Сейчас это политика «wrap even single line»; если владелец хочет авто-расширение — нужен FR с дизайном поведения на длинных URL/идентификаторах.
2. **Динамический кламп описания** — вместо `TABLE_DESC_CLAMP_LINES = 2` сделать зависимым от `node.height` (на высокой ноде — 4 строки, на низкой — 2).
3. **Альтернатива WordOrGlyph** — `Wrap::Glyph` только ломает везде, `Wrap::Word` не ломает слова и оставляет overflow. Поиск третьего варианта (Word с фолбэк-переносом через дефис) — отдельная задача шейпинга.
4. **Аудит ширины plain-text ноды (260)** — после правки шаблонного дефолта разрыв 260 vs 400 стал заметнее; стоит собрать телеметрию по `suggest_shown` с `body_width` и решить, нужно ли поднять plain-text до 400.
5. **`CELL_W` в `scheme_layout.rs`** — при 400 px дефолта схемы станут шире; проверить, что горизонтальный скролл не становится недружелюбным на узких экранах. Если да — подумать о режиме `compact` раскладки (только для framework-схем).
