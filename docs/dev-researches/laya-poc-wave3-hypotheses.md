### 1.2. Пять структурных наблюдений

1. **Комплементарность подтверждена дважды:** лексика и mm проваливаются на непересекающихся подмножествах (опечатки vs «смысл без ключевых слов»), фьюжн снимает взаимные провалы — но 15 п.п. до оракула остаются в маршрутизации «кому верить в каком контексте».
2. **Языковой сдвиг — крупнейший однофакторный разрыв** (25.5 п.п. внутри одного чекпойнта). ru-контексты CanvasDesk — код-свитчинг: кириллические описания + латинские ID шаблонов/метрик/переменных.
3. **Пределы Laya «по построению»:** honest limits авторов (zero-shot базовых чекпойнтов ≈ 0.362, уровень случайного на их бенче; 0.766 после fine-tune) согласуются с нашим пулом 0.309; предупреждение о температурах mm вне [0.5, 5] материализовалось в 55 конфиденс-провалах и ECE 0.269.
4. **Нулевые и слабые зоны:** C2 «вставка буфера» — 0.00 (5/5, единственный систематический нуль); C5 «что дальше» — n=1; bespoke-домены (ремонт/бюджет/онбординг) не распознаются как «none» (15 ошибок «шаблон вместо none»).
5. **Промпт — исчерпанный рычаг:** few-shot вреден, [nodes]-лист и [stats]-строка не помогают choice, температура инвариантна ранжированию. Оставшиеся рычаги — данные (контекст/обогащение), композиция (fusion/ансамбли), обучение (fine-tune) и модель (своп).

## 2. Логика анализа: почему именно эти гипотезы

### 2.1. Соответствие модам наших ошибок

Таксономия волны 1 (mm, 133 ошибки choice): конфиденс-провалы 55 (калибровка → H5), none-консерватизм 20 (→ H4), «шаблон вместо none» 15 (→ H4), категорийные путаницы соседних метрик 11 (→ H2/H8: имена метрик латиницей в ru-контексте; домен-знание), C2-провал (→ H3), языковой сдвиг §5.2 (→ H2). Плюс зазор fusion→оракул 15 п.п. (→ H7, H9) и недостаток мощности n=47 (→ H1).

### 2.2. Устройство Laya и Jev: что нельзя починить промптом

- **Laya** (Convai Innovations, Apache 2.0, релиз 18.09.2026): энкодеры с decision-head (en 421M ModernBERT-large, mm 322M mmBERT, td 421M typed-decisions), RLCD-обучение. Энкодер не декодер: in-context learning через state невозможен (подтверждено our few-shot). Confidence mm частично некалиброван по построению (авторский warning). `predict_shortlist` (эмбеддинг-префильтр + LRU-кэш) — штатный механизм, аналог нашего L0. Fine-tune ноутбук авторов (Kaggle 2×T4): 0.362 → 0.766 на их домене.
- **Jev** (TypeSafe AI, 15.09.2026, early access): System One Model — типизированные решения, не-авторегрессия, 70–500 мс; сильнее Laya на задачах с >20 опциями (Banking77 0.870 vs 0.425); на 4-workflow бенче TypeSafe 67.8% ≈ GPT-5.6 Terra 67.9%. Наш кейс (20 опций) — на границе раздела сил; платный/ранний доступ делает его кандидатом «на потом» (H10).

### H1. Перегейт гибрида на расширенном сете — «решающий эксперимент»

**Обоснование.** Fusion 0.468 с p=0.083 при n=47 — на границе значимости: для продуктового решения о фазе 2 мощности не хватает (CI разности с lex −12.9..+25.6 п.п. в волне 1; ширина CI ∝ 1/√n — удвоение n примерно вдвое сужает). Источники расширения: (а) ручная разметка синтетики владельцем (план волны 2 данных —Golden-подтверждение B-фикстур); (б) карвинг 3 новых framework-схем (AJTBD/CJM/Service blueprint уже в репо, коммит `f305ec7`) — примерно +40–50 choice-фикстур; (в) добор C2/C5-кейсов при генерации. Пререгистрированные пороги уже существуют (gate.yaml) — перегейт честен по построению.

**Дизайн.** Заморозить конфиг: mm, шортлист top20 (top10 — вторая точка), score-fusion с α, подобранным на dev (не на test), текст noul-вопроса v0.2. Полный повторный прогон на расширенном сете, отчёт по гейт-порогам §8 с разбивкой по слайсам.

**Критерий успеха.** p@1 ≥ 0.55 и CI разности с lex не содержит нуля → green-ветка (встраивание гибрида в фазу 2 по архитектуре §12 отчёта). p@1 0.47–0.55 → yellow (решение по латыни). Ниже — закрытие Laya-ветки до накопления продуктовых событий.

**Стоимость/зависимости.** Восстановление harness (§6) + разметка владельца 2–3 ч + один полный прогон. Блокер для интерпретации всех остальных гипотез.

### H2. Двуязычное обогащение контекста — лечение код-свитчинга

**Обоснование.** Языковой сдвиг mm (en 0.524 / ru 0.269) — крупнейший однофакторный разрыв. ru-контексты — смешение кириллицы и латинских ID; литература по CLIR/код-свитчингу показывает, что мультling-энкодеры теряют точность при отсутствии lexical overlap, а обогащение смешанным кодом — воспроизводимое лечение (Litschko 2022/2023; CSR-L 2026). Query/document expansion — стандартный прирост recall 5–6% (FlashRank 2025). Каталог CanvasDesk двуязычен по построению (ru/content, en/content_en) — словарь канонических имён бесплатен.

**Дизайн.** Сериализатор v0.4: к ru-тексту добавлять канонические латинские сущности из каталога — `title="Маркетинг" (marketing, mkt_spend)`, имена метрик латиницей в критериях уже есть; единый формат для критериев (ru-описание + en-имя). Настройка на dev-ru, оценка на test-ru; контроль невреждения en-слайса. Полного перевода контекста избегаем (дорого, вне контейнера).

**Критерий успеха.** ru-слайс p@1 0.269 → ≥ 0.40 без регрессии en (> 0.50); fusion на ru ≥ 0.45.

**Стоимость.** Низкая: правка сериализатора + повторный прогон ru-подмножества (dev-ru 74 + test-ru 26 фикстур) на mm.

### H9. lex v2: fuzzy-матч и синонимы v2 — прокачка гибрида изнутри

**Обоснование.** α=0.85: гибрид на 85% состоит из лексики — каждый пункт lex-качества почти напрямую конвертируется в гибрид. Слабости lex по данным волн: опечаточные вариации вне текущего char3-покрытия, словарь синонимов неполон (категорийные путаницы «срок жизни→LTV» — семантическая близость без лексического моста). Публичный паттерн 2025–2026: «лексика+BM25 первична, fuzzy — boost/fallback для коротких строк». Чистый Python, ноль новых зависимостей, согласуется с принципом «эмбеддер не оправдан» (§10 отчёта).

**Дизайн.** (а) SymSpell-подобный fuzzy по лексемам (расстояние ≤2) поверх текущих скорингов с малым весом; (б) расширение словаря синонимов из ru/en описаний всех 62 шаблонов + ручной список доменных пар (lifetime/срок жизни; churn/отток; …); (в) перебалансировка BM25/char3 на dev. Затем ре-фьюжн с mm-пробами (после восстановления инференса).

**Критерий успеха.** lex пул p@1 ≥ 0.42 (сейчас 0.381); fusion test ≥ 0.50.

**Стоимость.** Низкая; не требует sidecar на первом шаге (только eval-сет).

### H3. C2 «вставка буфера»: типизированный дескриптор вставки

**Обоснование.** C2 = 0.00 (5/5) — единственный систематический нуль волны 1: вставленный CSV/таблица попадает в state как сырой текст, а связка «форма данных → параметры шаблона» требует структурных признаков (колонки, типы, единицы). Продуктово это дорогой сценарий (вставка из Excel — типовой путь аналитика).

**Дизайн.** Препроцессор вставки: парсинг первых строк blob → компактная секция `[paste cols: spend RUB, clients int, date; rows 12; header yes]` ≤ 40 токенов + вопрос choose_template v0.2. Перегенерация C2-фикстур (те же сценарии, новый сериализатор), прогон mm, метрики C2-слайса; затем включение C2 в основную метрику перегейта (H1).

**Критерий успеха.** C2 p@1 ≥ 0.40 (n=5–14 после добора — направленная оценка; порог жёсткой значимости не ставим из-за n).

**Стоимость.** Низкая: препроцессор + перегенерация одного среза.

### H4. Материализация none и негативный словарь bespoke-доменов

**Обоснование.** 15 ошибок «выбрал шаблон, когда golden=none» — mm не распознаёт bespoke-домены (ремонт/бюджет/онбординг) как «вне каталога»; протокол допускает none-ответ, но none-опция в criteria — «неосязаема» (нет описания, когда её выбирать). Практика классификации с reject-option: явный абстейн-класс с внятными критериями повышает precision без потери recall. Симметричная проблема — 20 ошибок «сказал none, golden есть» (none-консерватизм) — лечится тем же описанием.

**Дизайн.** (а) none-критерий с описанием: «выбирай none, если домен вне перечисленных категорий (bespoke-тексты, свободные заметки, нереализованные идеи)»; (б) опционально — виртуальный кандидат `custom-note` как «мягкий none»; (в) оценка: none-precision/recall, p@1 основного выбора (без регрессии), итоговая точность «показал-правильное-или-промолчал».

**Критерий успеха.** False-template-when-none 15 → ≤ 6; «сказал none, golden есть» 20 → ≤ 12; p@1 не падает (> 0.37).

**Стоимость.** Низкая: правка критериев + повторный прогон.

### H5. Калибровка mm: Platt, изотоническая регрессия, margin-гейт

**Обоснование.** t-scaling упёрся в край грида (T=4, ECE 0.269) — одной температуре не хватает выразимости (асимметрия распределения скоров). Публичная лестница: temperature → Platt (сигмоида, 2 параметра) → isotonic (монотонная регрессия); для гейтинга показа робастен margin top1−top2 (не зависит от абсолютной шкалы). Требование продукта: precision гейта ≥ 0.9 — «не показывай, если не уверен».

**Дизайн.** По восстановленным probs mm на dev: fit Platt и isotonic (1D-регрессии), сравнение ECE/reliability-кривых на test; гейт: перебор порога по (confidence | margin) с фиксацией precision ≥ 0.9, отчёт покрытия; сравнение с lex-эвристикой волны 2 (0.95 acc) и гибридом «правило + confidence».

**Критерий успеха.** ECE ≤ 0.15 на test; гейт precision ≥ 0.9 при покрытии ≥ 0.5. Иначе — гейт остаётся детерминированным правилом (что уже продукт-приемлемо: 0.95).

**Стоимость.** Низкая (офлайн-анализ), но требует повторного инференса mm (пробы утеряны с контейнером) — синергия с H1/H2-прогонами.

### H6. Сериализация v0.3: эго-граф с расстоянием до редактируемой ноды

**Обоснование.** v0 [up]/[down] выбирает ≤4+4 соседей «по связности» без учёта расстояния/направления потока; v0.2 [nodes]-лист выбору не помог (§15.2), но и не ухудшил show; позиционные эффекты у энкодеров известны (порядок и близость к целевой ноде — сигнал). Гипотеза: ранжирование соседей по (hop-расстояние, тип ребра, вес) и 2-hop для пустых окружений даст релевантнее контекст при том же бюджете ≤400 токенов.

**Дизайн.** v0.3-сериализатор: соседи сортируются по расстоянию до [node], топ-3 вверх/вниз по потоку + секция [scheme] с представленными категориями; длина контролируется. Прогон mm dev (выбор варианта) → test.

**Критерий успеха.** p@1 carved-слайса + ≥ 5 п.п. без регрессии synth; в пуле — не хуже базового.

**Стоимость.** Средняя: новый сериализатор + полный прогон; риск низкого эффекта (v0.2-опыт) — поэтому приоритет ниже H2/H9.

### H7. Ансамбль чекпойнтов: весовое слияние mm + td (+en)

**Обоснование.** Оракул best-of-two 0.617 при fusion 0.468 — зазор 15 п.п.; td ошибается «иначе» (0 конфиденс-провалов, 0 none-ответов — другая мода ошибок §9), т.е. разнообразие для ансамбля есть. RRF уже поднимал en/td (0.340/0.426). Литература: ансамбли нейро-реранкеров дают стабильный прирост при разнородных ошибках.

**Дизайн.** Офлайн по пробам трёх чекпойнтов: score-fusion (веса на dev), Borda, RRF; сравнение с fusion(lex, mm). Если выигрыш > 3 п.п. — оценка латентности: последовательный инференс ×2 (top20: ~2.4 с p95 на T4) или два sidecar (RAM-лимит 3.9 ГБ — только mm 1.81 + td 2.08 впритык; на T3 владельца 32 ГБ — свободно).

**Критерий успеха.** p@1 > 0.50 при p95 ≤ 2.5 с (T4) — тогда ансамбль в кандидатурный конфиг; иначе зафиксировать как «не окупается латентностью».

**Стоимость.** Средняя: 2 дополнительных полных прогона (td, en) после восстановления + офлайн-анализ.

### H8. Fine-tune mm на eval-сете — «жёлтая ветка» с наибольшим эффектом

**Обоснование.** Honest limits авторов: zero-shot 0.362 → 0.766 после fine-tune (их домен, Kaggle 2×T4, ноутбук публичный); наш пул 0.309 — та же зона; few-shot провален → обучение — единственный путь «научить» домену (уже доказано отрицательным результатом). Индустрия: домен-адаптация реранкеров даёт +10–20%; hard negatives (лексически ближайшие кандидаты — наш shortlist уже их поставляет) критичны.

**Дизайн.** Экспорт train/dev из harness (только A-источник + размеченная синтетика; test — заморожен и не треникуется), hard negatives = top-lex-дистракторы; запуск ноутбука авторов на Kaggle 2×T4; возврат весов в sidecar (sha256 в манифест), перегейт по H1-протоколу.

**Критерий успеха.** p@1 ≥ 0.60 (green-зона) → пересмотр вердикта «не встраивать»; 0.50–0.60 → гибрид fine-tuned-mm + lex как основной кандидат фазы 2.

**Стоимость.** Высокая: подготовка данных (агент, ~полдня) + GPU-запуск (владелец/Kaggle, 4–8 ч) + перегейт. Решение о запуске — после H1 (нет смысла fine-tune'ить до подтверждения, что гибрид вообще проходит порог).

### H10. Модельный своп: jina-reranker-v3.5 / Qwen3-Reranker на нашем сете

**Обоснование.** Пин 0.3.20 стареет (экосистема Laya: 26k звёзд за 9 дней, релизы частые); публичный ландшафт ушёл: Jina v3.5 — 61.94 nDCG@10 BEIR (лучший среди оценённых реранкеров, +4.88% к v2), Qwen3-Reranker — вершина опен-весов (~77%); оба мультиязычны — могут снять ru-проблему (H2) самим фактом другой модели. Наш замороженный eval-сет — дешёвый стандартизированный бенчмарк для свопа. Jev: сильнее на >20 опциях (Banking77 0.870 vs 0.425) и калиброван (ECE 0.246 у Jev против... — по публикациям Laya калиброван лучше на их бенче: 0.081 vs 0.246), но early access + платно — кандидат «на потом».

**Дизайн.** Тот же протокол (state-текст + criteria), адаптер к /rerank API Jina (локально или hosted) и Qwen3-Reranker-0.6B (CPU, бюджет сопоставим с mm); метрики идентичны; сравнение zero-shot с mm (0.383) и fusion (0.468). Требует согласия на новые зависимости — держим вне репо (как harness-эксперимент).

**Критерий успеха.** Любой кандидат p@1 > 0.383 zero-shot и/или ru-слайс > 0.40 → включается в гибридные конфигурации перегейта.

**Стоимость.** Средняя: адаптер + прогоны; риск — лицензии/веса/формат (не systemone-протокол, нужен перевод задач в query-doc).

## 4. Порядок исполнения и зависимости

```
Восстановление harness (§6) ──┬─→ H9 (lex v2, без sidecar) ─┐
                              ├─→ H2 (ru-обогащение) ────────┤
                              ├─→ H3 (C2) ───────────────────┼─→ H1 (перегейт расширенного сета) → решение о фазе 2
                              ├─→ H4 (none) ─────────────────┤        │
                              ├─→ H5 (калибровка, офлайн) ────┤        └─→ если yellow/green → H8 (fine-tune, Kaggle) → повторный H1
                              ├─→ H6 (v0.3 сериализация) ─────┤
                              └─→ H7 (ансамбль: прогоны td/en)─┘
Разметка синтетики владельцем ──→ расширение сета для H1 (параллельно всему)
T3 one-shot (ноутбук) ──→ обновление латентных строк гейта (независимо)
H10 (своп моделей) ──→ по желанию владельца, параллельно, вне критического пути
```

Логика порядка: сначала дешёвые рычаги данных/композиции (H9, H2, H3, H4 — дни на CPU), затем решающий перегейт (H1), и только при положительном исходе — дорогой H8. H5-H7 — по остаточному принципу между прогонами (используют те же инфраструктурные прогоны). Рекомендуемый минимальный состав волны 3: **H9 + H2 + H3 + H4 → H1** (все четыре первых — правки сериализатора/словарей/критериев, один общий цикл прогонов).
