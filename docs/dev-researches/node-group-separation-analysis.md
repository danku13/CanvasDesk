# CanvasDesk — нода и группа: разделять ли объекты (deep dive)

**Дата:** 2026-09-27
**Тип:** анализ (alternatives-обзор, без обязательства реализовать)
**Заказчик:** владелец продукта
**Автор:** агент-сессия (Super Z)
**База:** commit `25fe9e9` (FR-012 v4)
**Источники:** аудит `canvas-core` / `canvas-app` / `canvas-render` / `canvas-scene` / `canvas-web`, история дефектов FR-012 v1→v4, `docs/adr/`, SPEC §5.1

## 0. Постановка

Исходный тезис владельца: «группы — это условно те же самые ноды, возможно, стоит сделать для групп другие объекты, чтобы их поведение минимально пересекалось». Тезис подтверждён серией дефектов одного узла за четыре итерации FR-012:

| v | Дефект | Где «группа = нода» сломалась |
|---|---|---|
| v1 | Плоский z-order: внешняя группа перехватывала клик у вложенной; рамка потомка уходила под заливку предка | Порядок снапшота `nodes` трактовался как z для контейнера |
| v2 | Разрыв вложенных групп при drag: `translate_group` двигал прямых детей, но не поддерево; двойное членство | Membership вычислялся геометрией, иерархия была неявной |
| v3 | Collision-avoidance считал рамку группы стеной: нода не «впрыгивала» в группу, release-snap выдёргивал её обратно | Snap-движок взял bbox группы как препятствие — «обычная нода» |
| v4 | Предки не расширялись при вставке во вложенную группу; Ctrl+G внутри группы давал двойное членство и не строил явную вложенность | Авторасширение и создание группы работали только с «одной нодой», не с иерархией |

Вопрос этого документа: **что должно измениться в модели, чтобы такие дефекты стали невозможными по построению, а не ловились точечными фиксами.** Разработки нет; документ — основа для решения владельца.

## 1. Текущее состояние (факты из кода)

### 1.1. Модель

```
Canvas { nodes: Vec<Node>, edges: Vec<Edge>, ... }
Node   { id, node_type: String, x, y, width, height, ...,
         children: Option<Vec<String>> }   // расширение .canvas, SPEC §5.1
kind() = match node_type.as_str() { ..., "group" => Group, ... }
```

- Группа — это `Node` с `node_type == "group"`; отдельного типа нет. `children` — расширение формата JSON Canvas (у сторонних редакторов это неизвестное поле, round-trip сохраняется).
- Членство **двулико**: явный список `children: Some([...])` (нативный формат FR-012) или **геометрический фолбэк** для легаси-групп (`children: None` — «центр ноды внутри rect»). Легаси-ветка — постоянный источник ветвлений и недетерминизма (`group_depths` сознательно отказался строить иерархию по геометрии — циклы).
- Иерархия **неявная**: родителя нет ссылкой; он вычисляется сканом (`enclosing_group_indices` — O(N·G) с транзитивным обходом, `group_depths` — явные списки + мемоизация + visited-защита).

### 1.2. Масштаб пересечения (метрики по кодовой базе)

- **62 ветвления** `NodeKind::Group` в 12+ файлах шести крейтов (core/app/render/scene/web/tests).
- **92 касания** поля `.children` (model 32, lineage 12, app/lib 8, explain_ui 8, zorder 4, scheme_apply 4, ...).

Где именно группа ведёт себя «не как нода»:

| Подсистема | Специальная обработка групп |
|---|---|
| Модель/IO | `children` + materialize + инварант одного членства (`group_add_children`); сериализация 1:1 с JSON Canvas |
| Spatial index | пометка `group: bool` в записях (`spatial.rs:66,79`) + отдельный запрос `query_rect_groups` для drop-target |
| Hit-test/выделение | `select_node_hit`: сначала не-группы (меньшая площадь), затем самая внутренняя группа по глубине |
| Drag | `drag_origins`/`translate_group` двигают всё поддерево; `group_drag_out_released` — вынос из явной группы |
| Snap/collision | v3: группы — кандидаты направляющих, но НЕ препятствия collision (`collision_obstacles`) |
| Z-order | `zorder::groups_first` — depth-aware: предки раньше потомков |
| Рендер | группы рисуются рамкой, без портов (`cards.rs:223,330,1426`); сегменты z-плана |
| Minimap | отдельный `MinimapNodeKind::Group` |
| Routing | `enclosing_group_indices` — исключение границ групп из препятствий для связей детей |
| drag_push (FR-073) | группы не участвуют в пружинах (`drag_push.rs:252,373`) |
| Insert/expand | авто-расширение rect по содержимому (v2/v4), settle-анимация, push-out чужих |
| Создание | `plan_group_around/at` (палитра, меню, Ctrl+G) + v4 `group_adopt_into_hierarchy` |

### 1.3. Корень пересечения — четыре структурных причины

1. **Нет типа — нет защиты компилятора.** Любой новый цикл по `canvas.nodes` может просто забыть проверить `kind() == Group`. Все 62 ветвления существуют потому, что язык не заставляет их писать. Каждый новый жест (snap, drag-push, scheme-раскладки) — новый шанс пропустить ветку; дефекты v3/v4 ровно об этом.
2. **Членство двулико.** Инвариант «у ноды один родитель» нельзя выразить типом, пока `children: None` легитимен и означает «смотри по геометрии». Инвариант приходится поддерживать процедурно (v2: `group_add_children`; v4: `group_adopt_into_hierarchy` + материализация до вычёркивания — порядок операций уже дважды был источником бага в тестах).
3. **Иерархия неявная.** Родительство вычисляется запросами вместо хранения ссылки. Следствия: O(N·G) сканы в горячих местах (drop-target каждый кадр драга), visited-защиты от циклов в трёх функциях, контракт «корни не входят в карту глубин».
4. **Rect группы — два источника истины.** Это одновременно геометрия объекта (его двигают, ресайзят вручную, клампят в viewport) и *функция содержимого* (авторасширение v2/v4). Конфликт разрешается каждый раз заново: expand перезаписывает rect целиком (группа «прыгает» к содержимому), ручной ресайз может увести рамку от детей.

## 2. Варианты решения

### Вариант A. Status quo + точечные фиксы

Продолжать латать v5, v6... Цена каждого инцидента уже видна: диагностика по 6 крейтам + регресс-тесты. Дефекты всплывают на каждом новом жесте, связанном с группами (коллапс групп, кросс-групповые связи, мульти-драг между группами).

### Вариант B. Радикальный enum: `CanvasObject { Node(..), Group(..) }`

Разорвать `Vec<Node>` на объект-сумму. Максимальная типовая защита (match обязан рассмотреть группу везде).

- **Против:** рвёт JSON Canvas IO (маппинг 1:1 теряется — придётся писать слой конвертации в обе стороны), MCP-инструменты, scheme-шаблоны, undo-снапшоты (`Vec<Node>` копируется целиком), все 60+ точек матчинга. Оценка: 25–35 файлов, недели работы, высокий риск регрессий в рендере/вводе. Выгода по сравнению с C/D — незначительная (те же match-и, просто обязательные).

### Вариант C. Разделение хранилища: `nodes: Vec<Node>` + `groups: Vec<Group>`

```rust
struct Node  { id, kind, x, y, w, h, ... }            // без children
struct Group { node: Node, children: Vec<ObjectId>, parent: Option<ObjectId> }
enum ObjectId { Node(usize), Group(usize) }
```

- **За:** инварианты в типах (Group без `children: None`; parent — ссылка → иерархия явная, O(1)); z-order = префиксный обход дерева; hit-test = спуск по дереву; 5 уровней вложенности — обычный обход, а не частные случаи; rect группы можно сделать вычисляемым из содержимого (закрывает причину 4).
- **Против:** все индексы `usize` по `nodes` меняются на `ObjectId` — касание практически всего app/render/scene; undo-снапшоты — новая структура; миграция сопоставима с B по ширине, но с сохранением IO-маппинга (сериализатор просто пишет group как node с `type:"group"`).

### Вариант D (рекомендуемый сейчас). Типовые фасады поверх текущего хранилища + деградация легаси

Хранилище не меняется (`Vec<Node>`, формат файла тот же), но:

1. **Фасады-вью** в canvas-core: `GroupRef<'a>` / `CanvasNodeRef<'a>` — единственная точка членства/иерархии/расширения (`children()`, `parent()`, `descendants()`, `expand_to_children()`, `adopt()`), с внутренними assert-инвариантами. Прикладной код постепенно переводится с сырых `.children`/сканов на фасады — причина 1 (забытая проверка) исчезает в переведённом коде, причина 3 — централизуется.
2. **Легаси-членство объявить устаревшим:** материализовать `children` при загрузке файла (`group_materialize_children` уже есть) и при создании группы. Через релиз-цикл геометрический фолбэк в `group_children` удалить → причина 2 закрыта, `children: Option` можно ужесточить до инварианта «всегда Some для group».
3. **Parent-карта с кэшем** (инвалидация по revision сцены) для горячих запросов drop-target/hover — снимает O(N·G) без смены хранилища.
4. **Разделить источники истины rect:** ввести явный флаг «auto-size» у группы (rect = f(содержимое)) против «ручного» (rect принадлежит пользователю; авторасширение не перезаписывает, а только клампит внутрь). Закрывает причину 4 — и попутно вопрос владельца «родитель должен вместить» становится инвариантом одного места, а не размазанной конвенцией.

- **За:** цена 1–2 дня, не ломает IO/MCP/undo, устраняет класс дефектов v2–v4 системно, готовит почву для C.
- **Против:** типовая защита неполная (фасады — конвенция, компилятор не заставит); остаются два Vec-поля в одной структуре.

### Сравнение

| Критерий | A (статус-кво) | B (enum) | C (два хранилища) | D (фасады) |
|---|---|---|---|---|
| Цена | 0 | недели, 25–35 файлов | недели | 1–2 дня |
| Риск регрессий | растёт с каждым жестом | высокий | высокий | низкий |
| Закрывает причины 1–2 | нет | да | да | 1 — частично, 2 — да |
| Закрывает причины 3–4 | нет | да | да | да |
| IO/MCP/undo | без изменений | переделка | переделка undo | без изменений |
| Когда | — | нет | при крупном рефакторинге модели/рендера | сейчас |

## 3. Связь с исходным запросом (z-index и вложенность)

Глубокая вложенность (5 уровней) в текущей модели обрабатывается «сканирующими» алгоритмами с защитами от повреждённых данных. При явной иерархии (C полностью, D через parent-карту):

- z-order строится префиксным обходом дерева — «предок раньше потомка» гарантирован построением, а не сортировкой с композитным ключом;
- hit-test — спуск от корня к самому глубокому контейнеру, содержащему точку;
- drag/translate — обход поддерева без visited-защит (циклы невозможны, если adopt не создаёт их, а он проверяет);
- авторасширение v4 — это прямой обход вверх по parent-ссылкам.

То есть именно те места, где происходили v1–v4, превращаются из «сканов с оговорками» в обычный обход структуры.

## 4. Рекомендация

1. **Сейчас: вариант D.** Фасады GroupRef/NodeRef + материализация легаси при загрузке + кэш parent-карты + флаг auto-size группы. Это закрывает фактический источник дефектов v2–v4 (двуликое членство, неявная иерархия, двойной rect) ценой 1–2 дней и без риска для IO/MCP/undo.
2. **Целевая архитектура — вариант C**, к которому имеет смысл прийти в рамках планового крупного рефакторинга модели (например, вместе с коллапсом групп или слоёв), а не отдельным аварийным миграционным PR.
3. **Вариант B не делать**: его выгода совпадает с C при большей цене миграции.
4. Отдельно зафиксировать поведение, выбранное в v4, как спецификацию: «rect группы с auto-size — функция содержимого; ручной ресайз переключает группу в ручной режим; предки расширяются вверх по цепочке при любом изменении содержимого» — сегодня это живёт в доккомментариях, а не в SPEC.

## 5. Открытые вопросы к владельцу

- Считать ли легаси-группы (`.canvas` без `children`) поддерживаемым форматом входа навсегда (тогда материализация — обязательный шаг D) или допустима разовая миграция файлов?
- Нужен ли ручной ресайз группы вообще (если rect — функция содержимого, ресайз конфликтует с auto-size)? Вариант: ресайз меняет padding, а не рамку.
- Приоритет: включать ли D в ближайший релиз-цикл отдельно от фичевого потока (рекомендую да — до коллапса групп, который добавит ещё одну подсистему поверх иерархии).
