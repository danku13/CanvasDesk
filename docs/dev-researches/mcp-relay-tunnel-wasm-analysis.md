## 1. Контекст (для читателя без истории чата)

### 1.1 Задача

CanvasDesk существует в двух исполнениях: нативное (Windows, GPU-рендер) и браузерное wasm (canvas-web, деплой на GitHub Pages). MCP-контур уже работает в двух конфигурациях: `canvas-mcp` (stdio-транспорт, натив, FR-008/034/035) и `canvas-mcp-headless` (in-process `HeadlessSession` над `canvas-scene`, wasm32-wasip1 под wasmtime — FR-037/ADR-0012, гейты `scripts/mcp_wasm_gate.sh` + `mcp_wasm_e2e.py`). Но **браузерная вкладка canvas-web сегодня MCP наружу не открывает**: транспорт в web нет (`app_spawn.rs`: «MCP-pipe — натив-Windows обвязка, не для web»), при этом canvas-web уже зависит от canvas-scene и в ней есть живой `mcp_dispatch` (~39 инструментов).

Цель — дать внешним агентам (Claude Desktop, hermes, удалённые агенты) доступ к **живому состоянию канвы пользователя в браузере**, включая undo/перерисовку, а не только к headless-снимку.

### 1.2 Принятый каркас — гибрид А+В (вывод предыдущих анализов)

Браузер не может «слушать порты», поэтому за образец взят паттерн Penpot (`docs/penpot-mcp.md`): клиент живёт в открытой вкладке браузера и подключается **наружу**, а стабильное MCP-лицо держит отдельная точка встречи — релей. Рекомендованная архитектура:

```
агент (любой MCP-клиент) ──Streamable HTTP──► РЕЛЕЙ ◄──WebSocket (исходящее из вкладки)── canvas-web
                                              │
                                              └── бэкенд: canvas-mcp-headless (в-process HeadlessSession)
                                                  или форвард в живой инстанс canvas-web
```

- **Релей** держит MCP-лицо (Streamable HTTP, URL-config — совместимо с любыми MCP-хостами, включая Penpot) и WS-сервер для исходящих подключений вкладки.
- **canvas-web** остаётся чистым WS-*клиентом* (web-sys) — это снимает все браузерные ограничения: вкладке не нужно ничего слушать.
- Инструменты: `tools/list` с capability-фильтром браузерного подмножества из ~39; форвард в живой `mcp_dispatch` — главный риск (связка с живым undo/перерисовкой), решается в волне по образцу MW2.
- Транспортная база уже готова частично: `AppTransport`/`handle_input`/`run_stdio_with_transport` публичны (canvas-mcp), протоколы 2025-06-18/2025-03-26/2024-11-05, batch (ADR-0009). ADR-0009 когда-то отложил сетевой транспорт — браузерный кейс триггер для нового ADR.

### 1.3 Где исполняется релей (вывод предыдущего шага)

GitHub Pages для релея **нельзя** (статический хостинг: нет процессов, нет WS-сервера, нет состояния — а релей по определению точка встречи двух сторон). Реальные уровни:

1. **localhost-процесс** — MVP, ноль инфраструктуры, агенты только на машине владельца;
2. **localhost + туннель** (ngrok / cloudflared / Tailscale Funnel) — публичный WSS/HTTPS-URL без VPS, подключение удалённых агентов;
3. **serverless free-tier** (Cloudflare Workers + Durable Objects / Supabase Realtime / Upstash) — логика релея в edge-функции; дороже по учёту (аккаунты, лимиты, холодные старты).

Экзотика без сервера вовсе — relay-over-GitHub (Gist/Issues как шина через REST, обе стороны опрашивают) — работает, но латентность секунды и рейт-лимиты; только last-resort.

Настоящий документ разбирает **уровень 2**: кто и где исполняет бинарники релея и туннеля, что должен ставить пользователь, и можно ли всё это закрыть «загрузкой wasm».

## 3. Топология: что где живёт

Оба процесса — релей и туннель — **нативные процессы на машине пользователя**. Никакой из них не «живёт в облаке» и не «живёт в браузере».

```
удалённый агент ──HTTPS/WSS──► edge Cloudflare ◄──исходящий туннель── cloudflared.exe
локальный агент ──HTTP──► ┌──────────────────────────────┐
                          │ canvasdesk-relay.exe (наш)   │  localhost:PORT
вкладка canvas-web ──WS──►│  • MCP Streamable HTTP-лицо  │
(GitHub Pages)            │  • WS-сервер для вкладки     │
                          └──────────────────────────────┘
```

### 3.1 Релей — наш бинарник

Релей — это *наш* Rust-код (будущий крейт вида `canvasdesk-mcp-relay`), собирается в один exe и распространяется нами. Два лица на одном процессе:

- **WS-сервер** на `localhost:PORT` — единственная точка, куда подключается вкладка canvas-web;
- **MCP Streamable HTTP** — лицо для агентов (тот же или соседний порт).

Распространение: в составе установщика десктопа, отдельным exe или `cargo install` из репо. Управление жизненным циклом — трей-тоггл «Agent bridge» / автостарт с приложением. Поскольку релей — нативный процесс, троттлинг вкладки ему не страшен: вкладка переподключается (семантика reconnect уже заложена в гибридном плане; ошибки «инстанс не подключён» возвращаются агенту честно).

### 3.2 Туннель — чужой бинарник, только для удалённых агентов

Туннель нужен **исключительно** для экспозиции MCP-лица наружу (удалённые агенты). Ключевые свойства:

- Это сторонний нативный бинарник (cloudflared / tailscale / ngrok), а не наш код.
- Он **не открывает публичных портов** на машине пользователя: процесс сам устанавливает *исходящее* соединение к edge провайдера, TLS терминируется на edge, релей продолжает держать plain HTTP на localhost.
- Встраить туннель *внутрь* процесса релея нереалистично: протокол cloudflared не публичный и не стабильный, а tsnet (embed Tailscale в свой процесс) — Go-only библиотека, у нас Rust. Практичный способ — отдельный процесс, супервайзимый релеем (§4).

### 3.3 Ключевой факт: браузерная сторона туннель не использует вообще

Вкладка canvas-web подключается к `ws://localhost:PORT` **из HTTPS-страницы GitHub Pages** — это разрешено: loopback считается «potentially trustworthy origin», mixed-content carve-out для localhost поддерживается Chrome/Firefox/Safari. То есть туннель не участвует в самом частом сценарии (вкладка ↔ релей ↔ локальный агент) — он чистая опция для удалённого доступа.

Нюанс на будущее: Chrome последовательно ужесточает доступ публичных страниц к локальной сети (Private Network Access → Local Network Access, permission-prompt, WebSockets тоже попадают под политику). Сегодня `ws://localhost` с Pages работает, но поведение может измениться. **Запасной вариант, снимающий вопрос целиком:** релей сам раздаёт тот же статический бандл canvas-web на `http://localhost:PORT` — тогда вкладка и релей в одном origin, ни mixed-content, ни PNA-вопросов нет (бандл уже статика, отдача файлов — тривиальная надстройка над релеем).

## 4. Бремя установки: что ставит пользователь

### 4.1 Релей — ничего

Это наш артефакт: ставится вместе с приложением (или отдельным exe). Ручной сетап нулевой — включил тоггл, процесс поднялся.

### 4.2 Туннель — варианты по возрастанию усилий

| Вариант | Что делает пользователь | Плюсы | Минусы |
|---|---|---|---|
| **(a) MVP без туннеля** | ничего | ноль установок и аккаунтов; локальные агенты и вкладка работают | удалённые агенты недоступны |
| **(b) quick tunnel, ручная установка** | разово `winget install cloudflared`, затем `cloudflared tunnel --url http://localhost:PORT` | без аккаунта; публичный URL сразу; cloudflared Apache-2.0 | URL случайный `*.trycloudflare.com` на каждую сессию; нужно помнить команду |
| **(c) обёртка с автоскачиванием (рекомендация для инкремента)** | один тоггл «удалённые агенты» в настройках | релей сам скачивает cloudflared (Apache-2.0, проверка checksum) в `%LOCALAPPDATA%`, супервайзит как дочерний процесс, парсит URL из stdout и показывает пользователю | авто-загрузка бинарника извне — нужен checksum/версионирование; URL всё ещё временный |
| **(d) Tailscale Serve/Funnel** | если tailnet уже есть — почти ничего | serve = только машины своей tailnet (ещё безопаснее публичного URL), стабильный hostname; funnel — публичный при необходимости | требует установки tailscale и аккаунта; для пользователей без tailnet — лишний барьер |
| ~~ngrok~~ | — | — | **отклонено:** проприетарный, обязательны аккаунт + authtoken, лицензия не позволяет тихое встраивание |

Стабильный публичный адрес при желании — named tunnel (облачный токен туннеля в настройках, Cloudflare может закрывать hostname за Access-политикой). Для ad-hoc сессий с агентами quick tunnel с временным URL достаточен: агенту URL передаётся на сессию.

### 4.3 Итог по бремени

Пользователь **не ставит ничего руками** ни в одном из рекомендуемых путей: релей — наш exe, туннель — либо не нужен (MVP), либо авто-скачивается обёрткой. Верхняя планка «ручной работы» — одна команда winget в варианте (b), и то она нужна только тем, кому нужны удалённые агенты *здесь и сейчас*.

## 5. Пределы wasm: почему «загрузкой wasm» это не решается

### 5.1 Браузерный wasm не может быть ни релеем, ни туннелем

- **Нет `listen`/`accept`.** В песочнице браузера wasm-код не имеет доступа к raw TCP: нет ни входящих соединений, ни произвольных исходящих сокетов. WebSocket доступен только как клиент и только через JS-glue.
- **Жизненный цикл вкладки несовместим с ролью сервера.** Троттлинг фоновых вкладок, закрытие таба, перезагрузка — любой «сервер в вкладке» умирает вместе с ней. Релей обязан переживать вкладку, а не наоборот.
- Именно поэтому в принятом каркасе wasm-часть (canvas-web) сознательно оставлена **чистым WS-клиентом**: вкладкаdial-out к релею — и это единственная роль, которую браузер исполняет корректно.

### 5.2 «Загрузка wasm в рантайме» не меняет сути

Сама по себе загрузка модуля ничего не решает: скачанный `.wasm` кто-то должен **исполнить**, а вариантов исполнителя два:

1. **Браузер** — песочница без сокетов (§5.1), максимум полезной нагрузки — тот же WS-клиент, который и так есть;
2. **Нативный WASI-рантайм** (wasmtime и т.п.) — но его установка на машину пользователя и есть установка программы; мы просто сменили формат артефакта с `.exe` на `.wasm`+рантайм, а требование установки не убрали.

### 5.3 WASI-релей возможен, но не даёт UX-выигрыша

Технически релей *можно* собрать под WASI: в preview2 есть `wasi:sockets` (TCP listen/accept), и прецедент WASI-рантайма в репо уже есть — `canvas-mcp-headless` целится в wasm32-wasip1 и исполняется под wasmtime в гейтах FR-037. Это дало бы один кроссплатформенный артефакт вместо exe под три ОС. Но:

- wasmtime (или другой рантайм) всё равно надо доставить пользователю — требование установки остаётся;
- сторонний туннель в wasm не положить в принципе (cloudflared — нативный Go-бинарник, Tailscale — то же);
- выигрыш «один .wasm вместо трёх exe» не стоит дополнительной прослойки рантайма в MVP.

### 5.4 Сводная таблица

| Компонент | Браузерный wasm | WASI (wasmtime) | Нативный процесс |
|---|---|---|---|
| Релей (WS-сервер + MCP HTTP) | ❌ нет listen/accept | ⚠️ возможно (preview2-сокеты, прецедент в репо), но рантайм = установка | ✅ рекомендуемый путь (наш exe) |
| Туннель | ❌ | ❌ (сторонний код в wasm недоступен) | ✅ cloudflared/tsd-бинарник, супервайзится релеем |
| WS-клиент вкладки canvas-web | ✅ web-sys (уже в плане гибрида) | — | — |
| Headless-бэкенд | ❌ | ✅ canvas-mcp-headless под wasmtime (FR-037, уже работает) | ✅ тот же код нативно |

**Вердикт:** вопрос «можно ли всё сделать через загрузку wasm» — нет. Wasm в этой архитектуре занимает ровно одну нишу — WS-клиент в вкладке — и она уже закрыта web-sys. Всё, что обязано жить дольше вкладки и уметь слушать порты, живёт в нативных процессах.

## 6. Безопасность (обязательные условия при включении туннеля)

- **Токен становится обязательным.** Как только MCP-лицо экспонировано наружу, доступ без токена недопустим. Токен передаётся в заголовке, не в URL — строже, чем Penpot (у них userToken в query-строке).
- **Quick tunnel = публичный по URL.** Защита = токен + непредсказуемость временного адреса. Для named tunnel поверх можно включить Cloudflare Access (Zero Trust) — тогда без аутентификации на edge до релея не долетает вообще ничего.
- **Tailscale Serve** — самый консервативный вариант: URL доступен только машинам tailnet, публичной экспозиции нет вовсе; Funnel включается точечно, когда публичный адрес реально нужен.
- **Capability-фильтр на tools/list** (браузерное подмножество из ~39 инструментов) — та же грануляция, что в плане гибрида: удалённый агент не должен видеть больше, чем локальный.
- CORS/allowlist на HTTP-лице релея — по умолчанию deny, кроме известных клиентов.

## 7. Рекомендация

1. **Волна релея (MVP): localhost-only.** Наш exe (в установщике / отдельным артефактом), WS-сервер для вкладки + MCP Streamable HTTP для локальных агентов. Ноль внешних установок, ноль аккаунтов, туннеля нет. Токен в заголовке включаем с первого дня (localhost — тоже граница доверия, но она мягче).
2. **Инкремент «удалённые агенты»: обёртка над cloudflared** (вариант (c) §4.2) — тоггл в настройках, автоскачивание с checksum, супервизия дочернего процесса, показ временного URL. Токен с этого момента жёстко обязателен.
3. **Опционально, по спросу:** named tunnel + Cloudflare Access (стабильный адрес), Tailscale Serve для tailnet-пользователей.
4. **Не делать:** WASI-формат артефакта релея (возможен позже как кроссплатформенная упаковка, UX-выигрыша нет), встраивание туннельного протокола в процесс релея, ngrok.

Отдельно зафиксировать в будущем ADR (преемник ADR-0009 по сетевому транспорту): топологию «релей = точка встречи», обязательность токена, границу доверия localhost, решение по PNA (loopback с Pages сейчас; раздача бандла релеем — запасной план).

## 8. Открытые вопросы для обсуждения

1. **Провайдер туннеля** по умолчанию: Cloudflare quick tunnel (рекомендация) vs Tailscale (если целевые пользователи массово сидят в tailnet)?
2. **Автоскачивание cloudflared** (вариант (c)) — приемлема ли тихая загрузка бинарника извне с точки зрения политики дистрибуции, или нужен явный диалог пользователя при первом включении?
3. **PNA-стратегия:** остаёмся на `ws://localhost` с Pages (с риском ужесточения Chrome) или сразу закладываем раздачу бандла релеем как первичный режим?
4. **Токен:** статичный в настройках (проще) vs per-session генерируемый релеем (безопаснее, но агенту надо его доставлять на каждую сессию)?
5. **WASI-релей:** закрывать вопрос окончательно или держать как «формат артефакта на будущее» (например, если появится desktop-Linux дистрибуция)?
6. **Удалённые агенты в MVP:** действительно ли нужны в первой волне, или localhost-only закрывает фактический сценарий владельца и туннель можно отложить без потери ценности?
