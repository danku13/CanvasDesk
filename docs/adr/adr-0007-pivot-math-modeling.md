# ADR-0007: Pivot CanvasDesk — визуальная система математического моделирования

- **Статус:** принято
- **Дата:** 2026-09-17
- **Участники:** владелец (концепция pivot, прямое указание), агент (аудит документации, оформление)
- **Связанные:** CR-013; FR-013…FR-029; ADR-0001…ADR-0006; README.md, AGENTS.md, CONTEXT.md, docs/SPEC.md, user-docs/

## Контекст

Прямое указание владельца от 2026-09-17: **CanvasDesk делает pivot в визуальную
систему математического моделирования**. До этого момента позиционирование
продукта (README, AGENTS.md, SPEC, user-docs) оставалось на уровне первой
волны — «аналог Obsidian Canvas / Miro поверх реальной файловой системы», —
тогда как фактическая траектория продукта (волна FR-013…FR-029: Numi-движок,
поток значений, доменные единицы, queueing, 45 шаблонов, юнит-экономика,
MCP-композиция) уже сформировала другое ядро: **исполняемые математические
модели на зумируемом канвасе**. Документация разошлась с продуктом.

Аудит всей документации репозитория (2026-09-17) зафиксировал разночтения;
они устраняются в соответствии с этим pivot. Реестр аудита — ниже.

## Драйверы решения

- Единое позиционирование во всех входных документах (README, AGENTS, SPEC,
  user-docs, глоссарий): CanvasDesk — визуальная система математического
  моделирования; расчётное ядро — первичный контент канваса.
- Файловый канвас, виджеты, desktop-режим, M7 — **носитель и инфраструктура**
  (не отвергаются, переопределяются как основа, на которой строятся модели).
- Концепция «один шаблон = один расчёт» (ADR-0002) — частный случай нового
  позиционирования, её формулировки не меняются.
- Вся документация согласована по фактам: счётчики (шаблоны, крейты,
  инструменты), нумерация FR, статусы форматов, исторические пометки.

## Рассмотренные варианты

### Вариант A: Переписать всю документацию «с нуля» под новое позиционирование
- Плюсы: максимальная чистота.
- Минусы: уничтожает трассируемость (CR/FR, ACCEPTANCE, статьи — история
  проектирования); большие риски регрессии фактов, которые верны.

### Вариант B: Перецентрация входных документов + точечные правки фактов + ренумерация + дисклеймеры
- Плюсы: позиционирование меняется там, где оно живёт (README/AGENTS/SPEC/
  CONTEXT/user-docs); факты исправляются адресно по реестру; история
  сохраняется и помечается; объём правок ограничен.
- Минусы: часть документов остаётся двухслойной (историческая волна +
  новая волна) — принято: слои явно помечены ссылками.

### Вариант C: Не трогать корень, ограничиться CR/FR-документацией
- Плюсы: минимальный diff.
- Минусы: входные документы (README/AGENTS/SPEC) — то, что читает первый
  агент и пользователь; разночтение позиционирования воспроизводится снова.

## Решение

Принят вариант B. Позиционирующий контракт продукта:

> **CanvasDesk — визуальная система математического моделирования:**
> бесконечный зумируемый канвас, на котором исполняемые математические модели
> строятся из расчётных нод (Numi-листы и шаблоны), значения проливаются по
> value-связям (DAG-движок), доменная математика (единицы, queueing, финансы)
> встроена в ядро, а ИИ-агент собирает и проверяет модели через MCP.

Файловый канвас, виджеты, desktop-режим, M7 — носитель/инфраструктура.
Устранение разночтений — по реестру выше: перецентрация входных документов,
исправление счётчиков (45 шаблонов, 7 крейтов, хоткеи, оглавление
ACCEPTANCE), ренумерация задвоенных FR (fr-025-persistent → FR-030,
fr-027-help → FR-031), исторические дисклеймеры (статья FR-013, BYOK),
фиксация фактического объёма v1 в FR-027 (4 из 14 функций).

## Обоснование

Вариант B устраняет причину разночтений (устаревшее позиционирование входных
документов) без разрушения истории проектирования, которая сама по себе —
актив проекта (CR/FR-документы, статьи, девлог используются как источник
контекста агентами). Ренумерация устраняет постоянный источник ошибок
ссылок (два FR-027 в ACCEPTANCE/user-docs), дисклеймеры защищают от
восприятия исторического стека как актуального.

## Последствия

- **Положительные:** один и тот же позиционирующий контракт во всех входных
  документах; новые агенты и пользователи видят продукт как систему
  моделирования; счётчики и нумерация согласованы с кодом.
- **Отрицательные / принятые риски:** коммиты и часть код-комментариев
  сохраняют старые номера FR-025/FR-027 (историческая трассировка) — снято
  легаси-пометками в шапках перенумерованных документов; двухслойность
  дорожной карты README (T-волна и FR-волна) — принято, слои подписаны.
- **Нейтральные:** далее позиционирование меняется только новым ADR.

## Валидация

- grep-контроль: «Аналог Obsidian Canvas / Miro» остаётся только в
  исторических документах с дисклеймером или в контексте совместимости
  формата (Obsidian как interoperability, не позиционирование).
- Числа согласованы: шаблоны — 45 (`ls assets/templates`), крейты — 7
  (`ls crates`), страницы user-docs — 7, MCP-инструменты — 22.
- Нумерация: `fr-030-*`, `fr-031-*` существуют; примечание index говорит
  о следующем номере FR-032; задвоенных номеров нет.
- Чек-лист фактических правок — в реестре выше; каждый пункт закрыт
  коммитом этого ADR.
