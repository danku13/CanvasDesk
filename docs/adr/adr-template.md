# Шаблон Architecture Decision Record (ADR)

Один файл = одно архитектурное решение. Имя файла: `adr-<NNNN>-<краткое-название>.md`,
нумерация сквозная, номера не переиспользуются. Запись дополняется, но не переписывается
задним числом: изменение решения фиксируется новым ADR со ссылкой на заменяемый.

---

```
# ADR-NNNN: <Название решения>

- **Статус:** предложено | принято | заменено (ADR-XXXX) | отклонено
- **Дата:** YYYY-MM-DD
- **Участники:** <кто принимал решение (владелец, агент)>
- **Связанные:** <CR/FR, другие ADR, разделы SPEC/TASKS>

## Контекст

<Ситуация и ограничения, в которых принимается решение. Факты о системе
с ссылками на код/документы. Что известно на момент решения.>

## Драйверы решения (требования)

<Список требований/ограничений, которым решение обязано соответствовать.
Каждое требование — проверяемая формулировка.>

## Рассмотренные варианты

### Вариант A: <название>
<Описание.>
- Плюсы: …
- Минусы: …

### Вариант B: <название>
…

## Решение

<Выбранный вариант + точная формулировка решения (1–3 предложения,
которые можно проверить кодом или тестом).>

## Обоснование

<Почему выбран именно этот вариант: какие драйверы он закрывает,
чем пожертвовали, почему остальные варианты хуже.>

## Последствия

- **Положительные:** …
- **Отрицательные / принятые риски:** …
- **Нейтральные (инерция):** …

## Валидация

<Как проверить, что решение работает: тесты, метрики, ручной сценарий,
ссылка на acceptance-чек-лист CR/FR.>
```

---

Правила для агентов:

1. ADR пишется **до** реализации решения в коде (допустимо — одновременно с первым FR).
2. `Статус: принято` — только после подтверждения владельца либо если решение
   вытекает из его прямого запроса (ссылка на запрос в `Контекст`).
3. Каждый ADR ссылается минимум на один CR/FR (там живут требования и приёмка)
   и наоборот — соответствующий CR/FR ссылается на ADR.
4. Отмена решения: новому ADR поле `Статус` заменяемого → `заменено (ADR-XXXX)`.
