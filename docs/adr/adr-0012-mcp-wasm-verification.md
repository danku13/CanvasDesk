# ADR-0012: Верификация MCP-реализации в WASM — крейт canvas-scene и headless MCP-сервер (wasm32-wasip1, wasmtime)

- **Статус:** принято (2026-09-19: исполнено MW1–MW4 по приказу владельца «работай сам» — план FR-037 реализован, гейты зелёные)
- **Дата:** 2026-09-18
- **Участники:** владелец (приказ «теперь спланировать реализацию MCP для WASM, чтобы можно было проверять не только UI, но и реализацию MCP»), агент (исследование кода, дизайн, план FR-037)
- **Связанные:** ADR-0011 (прецедент: wasm-гейт ядра + wasmtime), ADR-0009 (транспортная совместимость MCP), ADR-0010 (чистота stdio), ADR-0004 (агентная сборка через MCP), FR-037 (план реализации), FR-036, `docs/plans/wasm-port.md` (M8: задача W2, §9 волна 2), `crates/canvas-app/src/main.rs` (mcp_dispatch), `crates/canvas-mcp/src/lib.rs`

## Контекст

Приказ владельца от 2026-09-18: спланировать реализацию MCP для WASM, чтобы
проверять **не только UI, но и реализацию MCP**. Состояние верификационных
способностей после FR-036/CP5 (main `b9e011c`):

- **Ядро** — верифицируется под wasm: компиляция `wasm32-unknown-unknown`
  (CI `wasm-check`) + исполнение 301 теста `canvas-core` в wasmtime
  (`wasm32-wasip1`, FR-036/ADR-0011).
- **UI** — верифицируется частично и не в wasm: Xvfb-демо на Linux
  (`docs/DEMO.md`, `scripts/xdemo.py`); браузерный wasm-рантайм — волна 1
  плана M8 (бэклог S5 роадмапа, задачи W1–W12).
- **MCP** — не верифицируется вне Windows **вообще**:
  - 27 инструментов (`mcp_dispatch`, `main.rs:6074`) физически живут в
    бинарнике `canvas-app`, который под wasm не собирается (winit-run,
    потоки, arboard, `env::args` — карта замен §3 плана M8);
  - мост `canvas-mcp` под wasm-таргеты ни разу не проверялся;
  - end-to-end MCP-сессия требует named pipe `\\.\pipe\canvasdesk` и
    запущенное GUI-приложение — в Linux-контейнере агента нет ни того, ни
    другого.

При этом MCP-слой — **контрактный центр продукта** (ADR-0004): «вау-петля»
роадмапа — «агент собирает модель по описанию» — целиком стоит на
MCP-инструментах; ближайшие шаги роадмапа (CP4 — рецепт агента, CP6 —
FR-017) будут интенсивно итерировать именно этот слой.

Факты кода, делающие дешёвое решение возможным:

1. `mcp_dispatch` — уже чистая функция: «тестируется без окна и pipe»
   (комментарий `main.rs:6070`); её зависимости — `SceneState`, `Camera`
   (только `position`/`zoom`/`set_center`/`set_zoom`, `main.rs:6855–6876`),
   `TemplateRegistry` (`canvas-core`, embedded `include_dir` — wasm-OK).
   Мутирующие ветки ходят в `scene.mark_dirty/push_undo/recompute_flow/
   move_node/ensure_reserve_at` — всё модельное, без UI и ФС
   (`node_create_file` файл на диске НЕ создаёт; автосейв — обязанность
   App, не диспетчера).
2. Тесты уже есть и уже чистые: ~40 MCP-тестов в `main.rs:12060+`
   (включая гейт эталона `mcp_fr029_instagram_mvp_reference`,
   `main.rs:14183`) — исполняются нативно на Linux, но не в wasm-рантайме.
3. Мост `canvas-mcp` — уже чистая протокольная логика за трейтом
   `AppTransport` (`lib.rs:60`: `send_line`/`recv_line`/`is_connected`) +
   stdio-цикл `run_stdio` (`lib.rs:594`); платформенное — только
   Windows-pipe и автоспавн под `cfg(windows)`/`cfg(any(windows, test))`.
   Протокол — newline-delimited JSON-RPC 2.0, batch, версии
   2024-11-05…2025-06-18 (ADR-0009); на wasip1 stdio полноценно работает в
   wasmtime.

## Драйверы решения

- **Автономная верификация контрактного слоя.** Регресс MCP-инструментов =
  слом агентной петли (ADR-0004/0005) — самый дорогой класс регрессов
  продукта; агент должен уметь ловить его без Windows и GUI.
- **Дешёвые итерации CP4/CP6.** Рецепт агента (CP4) и what-if (CP6) будут
  править MCP-слой; wasm-сессия в контейнере сокращает цикл проверки с
  «нативные юнит-тесты + ручная сессия владельца на Windows» до одной
  локальной команды.
- **Reuse волны 2 M8.** Заявка «MCP WebSocket-мост» (`wasm-port.md` §9)
  потребует ровно headless-сервер над SceneState; проектируемый слой —
  серверная сторона этого моста, не выброс.
- **Минимум поверхности.** Ноль новых внешних cargo-зависимостей
  (serde_json/anyhow/tracing/canvas-core уже в дереве — лицензионный гейт
  CP0 не затронут); wasmtime — внешний инструмент гейта, не зависимость.

## Рассмотренные варианты

### Вариант A: ничего не выносить — оставить нативные юнит-тесты mcp_dispatch
- Плюсы: ноль работы — тесты уже зелёные на Linux.
- Минусы: нет end-to-end протокольного цикла (initialize → tools/list →
  tools/call) в воспроизводимой песочнице; wasm-совместимость слоя не
  защищена гейтом; реальная MCP-сессия с внешним клиентом в контейнере
  невозможна — цель приказа не достигается.
- Вывод: отклонено.

### Вариант B: выполнить W2 целиком (вынос App в lib) — затем wasm-тесты
- Плюсы: канонический путь плана M8; максимальное переиспользование.
- Минусы: W2 — перемещение ~10–15 тыс. строк `main.rs` с обвязкой
  сервисов; сам по себе не даёт ни MCP-гейта (нужен ещё транспорт), ни
  сессии; объём несопоставим с приказом «спланировать MCP для WASM».
- Вывод: отклонено в этом заходе; FR-037 выполняет **ядро W2** (вынос
  SceneState) и сужает W2 до App-обёртки — см. «Последствия».

### Вариант C: wasm-bindgen-фасад + wasm-bindgen-test (Node/браузер) сразу
- Плюсы: прямой путь к продуктовому web-слою (W4+ M8).
- Минусы: смешивает верификацию с продуктовым портом (бэклог S5); тянет
  пин wasm-bindgen-cli и Node-обвязку; для драйвера «проверять реализацию
  MCP» stdio в wasmtime проще и уже обоснован ADR-0011.
- Вывод: отклонено сейчас (прецедент ADR-0011, вариант C); фасад —
  волна 2, поверх HeadlessSession.

### Вариант D: трёхслойная верификация без продуктовых изменений — ПРИНЯТО
1. вынос слоя инструментов в платформенно-нейтральный крейт
   **`canvas-scene`** (SceneState модельного слоя + `mcp_dispatch`);
2. исполнение инструментов и **протокольного цикла** под
   `wasm32-wasip1` в wasmtime (расширение паттерна FR-036);
3. **headless MCP-сервер** `canvas-mcp-headless`: stdio-сервер с
   in-process транспортом — реальная MCP-сессия для внешнего клиента или
   драйвера в контейнере, без Windows и GUI.

## Решение

1. **Крейт `canvas-scene`** (lib, лист в DAG рядом с core): `SceneState`
   модельного слоя — поля `canvas/spatial/path/dirty_since/undo_stack/
   redo_stack/expr_results/expr_line_results/analysis/viewport` и методы
   (`new`, `recompute_flow`, `mark_dirty`, `push_undo/take_undo/take_redo`,
   `move_node`, `ensure_reserve_at`, `recompute_expr`, …) — плюс модуль
   `mcp`: `mcp_dispatch` (27 инструментов, ~1550 строк), хелперы
   (`mcp_unwrap_call`, `mcp_req_str/f32`, `mcp_node_*`, `mcp_edge_json`,
   ~130 строк), `next_free_id`. UI-состояние взаимодействия
   (`selected`, `selected_nodes`, `dragging` — 99 мест доступа в main.rs)
   остаётся в App. Viewport-инструменты работают со значением
   `Viewport {x, y, zoom}` в SceneState; синхронизация с `Camera` — в
   `on_mcp_wake` (`cfg(windows)`, ~8 строк, числа идентичны — поведение
   viewport_get/set не меняется). Зависимости: `canvas-core`,
   `serde_json`, `tracing` — **ноль новых внешних зависимостей**.
2. **`canvas-mcp`**: чистый рефактор — выделение
   `run_stdio_with_transport<T: AppTransport>` (публичная функция;
   `run_stdio` становится обёрткой с Windows/offline-логикой подключения,
   поведение FR-008/034/035 не меняется). Крейт включается в
   `wasm-check` (компиляция `wasm32-unknown-unknown`) и в wasip1-прогон
   тестов (15 шт.; тесты автоспавна, использующие `std::process` в
   test-cfg, гейтятся `#[cfg(not(target_arch = "wasm32"))]` — test-only
   cfg по прецеденту FR-036/ADR-0011).
3. **Крейт `canvas-mcp-headless`** (lib + bin `canvasdesk-mcp-headless`,
   лист в DAG — паттерн `canvas-web` §3.5 M8, нативный граф зависимостей
   не затронут): `HeadlessSession` (SceneState +
   `TemplateRegistry::builtin()`) за `AppTransport` — `send_line`
   воспроизводит конверт приложения ровно как `on_mcp_wake`:
   `parse_envelope → mcp_unwrap_call → mcp_dispatch → build_result/
   build_call_error`; bin — stdio-цикл `run_stdio_with_transport` для
   исполнения в wasmtime. Сессия in-memory: файловых операций нет
   (модель собирается `graph_apply`, как в гейте эталона CP1/CP3/CP5).
4. **Верификационные артефакты**: `scripts/mcp_wasm_e2e.py` — драйвер
   реальной JSON-RPC-сессии (initialize → tools/list = 27 → graph_apply
   мини-эталон №1 → oracle ±1% → analyze_bottlenecks → негативные ветки:
   неизвестный инструмент, битый конверт, batch); `scripts/
   mcp_wasm_gate.sh` — гейт одной командой (сборка wasip1 + wasmtime +
   драйвер); CI-джоба `wasm-check` расширяется компиляцией трёх крейтов
   (исполнение остаётся локальной ступенью — прецедент ADR-0011).
5. **Границы**: продуктовые Windows-ветки (pipe-сервер, автоспавн, GUI)
   не меняются; `wasm32-unknown-unknown` остаётся продуктовым таргетом
   (компиляция), `wasm32-wasip1` — тестовым; браузерный WebSocket-мост и
   wasm-bindgen-фасад — волна 2 M8 поверх `HeadlessSession`.

## Обоснование

Вариант D закрывает приказ минимальной ценой, потому что оба слоя уже
спроектированы чистыми: диспетчер — чистая функция (факт кода), мост —
чистый протокол за `AppTransport` (факт ADR-0009). Недостаёт только
(а) физического выноса инструментов из непригодного для wasm бинарника и
(б) in-process транспортом, который сшивает их с протоколом моста — оба
действия механические и не меняют поведение. Уровни верификации
оказываются полными: юнит-семантика инструментов (wasip1-тесты перенесённого
модуля) → протокольный цикл (lib-тесты headless) → реальная сессия
(драйвер в wasmtime) — при сохранении 1034+ нативных тестов без регресса.
Вариант A не даёт сессии; B несопоставим по объёму; C преждевременен.

## Последствия

- **Позитив:** MCP-слой верифицируется в wasm-рантайме одной командой
  (`scripts/mcp_wasm_gate.sh`) в контейнере без GUI/Windows; регресс
  контракта ADR-0004 ловится до пуша; CP4/CP6 получают дешёвый цикл
  итераций; волна 2 M8 получает готовую серверную сторону моста;
  W2 сужается до выноса App-обёртки (~половина его объёма уже сделана
  этим решением).
- **Нейтрально:** перенос ~5 тыс. строк из `main.rs` (механика, защищена
  паритетом тестов — те же ассерты, то же число тестов); wasip1-харнесс
  однопоточный (принято ADR-0011); `Instant` в `mark_dirty` исполняется
  на wasip1 корректно, но остаётся блокером браузерного исполнения до
  W1 (`web_time`) — wasm32-unknown-unknown для новых крейтов остаётся
  compile-only, как у ядра по FR-036.
- **Негативно:** явных минусов нет; риск переноса крупного блока
  митигируется нулевым изменением ассертов и гейтами fmt/clippy/test.
- **Отложено:** wasm-bindgen-фасад и WebSocket-мост (волна 2 M8, S5);
  файловый режим headless-сервера (`--canvas <путь>` через wasip1
  `--dir`); wasmtime-ступень в CI.

## Валидация (планируемая — критерии приёмки FR-037)

- `cargo check --target wasm32-unknown-unknown -p canvas-core
  -p canvas-render -p canvas-widgets -p canvas-mcp -p canvas-scene
  -p canvas-mcp-headless` — зелёный (расширение гейта FR-036).
- `RUST_TEST_THREADS=1 cargo test --target wasm32-wasip1 -p canvas-core
  -p canvas-scene -p canvas-mcp` — зелёный: 301 (core) + ~40
  (перенесённые MCP-тесты) + ~15 (мост) + протокольные e2e headless.
- `scripts/mcp_wasm_gate.sh` — полная MCP-сессия в wasmtime сходится по
  oracle-числам эталона №1 (ADR-0005/0006) ±1%.
- Нативный регресс — ноль: `cargo test --workspace` — 1034+ зелёные
  (состав тестов сохранён, счёт не убывает); fmt/clippy чистые.
- Поведение Windows-веток не изменено: pipe round-trip тесты
  `canvas-shell` зелёные; `canvasdesk mcp` (FR-008) — без изменений.
