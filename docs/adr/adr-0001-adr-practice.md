# ADR-0001: Введение практики ADR и формата записей

- **Статус:** принято
- **Дата:** 2026-09-17
- **Участники:** владелец (запрос), агент (оформление)
- **Связанные:** CR-013; `docs/adr/adr-template.md`; ADR-0002…ADR-0005

## Контекст

Проект развивается сериями CR/FR, где фиксируются требования и приёмка, но не
фиксируются сами **архитектурные решения** — почему выбран такой контракт, какие
варианты отвергнуты и чем пожертвовали. Запрос владельца от 2026-09-17 (завести
`/adr` с шаблоном описания ADR и записями под задачу агентной композиции
архитектур) сделал практику обязательной: решения по концепции «проливания
значений» (CR-013) касаются модели данных рёбер, манифестов шаблонов и MCP —
эти решения переживают несколько FR и должны иметь постоянный адрес.

## Драйверы решения

- Каждое значимое решение имеет постоянный, цитируемый адрес (`docs/adr/adr-NNNN`).
- Формат един для агентов и человека: контекст → варианты → решение → последствия → валидация.
- Решения прослеживаемы: ADR ↔ CR/FR ссылаются друг на друга.
- Записи иммутабельны по существу: отмена — через новый ADR, а не переписывание.

## Рассмотренные варианты

### Вариант A: Решения внутри CR/FR-документов (раздел «Решение»)
- Плюсы: всё в одном файле с требованиями.
- Минусы: решение размазывается по многим FR; нет единого индекса; невозможно
  сослаться на «решение» независимо от конкретной фичи; отвергнутые варианты
  теряются при реализации.

### Вариант B: Классический MADR на английском в `docs/adr/`
- Плюсы: проверенный формат, англоязычная совместимость.
- Минусы: вся проектная документация ведётся на русском (CR/FR, user-docs) —
  второй язык создаёт рассинхрон терминологии.

### Вариант C: Свободная форма без шаблона
- Плюсы: быстро.
- Минусы: записи несопоставимы, «варианты» и «последствия» пропадают.

## Решение

Принята практика ADR по шаблону `docs/adr/adr-template.md` (вариант B,
адаптированный: русский язык, поля `Участники`/`Связанные` как в CR-шаблоне,
раздел «Валидация» обязателен). Один файл — одно решение; нумерация сквозная;
жизненный цикл статуса: `предложено → принято → заменено/отклонено`.

## Обоснование

Формат закрывает все четыре драйвера при минимальной надстройке над существующим
процессом CR/FR. Русский язык согласован с остальной документацией; обязательный
раздел «Валидация» связывает решение с автогейтами и acceptance-чек-листами.

## Последствия

- **Положительные:** решения имеют постоянный адрес; новые агенты читают
  контекст решений до реализации; отвергнутые варианты не переоткрываются.
- **Отрицательные / принятые риски:** дублирование части контекста между ADR и
  CR/FR (принято: ADR — «почему», CR/FR — «что и как проверить»).
- **Нейтральные:** каталог `docs/adr/` ведётся вручную; индекс — `docs/adr/README.md`.

## Валидация

- Каждый новый ADR соответствует структуре шаблона (контекст, драйверы, варианты, решение, обоснование, последствия, валидация).
- Каждый ADR связан ≥ 1 CR/FR, и соответствующий CR/FR ссылается обратно.
- Первая пятёрка записей (ADR-0001…0005) сопровождает CR-013/FR-029 — пример применения практики.
