# ADR-0004: Агентная сборка архитектур — MCP как единственный канал, с чтением графа, адресацией и батч-применением

- **Статус:** принято
- **Дата:** 2026-09-17
- **Участники:** владелец (запрос), агент (анализ и оформление)
- **Связанные:** CR-013 (G3, G4, G6, G7); FR-005, FR-014, FR-029; ADR-0002, ADR-0003

## Контекст

ИИ-агент работает с канвасом только через MCP (`canvasdesk-mcp` → named pipe →
`canvas-app`): 22 инструмента (`crates/canvas-mcp/src/lib.rs:175-332`). Аудит
под задачу композиции (CR-013) выявил: агент не видит существующие связи (нет
`edges_list` — G4); не может создать value-ребро с адресацией порта одним
вызовом (`edge_create` без `fromLine/fromOutput/toParam/kind` — G3); сборка
эталонной архитектуры — ~50 RPC-вызовов без транзакционности (G6); нет
инструмента валидации графа (G7). При этом расчётное ядро готово отдать всё
нужное: `propagate_with_lines` уже считает построчные выходы на каждом ревале.

## Драйверы решения

- Агент должен и строить, и **читать** граф (ноды, связи, значения) — полный цикл «собрал → проверил → скорректировал».
- Одна связь — один вызов (тип + адресация портов вместе с геометрией).
- Сборка архитектуры — воспроизводимая и атомарная операция: частичный сбой не оставляет полусобранный граф.
- Нарушения контракта (неизвестное имя порта, несовместимая единица) диагностируются в момент создания, а не молча при eval.

## Рассмотренные варианты

### Вариант A: Точечное расширение текущих инструментов (+5 мелких вызовов)
- Плюсы: минимальные изменения.
- Минусы: не решает атомарность; число вызовов на эталон остаётся ~50; агент
  обязан держать protocol-состояние между вызовами.

### Вариант B: Чтение графа + расширенный `edge_create` + батч `graph_apply` (+ `graph_validate`)
- Плюсы: закрывает G3–G7 системно; `graph_apply` даёт транзакционность и один
  undo-шаг; декларативный JSON-план архитектуры легко генерировать и версио-
  нировать (рецепты = файлы).
- Минусы: крупнейший объём работы из вариантов; нужен careful-дизайн схемы
  операций и отчёта.

### Вариант C: Отдельный композитный формат (агент присылает целый «документ архитектуры»)
- Плюсы: максимум декларативности.
- Минусы: дублирует формат `.canvas`; пропускает инкрементальные сценарии
  (добавить одну связь в чужой граф); преждевременно до FR-020 (custom templates).

## Решение

MCP — единственный канал агентной сборки. Поверх существующих 22 инструментов:
(1) `edges_list` — чтение связей; (2) `edge_create` v2 — опциональные
`fromLine/fromOutput/toParam/kind` (одна связь — один вызов, валидация имён
портов на месте); (3) `flow_recalc` v2 — узловые значения + именованные выходы
+ построчные значения + warnings; (4) `graph_apply` — атомарный батч операций
(create_note / instantiate / edge / set_params / delete), один undo-шаг,
отчёт с созданными id и ошибками по операциям; (5) `graph_validate` —
единицы/висячие входы/дубль-входы/перегрузки как отчёт. Композитный формат
(вариант C) — следующий шаг после FR-020 и не заменяет, а надстраивается над
этим набором.

## Обоснование

Вариант B закрывает все драйверы и сохраняет инкрементальность: каждый
инструмент полезен независимо (чтение графа — сразу, батч — по мере роста
сценариев). Транзакционность батча ложится на уже существующий undo-механизм
(`push_undo` в `mcp_dispatch`) — снапшот канваса до применения. Декларативный
план `graph_apply` естественным образом становится форматом «рецептов
архитектур» (эталон ADR-0005 сериализуем в план).

## Последствия

- **Положительные:** полный цикл агентной работы без UI; воспроизводимые
  сборки; простая диагностика контракта; уменьшение числа RPC на эталон
  (~50 → ~2: `graph_apply` + `flow_recalc`).
- **Отрицательные / принятые риски:** рост поверхности MCP-инструментов
  (схемы дублируются в `tools_list`-тесте); батч из ~30 операций увеличивает
  таймаут-риск (30 с) — принято: применять чанками или поднять таймаут для
  `graph_apply`.
- **Нейтральные:** старые инструменты не удаляются и не меняют семантики
  (обратная совместимость агентов).

## Валидация

- E2E-тест `mcp_dispatch`: последовательность `graph_apply(план ADR-0005)` →
  `edges_list` показывает все связи с адресацией → `flow_recalc` сходится с
  эталонной таблицей.
- Откат: ошибка в середине батча — канвас байт-в-байт равен снапшоту до
  `graph_apply`; один `undo` (внутренний) возвращает базу.
- FR-029 (чтение + адресация) — первый шаг; `graph_apply`/`graph_validate`
  оформляются отдельными FR из R3/R2 CR-013.
