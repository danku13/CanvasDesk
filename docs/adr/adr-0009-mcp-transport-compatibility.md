# ADR-0009: Транспортная совместимость MCP — протокол 2025-06-18, batch-запросы и отказоустойчивый handshake

- **Статус:** принято
- **Дата:** 2026-09-18
- **Участники:** владелец (запрос «перепроектировать MCP — hermes agent не может нормально подключиться»), агент (диагностика, дизайн, реализация)
- **Связанные:** ADR-0004 (агентная композиция через MCP), FR-034, ADR-0008; `crates/canvas-mcp/src/lib.rs`, `crates/canvas-mcp/src/main.rs`, `docs/SPEC.md` §13, `docs/BYOK.md` §3

## Контекст

Внешний MCP-клиент (агент hermes) не может нормально подключиться к
`canvasdesk-mcp`. Диагностика транспортного слоя (чтение кода + прогон
эмуляции клиентской сессии, 2026-09-18) выявила пять дефектов моста
stdio ↔ named pipe:

1. **Протокольный даунгрейд.** `SUPPORTED_PROTOCOLS = ["2025-03-26", "2024-11-05"]`
   — клиент, присылающий актуальную версию спецификации `2025-06-18`,
   получает в ответ `2024-11-05`. Строгие SDK (TypeScript/Python MCP SDK
   проверяют `protocolVersion` в ответе сервера) разрывают соединение:
   «Server's protocol version is not supported».
2. **Batch-запросы отклоняются.** JSON-RPC 2.0 массив (батчи разрешены
   спецификацией MCP с 2025-03-26) не проходит `parse_envelope` — клиент
   получает `-32600 «ожидался JSON-RPC объект»` и считает сервер сломанным.
3. **Двойная упаковка результата tools/call.** Приложение отвечает по pipe
   JSON-RPC-конвертом (`build_result` в `on_mcp_wake`), а мост кладёт этот
   конверт ЦЕЛИКОМ строкой в `content[0].text` — агент получает
   `"{\"jsonrpc\":\"2.0\",\"id\":…,\"result\":…}"` вместо результата
   инструмента и обязан парсить JSON внутри JSON. Юнит-тест моста этого не
   ловит: `FakeTransport` возвращает чистое значение, а не конверт.
4. **Крах сервера при недоступном приложении.** `initialize` без pipe →
   JSON-RPC ошибка `-32002` и `exit(2)`. Для клиента это выглядит как
   падение MCP-сервера: сессия не устанавливается вовсе, диагностики нет.
   Автоспавн GUI ждёт pipe до 15 с — на медленной машине клиент успевает
   прибить процесс раньше (свой connect-timeout).
5. **Нет переподключения.** Транспорт фиксируется один раз при старте
   процесса: если приложение поднялось позже (или pipe-сессия разорвалась),
   все вызовы до перезапуска моста отвечают «не запущен».

Дополнительное ограничение: read-only методы `resources/list`,
`prompts/list`, `resources/templates/list`, `logging/setLevel` и
уведомление `notifications/cancelled` отвечают `-32601`; часть хостов
зондирует их безотносительно заявленных capabilities.

## Драйверы решения

- hermes подключается как типовой MCP-клиент по stdio: handshake обязан
  проходить при любом состоянии бэкенда (приложение запущено / поднимается /
  отсутствует).
- Совместимость с уже работающими клиентами (Claude Desktop и конфиги из
  `docs/BYOK.md`) — поведение живого стека не должно ухудшиться.
- SPEC §7.6: MCP работает только локально, сетевых вызовов нет.
- Инструментальный слой (26 инструментов, `mcp_dispatch`) стабилен и не
  пересматривается — меняется только транспортный конверт.

## Рассмотренные варианты

### Вариант A: Сетевой транспорт (Streamable HTTP / SSE endpoint)
- Плюсы: покрывает удалённых агентов и контейнеры; современный стандарт.
- Минусы: hermes работает на той же машине (подтверждено владельцем) — сеть
  не нужна; противоречит SPEC §7.6 («только локально»); новый порт/токен/
  поверхность атаки; отдельная реализация HTTP-стека.
- Вывод: отклонено; возвращаться к варианту стоит только при появлении
  удалённого агента (тогда — отдельный ADR с Bearer-токеном и bind-адресом).

### Вариант B: Переход на официальный MCP SDK (rmcp и аналоги)
- Плюсы: протокол «из коробки».
- Минусы: тяжёлая зависимость (async-runtime, транспортные фреймворки)
  ради исправления конверта; переписывание моста и ревизия 26 инструментов;
  текущие чистые функции lib.rs хорошо тестируются без pipe.
- Вывод: отклонено — несоразмерно дефектам.

### Вариант C: Точечное перепроектирование моста (протокольная совместимость)
- Плюсы: закрывает все пять дефектов в одном crate без изменений
  инструментального слоя и pipe-протокола приложения; обратная совместимость
  со старыми клиентами сохраняется (newline JSON-RPC, те же методы).
- Минусы: удалённые агенты по-прежнему не поддерживаются (осознанно —
  вариант A).
- Вывод: принято.

## Решение

Перепроектировать конвертный слой `canvas-mcp` (библиотека `run_stdio`):

1. **Версии протокола:** `SUPPORTED_PROTOCOLS = ["2025-06-18", "2025-03-26", "2024-11-05"]`
   — версия клиента эхом, если она нам известна; неизвестная версия →
   `DEFAULT_PROTOCOL = "2024-11-05"` (максимальная совместимость).
2. **Batch-запросы:** входная строка разбирается как одиночный объект ИЛИ
   массив; массив обрабатывается поэлементно, ответы собираются в массив
   (уведомления ответа не порождают; пустой массив → один ответ `-32600`;
   батч целиком из уведомлений → тишина).
3. **Разворот ответа приложения:** по pipe приходит JSON-RPC-конверт — мост
   достаёт `result` (или `error.message`) и отдаёт клиенту стандартный
   MCP-результат: `content[0].text` — чистый JSON результата,
   `structuredContent` — тот же результат, если он объект (spec 2025-06-18).
   Не-конвертный payload (легаси/тесты) кладётся как есть.
4. **Handshake без бэкенда:** `initialize` отвечает успешно всегда
   (мост — самостоятельный MCP-сервер; отсутствие приложения — состояние,
   а не фатальная ошибка). `tools/call` при недоступном приложении →
   `isError` с текстом «CanvasDesk не запущен…». `Exit` из автомата
   убирается — процесс моста живёт, пока жив stdio.
5. **Reconnect:** перед каждым `tools/call` при мёртвом транспорте —
   короткая попытка подключения к pipe (500 мс, без автоспавна): приложение,
   поднявшееся позже моста, подхватывается без перезапуска сессии.
6. **Толерантные заглушки:** `resources/list` → `{"resources":[]}`,
   `prompts/list` → `{"prompts":[]}`, `resources/templates/list` →
   `{"resourceTemplates":[]}`, `logging/setLevel` → `{}`,
   `notifications/cancelled` → тишина.
7. Автоспавн GUI при старте (FR-008), pipe-сервер приложения (`mcp_pipe`)
   и `mcp_dispatch` — без изменений.

## Обоснование

Вариант C устраняет каждый из наблюдаемых отказов подключения при
минимальной площади изменений: агент получает стандартный handshake
(эхо версии — строгие SDK не отвалятся), батчи обрабатываются по спеке,
результат вызова — чистый JSON (структурированный разбор без вложенного
парсинга), а недоступность GUI перестаёт убивать сессию. Pipe-протокол
мост ↔ приложение не меняется, поэтому приложение и 26 инструментов
остаются нетронутыми; изменения локализованы в `crates/canvas-mcp`.

## Последствия

- Позитив: hermes и любые спек-совместимые клиенты подключаются при любом
  состоянии приложения; диагностика недоступности — в каждом вызове
  (isError), а не в краше сервера; strict-SDK больше не рвут соединение
  из-за даунгрейда версии.
- Нейтрально: `HandleOutcome::Exit` удалён из публичного enum — внешний
  API крейта внутренний (`publish = false`), ревизия тестов включена в FR-034.
- Негативно: каждый `tools/call` при отсутствующем приложении добавляет до
  0,5 с на попытку reconnect (осознанная цена самовосстановления).
- Отложено: сетевой транспорт (вариант A) — при появлении удалённых агентов;
  поддержка Content-Length фрейминга не добавляется (spec требует
  newline-delimited, клиентов с LSP-фреймингом не наблюдается).

## Валидация

- Юнит-тесты `crates/canvas-mcp/src/lib.rs`: эхо `2025-06-18`; batch
  [initialize, ping] → массив двух ответов; батч из уведомлений → тишина;
  пустой батч → `-32600`; tools/call с конвертом приложения → чистый
  результат + structuredContent; tools/call с error-конвертом → isError;
  offline-handshake (initialize успешен без транспорта); reconnect-fail →
  isError; заглушки read-only методов.
- Регресс: существующие тесты моста и pipe round-trip зелёные;
  `cargo test --workspace` — без падений.
