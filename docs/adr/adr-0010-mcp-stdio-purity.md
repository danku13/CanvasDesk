# ADR-0010: Чистота stdout MCP-потока — изоляция stdio автоспавна и перевод диагностики в stderr

- **Статус:** принято
- **Дата:** 2026-09-18
- **Участники:** владелец (логи отказа hermes после FR-034), агент (диагностика, дизайн, реализация)
- **Связанные:** ADR-0009 (транспортная совместимость, FR-034), ADR-0004, FR-008 (автоспавн), FR-035; `crates/canvas-mcp/src/lib.rs`, `crates/canvas-app/src/main.rs`, `docs/SPEC.md` §13

## Контекст

После FR-034 (ADR-0009) hermes успешно регистрирует сервер `canvasdesk`
(handshake проходит, инструменты `mcp__canvasdesk__*` видны, сессии
«parked → connected»). Но вызовы инструментов падают с ошибкой клиента:

```
Invalid JSON: expected value at line 1 column 1
[type=json_invalid,
 input_value='\x1b[2m2026-09-18T11:16:…canvasdesk\\widgets"', input_type=str]
```

Разбор улики: `\x1b[2m` — ANSI escape (dim), далее timestamp формата
`tracing_subscriber::fmt`, в тексте — путь каталога виджетов
`…\canvasdesk\widgets`. В JSON-RPC-канал (stdout процесса моста) попадает
строка tracing-лога **GUI-приложения**. Цепочка (подтверждена кодом):

1. `connect_app` (canvas-mcp/src/lib.rs) при недоступном pipe спавнит
   `Command::new(exe).spawn()` **без явной настройки stdio** — в Rust это
   наследование stdin/stdout/stderr родителя.
2. Спавненный GUI (`canvasdesk`, тот же exe без аргументов) инициализирует
   `tracing_subscriber::fmt().with_env_filter(…).init()` — writer по
   умолчанию **stdout**, ANSI-коды включены по умолчанию (фича `ansi`).
3. При старте GUI логирует версию сборки, материализацию встроенных
   виджетов (реестр сканирует `…\canvasdesk\widgets`), инициализацию wgpu —
   всё это ANSI-раскрашенным текстом в унаследованный stdout.
4. Hermes парсит stdout моста как newline-delimited JSON-RPC: любая
   не-JSON строка — `Invalid JSON`, вызов падает, сессия парковится и
   возрождается (в логе — два «revived» за 12 секунд), цикл повторяется.

FR-034 этого не ловил: его тесты проверяли содержимое ответов моста, а
комментарий «Молчалив по stdout» относился только к собственному коду
моста — чужой stdout (унаследованный ребёнком) не рассматривался как
канал загрязнения.

Дополнительный дефект той же зоны: если хост запускает автономный
`canvasdesk-mcp.exe`, автоспавн поднимает `current_exe` — то есть **сам
мост**, а не GUI. Ребёнок наследует stdin родителя и начинает конкурировать
за чтение JSON-RPC-запросов (двойные ответы, потерянные сообщения), а
сам не находит pipe и рекурсивно спавнит следующего двойника. Допущение
«current_exe без аргументов — это GUI-режим того же бинарника» верно
только для единого дистрибутива `canvasdesk`.

## Драйверы решения

- **Контракт потока:** stdout процесса моста — только newline-delimited
  JSON-RPC (MCP spec); ни одна строка лога, баннера или чужого процесса
  не имеет права там появиться. stderr — диагностика (уже используется).
- Автоспавн (FR-008) сохраняется: «сервис + MCP одной командой» —
  продуктовое обещание BYOK-конфигов.
- Оба способа запуска моста обязаны работать одинаково: единый бинарь
  (`canvasdesk mcp`) и автономный (`canvasdesk-mcp.exe`).
- Логи GUI должны оставаться доступными человеку (консоль) и безопасными
  для машин-потребителей stderr (без ANSI-escape в машиночитаемых хвостах).
- Инструментальный слой (26 инструментов), pipe-протокол и конвертный
  слой FR-034 не пересматриваются.

## Рассмотренные варианты

### Вариант A: Изоляция stdio спавна в мосту (null-хэндлы)
- Плюсы: один пункт изменения закрывает класс проблемы целиком — ребёнок
  физически не может писать в stdout/stderr моста и красть его stdin;
  не зависит от того, что именно спавним и как оно логирует.
- Минусы: логи спавненного GUI теряются (для автоспавна это приемлемо —
  пользователь обычно видит GUI-окно; диагностика старта — результат
  подключения к pipe).
- Вывод: принято как ядро решения.

### Вариант B: Перевод tracing GUI в stderr (+ANSI по факту терминала)
- Плюсы: системная гигиена для всех сценариев (запуск из терминала,
  редиректы, будущие интеграции), «stdout — протокол/продукт, stderr —
  диагностика» становится явным контрактом приложения; ANSI только на
  живом терминале — хвосты stderr машиночитаемы.
- Минусы: сам по себе не защищает MCP-поток (GUI может писать в stdout
  и не через tracing).
- Вывод: принято как defense-in-depth вместе с A.

### Вариант C: Отказ от автоспавна (требовать запущенный GUI)
- Плюсы: исчезает сама возможность загрязнения от ребёнка.
- Минусы: ломает продуктовое обещание FR-008 и BYOK-конфиги «одной
  командой»; переносит сложность на пользователя.
- Вывод: отклонено.

### Вариант D: Перехват/парсинг чужого мусора в мосту (фильтр строк)
- Плюсы: мост «прощает» загрязнение.
- Минусы: лечение симптома; фильтр обязан отличать мусор от легитимных
  строк протокола (надёжно невозможно); поощряет новые источники грязи.
- Вывод: отклонено — чистота источника лучше фильтрации стока.

## Решение

Точечные изменения в двух крейтах (продолжение философии ADR-0009):

1. **Изоляция stdio автоспавна** (`canvas-mcp::connect_app`): ребёнок
   спавнится через `spawn_service_command` с
   `stdin/stdout/stderr = Stdio::null()` — унаследованный канал
   невозможен по построению; это проверяется юнит-тестом через
   `Command::get_stdin/get_stdout/get_stderr`.
2. **Ориентация спавна по бинарю:** helper `autosprawn_target` — единый
   `canvasdesk` спавнит сам себя (GUI-режим); автономный мост
   `canvasdesk-mcp` ищет GUI-бинарь `canvasdesk.exe` рядом (тот же
   каталог дистрибутива); нет соседа → offline-режим ADR-0009
   (handshake успешен, вызовы — isError «не запущен»), рекурсивный
   спавн невозможен по построению.
3. **Логи GUI — в stderr** (`canvas-app::main`): `with_writer(io::stderr)`,
   ANSI — `io::stderr().is_terminal()` (цвет для человека, чистый текст
   для машин-потребителей stderr).
4. Контракт фиксируется в SPEC §13: stdout моста — только JSON-RPC;
   автоспавн не наследует stdio; диагностика моста и GUI — stderr.

## Обоснование

Вариант A закрывает наблюдаемый отказ (единственный путь попадания чужого
текста в JSON-RPC-канал — унаследованные хэндлы спавна; других
`Command::new`/`println!` в крейте моста нет), вариант B делает тот же
класс ошибки невозможным на уровне приложения (GUI-логи вообще не
претендуют на stdout), а исправление ориентации спавна устраняет
параллельный дефект рекурсии автономного моста. Площадь изменений —
два крейта, ноль новых зависимостей, ноль изменений pipe-протокола.
Фильтрация стока (вариант D) отвергнута как ненадёжная; отказ от
автоспавна (C) — как регрессия продукта.

## Последствия

- Позитив: stdout моста гарантированно чист при любом состоянии GUI и
  любом способе запуска; hermes перестаёт терять ответы на «Invalid JSON»;
  рекурсивный спавн автономного моста невозможен; логи GUI в консоли
  сохраняют цвет, в редиректах — читаемы без escape-мусора.
- Нейтрально: логи автоспавненного GUI идут в null — старта GUI видно по
  результату (pipe подхвачен reconnect'ом / isError исчезает), а не по
  тексту лога.
- Негативно: явных минусов нет (поведение уже заявленного контракта
  приводится в соответствие).
- Отложено: файловый/rotating лог GUI (если понадобится послестартовая
  диагностика автоспавна) — отдельное решение, не MCP-требование.

## Валидация

- Юнит-тесты `canvas-mcp`: `spawn_service_command_isolates_stdio`
  (все три хэндла — `Stdio::Null`), `autosprawn_target_prefers_sibling_gui_for_standalone_bridge`
  (мост → сосед GUI; нет соседа → None; единый бинарь → сам себя).
- Прогон реальной сессии (probe): initialize → success; batch → массив;
  tools/call → isError; **каждая строка stdout — валидный JSON**.
- Регресс: `cargo test --workspace` зелёный; FR-034 тесты не тронуты.
