# ADR-0011: WASM-сборка ядра — гейт wasm32-unknown-unknown и исполнение тестов в wasmtime (wasm32-wasip1)

- **Статус:** принято
- **Дата:** 2026-09-18
- **Участники:** владелец (приказ «распланировать сборку wasm и реализовать сборку для повышения автономности в тестировании»; выбор скоупа, таргетов, CI-формата и ветки при уточнении), агент (исследование, дизайн, реализация)
- **Связанные:** `docs/plans/wasm-port.md` (план M8, задача W0), ADR-0008 (пин тулчейна, лицензионная чистота), FR-036; `scripts/wasm_gate.sh`, `.cargo/config.toml`, `.github/workflows/ci.yml`, `crates/canvas-core/src/lib.rs` (тестовая песочница)

## Контекст

Приказ владельца от 2026-09-18: распланировать и реализовать wasm-сборку,
чтобы агент мог **самостоятельно тестировать приложение**. Среда агента —
Linux-контейнер без GUI и без Windows: нативные гейты дают 1012 тестов и
probe моста (ADR-0010), но end-to-end сценарии (окно, named pipe) недоступны
в принципе; при этом существенная часть ценности CanvasDesk — чистое
расчётное ядро (`canvas-core`: модель, JSON Canvas I/O, expr/flow, R-tree,
шаблоны, валидация), для которого среда исполнения не важна.

План веб-порта M8 (`docs/plans/wasm-port.md`, директива владельца от
2026-09-16) уже зафиксировал экспериментальную базу (§2): `canvas-core`,
`canvas-render`, `canvas-widgets` компилируются под `wasm32-unknown-unknown`
без изменений, а задача **W0** требует закрепить это CI-гейтом. Но W0 в
чистом виде — только `cargo check`: компиляция не доказывает, что ядро
**исполняется** под wasm корректно, и не даёт агенту возможности гонять
тесты в wasm-среде. Драйвер «автономность тестирования» требует второго
шага — реального исполнения тестов в wasm-рантайме.

Дополнительные факты, выявленные эмпирически (rustc 1.98.1, wasmtime 48):

- `std::env::temp_dir()` на wasm-таргетах **паникует** (std для
  wasm32-unknown-unknown/wasip1 её не реализует) — падают тесты настроек
  и шаблонов, использующие временные каталоги.
- `std::process::id()` на wasm32-wasip1 тоже **паникует** — интеграционный
  тест бэкапов использовал pid для уникальности каталога.
- `std::fs` на wasip1 полноценно работает через предоткрытые каталоги
  (wasmtime `--dir`), `std::time::SystemTime` работает; потоки — нет.

## Драйверы решения

- **Автономность тестирования:** агент обязан уметь без GUI и Windows
  проверить, что ядро не только собирается, но и исполняется в wasm-рантайме.
- **Защита wasm-совместимости от регресса:** правило плана M8 «ядро
  обязано собираться под wasm» должно проверяться на каждый пуш, а не
  разовым экспериментом от 2026-09-16.
- **Не пересматривать волны M8:** браузерный MVP (W1–W12: web_time, вынос
  App, canvas-web, OPFS) — отдельные задачи; текущий заход не создаёт
  продуктового веб-слоя и не трогает нативные ветки (нулевой регресс).
- **Минимум поверхности:** ноль новых cargo-зависимостей; wasmtime —
  внешний инструмент локального гейта, не зависимость дерева.
- Лицензионная политика ADR-0008: wasmtime (Apache-2.0 WITH LLVM-exception)
  не входит в дерево зависимостей продукта.

## Рассмотренные варианты

### Вариант A: W0 в чистом виде — только CI-check
- Плюсы: дёшево (одна джоба `cargo check --target wasm32-unknown-unknown`).
- Минусы: исполнение не доказано; автономность тестирования не растёт —
  тесты по-прежнему нельзя запустить в wasm-среде; паники `temp_dir`/
  `process::id` остались бы не найденными до волны W1+.
- Вывод: недостаточно — закрывает половину драйверов.

### Вариант B: Гейт + исполнение тестов ядра в wasmtime (wasm32-wasip1)
- Плюсы: стандартный `cargo test --target wasm32-wasip1` исполняет
  существующие 301 тест ядра без единого изменения тестовой логики
  (нужны только wasm-совместимые хелперы песочницы); wasmtime работает
  в контейнере без GUI; таргет wasip1 ортогонален продуктовому
  unknown-unknown и не пересекается с волнами браузерного порта.
- Минусы: харнесс на wasip1 однопоточный и panic=abort (первый провал
  обрывает процесс); в тестовом коде ядра появляется точечное
  `cfg(target_arch)` (см. Решение, п. 3).
- Вывод: принято как ядро решения.

### Вариант C: wasm-bindgen-фасад + wasm-bindgen-test (Node/браузер)
- Плюсы: путь к продуктовому `.wasm`-артефакту (W4/W12 плана M8).
- Минусы: требует wasm-bindgen-cli с пином версии, dev-deps в core,
  Node/браузерную обвязку; для драйвера «исполнять тесты ядра» избыточно;
  смешивает задачу гейта с задачей веб-портa.
- Вывод: отклонено в этом заходе — отложено до W4/W12 плана M8.

### Вариант D: Вынос `mcp_dispatch`/`SceneState` в lib (фрагмент W2) + wasm-тесты диспетчера 26 инструментов
- Плюсы: максимальная автономность — семантика MCP-инструментов
  тестировалась бы end-to-end в wasm.
- Минусы: перемещение ~10k строк `main.rs` — задача M-объёма с риском
  регресса; по плану M8 это самостоятельная задача W2.
- Вывод: отклонено в этом заходе — выполняется отдельной задачей W2.

## Решение

1. **Продуктовый таргет — `wasm32-unknown-unknown`** (по плану M8):
   ступень 1 — `cargo check` ядра (`canvas-core`, `canvas-render`,
   `canvas-widgets`), ступень 2 — артефакт `cargo build -p canvas-core`
   (rlib). Обе ступени в локальном скрипте **`scripts/wasm_gate.sh`**
   (режим `--check` — только ступень 1) и в CI-джобе **`wasm-check`**
   (ubuntu, на каждый пуш — приёмка W0).
2. **Тестовый таргет — `wasm32-wasip1`**: runner **wasmtime** фиксируется
   в `.cargo/config.toml` (активен только при явном `--target`):
   `-S inherit-env`, предоткрытые каталоги `--dir .::/` (корень пакета →
   гостевой `/`, тесты читают `tests/fixtures`) и `--dir /tmp::/tmp`;
   ступень 3 гейта — `RUST_TEST_THREADS=1 cargo test --target
   wasm32-wasip1 -p canvas-core` (301 тест) локально. wasmtime в CI не
   ставится — исполнение в рантайме остаётся локальной ступенью гейта.
3. **wasm-совместимость тестов** без изменения нативного поведения:
   хелпер `test_scratch_root()` в `#[cfg(test)]`-коде `canvas-core`
   (нативно — `std::env::temp_dir()`, под wasm — каталог `.wasi-scratch`
   внутри предоткрытого CWD с уборкой по завершении тестов) и замена
   `std::process::id()` на `SystemTime`-суффикс в интеграционном тесте
   `scene_ops`. Интеграционные тесты не видят `#[cfg(test)]`-хелперы
   крейта, поэтому в `scene_ops.rs` — локальная копия хелпера (осознанное
   дублирование восьми строк). Это **единственное исключение** из правила
   плана M8 §3.1 «без `cfg(target_arch)` в core»: хелпер существует только
   в тестовой компиляции и в продуктовые сборки не попадает.
4. Контракты фиксируются: правило «ядро обязано собираться и исполняться
   под wasm» — в AGENTS («Сборка и тесты»), строка в SPEC §3 (wasm-таргеты),
   статус W0 — в плане M8.

## Обоснование

Вариант B закрывает оба драйвера одним движением: CI-джоба закрепляет
компилируемость ядра (приёмка W0 плана M8), а wasmtime-раннер даёт агенту
реальное исполнение 301 теста расчётного ядра в wasm-среде контейнера —
уровень уверенности, которого не давал ни `cargo check`, ни нативные
гейты. Стоимость минимальна: ноль новых cargo-зависимостей, ~40 строк
тестовых хелперов, один конфиг-файл, один скрипт, одна CI-джоба.
Вариант C смешивает гейт с веб-портом и тянет пин wasm-bindgen-cli;
вариант D — отдельная задача W2 с несопоставимым объёмом; вариант A —
неполный. wasip1 не конкурирует с продуктовым таргетом M8: браузерная
волна остаётся на unknown-unknown, wasip1 — служебный тестовый таргет.

## Последствия

- Позитив: агент и разработчик проверяют ядро под wasm одной командой
  (`scripts/wasm_gate.sh`); wasm-совместимость защищена CI-джобой на
  каждый пуш; найденные и устранённые паники `temp_dir`/`process::id`
  больше не блокируют тесты под wasm; артефакт rlib ядра — измеримая
  база для будущих задач размера бандла (W12).
- Нейтрально: харнесс wasip1 однопоточен и panic=abort — провал обрывает
  процесс, диагностика через `cargo test --test <имя>` по одному бинарю;
  `.wasi-scratch` остаётся в рабочем дереве только после wasm-прогонов
  (в `.gitignore`, уборка тестами).
- Негативно: явных минусов нет — нативное поведение тестов не изменено
  (301/301 до и после).
- Отложено (план M8): W1 — миграция `Instant`→`web_time` (нужна для
  runtime-браузера, не для wasip1); W2 — вынос App/mcp_dispatch в lib;
  W4+ — крейт `canvas-web`, OPFS, wasm-bindgen-фасады; CI-прогон
  wasmtime-ступени, если появится потребность.

## Валидация

- `cargo check --target wasm32-unknown-unknown -p canvas-core -p
  canvas-render -p canvas-widgets` — зелёный (локально 55.8 с, rustc 1.98.1).
- `cargo test --target wasm32-wasip1 -p canvas-core` (wasmtime 48,
  runner из `.cargo/config.toml`) — **301/301**: lib 189 + core_api 4 +
  edgegeom 43 + expr_queueing 32 + json_canvas_io 15 + scene_ops 4 +
  spatial 6 + templates_schema 8.
- Нативный регресс: `cargo test -p canvas-core` — **301/301** (хелпер
  возвращает `temp_dir`, поведение тестов не менялось).
- `scripts/wasm_gate.sh` — все три ступени OK; `--check` — ступень 1 OK.
- CI: джоба `wasm-check` (ubuntu) зелёная на пуш (приёмка W0).
