- **Статус:** в анализе
- **Тип:** CR
- **Приоритет:** важно
- **Владелец:** агент (анализ по запросу владельца)
- **Источник:** запрос владельца (сессия 2026-09-17): проанализировать возможности MCP-сервера, шаблоны и функционал сервиса на предмет возможности ИИ-агента через MCP-сервер собрать примеры архитектур исключительно с «проливанием» значений из нод, без ручного копирования значений

- **Создан:** 2026-09-17
- **Обновлён:** 2026-09-17

## Описание

Концепция владельца: **«один шаблон = один расчёт»**. Шаблон (например, API Gateway) содержит N математически взаимозависимых внутренних характеристик (внутренние расчёты), которые выдают N основных выходных характеристик, важных для других сервисов. ИИ-агент через MCP-сервер должен уметь собирать из таких абстрактных шаблонов архитектуры (пример-эталон — упрощённый MVP Instagram для service design: нагрузка, пропускная способность и т.д.), в которых значения **перетекают по связям** («проливание»), а не копируются агентом вручную из ноды в ноду.

Этот документ фиксирует: (1) что из механики «проливания» уже есть и подтверждено кодом; (2) эталонный сценарий-эталон Instagram MVP с полными цепочками проливания; (3) gap-анализ — чего не хватает в концепции (G1…G8, каждый с ссылками на код); (4) дорожную карту доработок, из которой оформлен FR-029 (первый реализуемый шаг).

## Эталонный сценарий: упрощённый Instagram MVP (service design)

Цель: агент через MCP собирает граф из шаблонов и получает просчитанную цепочку нагрузки — от входных допущений до БД/хранилища, где каждое значение приходит по связи, а не копируется.

### Входные допущения (единственная ручная точка — стартовые параметры ноды «Трафик»)

| Параметр | Значение | Комментарий |
|---|---|---|
| DAU | 1 000 000 | пользователи/день |
| Сессий на пользователя | 4 / день | |
| Запросов на сессию | 12 req | |
| Пиковый множитель | 2.5× | |
| Read:write | 8:2 | доля чтений в трафике фида |
| Cache hit | 70 % | Redis перед БД |
| CDN hit | 60 % | отдача медиа с кромки |

### Состав графа (все ноды — из текущей библиотеки `assets/templates/`)

| Нода | Шаблон (`id`) | Роль в расчёте |
|---|---|---|
| Трафик-профиль | (текстовая Numi-нода) | `dau`, `sess`, `req`, `peak` → `avg_rps = dau*sess*req/86400 s`, `peak_rps = avg_rps*peak` ≈ 1389 rps |
| CDN | `com.canvasdesk.cdn` | hit_rate 60 % → выход `origin_rps = peak_rps*(1-hit)` ≈ 556 rps |
| Балансировщик | `com.canvasdesk.tcp-lb` | делит origin_rps по сервисам |
| API Gateway | `com.canvasdesk.api-gateway` | латентный бюджет: `mm1($rps, 1 req/($latency_budget - $auth_overhead))` |
| Auth Service | `com.canvasdesk.auth-service` | ~15 % трафика ≈ 83 rps |
| Feed/GraphQL | `com.canvasdesk.graphql` | ~60 % трафика ≈ 333 rps |
| Media Service | `com.canvasdesk.grpc-service` | ~25 % трафика ≈ 139 rps |
| Кэш | `com.canvasdesk.cache-redis` | hit 70 % → в БД уходит 30 % чтений |
| БД master | `com.canvasdesk.db-sql-master` | запись + промахи кэша ≈ 80 rps чтений + записи |
| БД replica | `com.canvasdesk.db-sql-replica` | разгрузка чтений |
| Хранилище медиа | `com.canvasdesk.storage-s3` | 139 rps × 2 MB ≈ 278 MB/s |
| Очередь + воркеры | `com.canvasdesk.queue-kafka` + `com.canvasdesk.worker` | асинхронные события фида ≈ 333 rps |

### Цепочки «проливания» (каждая связь = value-ребро с адресацией порта)

```
Трафик.peak_rps ──────────────→ CDN.rps ─────────→ LB.rps
LB.out_gateway (≈556 rps) ────→ Gateway.rps
LB.out_auth (≈83 rps) ────────→ Auth.rps
LB.out_feed (≈333 rps) ───────→ GraphQL.rps
LB.out_media (≈139 rps) ──────→ Media.rps
GraphQL.db_qps (≈80 rps) ─────→ DbMaster.qps
DbMaster.replica_load ────────→ DbReplica.qps
Media.bandwidth (≈278 MB/s) ──→ Storage.put_rate
GraphQL.events (≈333 rps) ────→ Kafka.produce_rate → Worker.consume_rate
```

Сегодня агент может создать все ноды (`template_instantiate`), но **не может** соединить ни одну из этих связей так, чтобы значение реально пролилось: см. G1–G7.

## Gap-анализ: чего не хватает концепции

### G1. Значение не «проливается» внутрь шаблона (критический)

Входящее value-ребро попадает в **позиционный** слот `$1..$N` (`Env.inbound`, `expr.rs:414-458`), а формула шаблона читает только **именованные** `$param` (`flow.rs:270-299`: env = inbound-слоты + `param_map`, но это разные пространства имён). Манифесты написаны как `expr: "mm1($rps, ...)"` — ссылок на `$1` нет, поэтому привязанное значение **молча игнорируется**: нода считает по локальному параметру. Единственные пути сегодня — вручную переписывать формулу инстанса на `mm1($1, ...)` (ломает контракт шаблона) или копировать число в параметр (антипаттерн, который концепция запрещает). Детально: `flow.rs:264-314`, `assets/templates/com.canvasdesk.api-gateway/template.json`.

### G2. Шаблон не декларирует выходные характеристики

Манифест (`templates.rs:88-118`) имеет ровно один `expr` → одно значение ноды. Концепция требует N выходов («выдают N основных характеристик для других сервисов»), а их источник — строки Numi-листа инстанса — не имеют имён и контракта: нет секции `outputs` (имя, единица, формула/строка-источник), нет их в `template_list`, агент не может узнать, ЧТО шаблон отдаёт наружу, кроме финального значения.

### G3. MCP не адресует построчные выходы

`edge_create` (`canvas-mcp/src/lib.rs:259-268`, `main.rs:6282-6302`) принимает только `from/to/fromSide/toSide` — ни `fromLine` (индекс строки, уже существующий в модели `Edge::from_line`), ни `kind` (`value` ставится отдельным вызовом `flow_set_kind` — 2 вызова на связь). `flow_recalc` (`lib.rs:284-289`, `main.rs:6367-6384`) возвращает только узловые значения (`outputs`), не `FlowSolutions.lines` (`flow.rs:231-241`) — агент не видит N внутренних характеристик, хотя ядро их уже считает при каждом ревале.

### G4. Агент не видит существующие связи

Из 22 инструментов нет `edges_list`/`edge_get`: `canvas_info` даёт только счётчик (`main.rs:6010-6014`), `nodes_list`/`node_get` связей не содержат. Агент не может ни прочитать собранный граф, ни проверить свои связи, ни работать с чужим канвасом — сборка вслепую.

### G5. Входы приёмника позиционны и хрупки

Значение падает в `$1..$N` **по порядку рёбер в `canvas.edges`** (`flow.rs:319-350`). При 2+ входах семантика формулы зависит от порядка создания связей; удаление/добавление любого ребра сдвигает слоты и молча меняет смысл формулы. Нет адресации входа (`to_param`/`to_line`) — нельзя сказать «это значение для `rps`, а это для `servers`».

### G6. Нет батч-операций и композитных шаблонов

Сборка эталона — 12+ нод и 10+ связей ≈ 50+ RPC-вызовов (`template_instantiate` + `node_move` × N, `edge_create` + `flow_set_kind` × связи) без транзакционности: ошибка на середине оставляет полусобранный граф (undo-стек есть, но агенту нечем его откатывать одним шагом — `undo`/`redo` инструментов тоже нет). Композитный шаблон «архитектурный паттерн подграфом с граничными портами» отсутствует; FR-020 (custom templates) — статус «выявлено», подграфов с внешними портами нет ни в модели, ни в манифесте.

### G7. Нет валидации совместимости при связывании

Размерность выхода источника против единицы параметра приёмника не сверяется при создании связи: ошибка единиц/перегрузки (`Overload`, `BadArg`) всплывает только при eval, постфактум. Нет инструмента `graph_validate` (висячие входы, ноды без значения, несколько рёбер в один вход, перегрузки ρ ≥ 1 как отчёт, а не исключение). `flow_cycle_check` — единственная структурная проверка.

### G8. Нет эталонного рецепта для агентов

`user-docs/` (7 страниц) и `docs/SPEC.md` описывают инструменты, но нет end-to-end рецепта «агент собирает service-design-архитектуру из шаблонов с проливанием значений»: какие вызовы в каком порядке, как читать параметры шаблона, как проверять результат. Принято решение зафиксировать эталон сценарием ADR-0005 (`docs/adr/adr-0005-instagram-mvp-reference.md`).

## Проверка (критерии готовности концепции)

1. Агент через MCP собирает эталоны целиком: Instagram MVP (ADR-0005) и
   каталог №1–№5 (ADR-0006: system design, защита бюджета, P&L, value chain,
   unit economics) — ноды, связи kind=value, адресованные порты — **без**
   единой ручной правки формул и без копирования чисел между нодами (ручной
   ввод — только стартовые допущения входных нод).
2. `flow_recalc` возвращает и узловые значения, и именованные выходы каждой шаблонной ноды; значения совпадают с эталонными таблицами ADR-0005 и ADR-0006 (± округление).
3. Изменение стартового допущения (например, DAU 1M → 2M в №1, рост 15 %/мес в №2, конверсия ±20 % в №3, активация +5 п.п. в №4, churn 10 % → 25 % в №5) одним вызовом пересчёта обновляет ВЕСЬ downstream без правки связей/формул — включая перегрузочные ошибки (`Overload`) в сценарии №2 без инвестиций.
4. Нарушение контракта (несовместимая единица, два ребра в один `to_param`) диагностируется `graph_validate`/ошибкой `edge_create`, а не молчаливым нулём.
5. Автогейты зелёные (`cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace`).
