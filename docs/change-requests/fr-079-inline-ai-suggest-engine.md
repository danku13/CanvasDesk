# FR-079: Inline AI-подсказки нод — гибрид lex+Laya с fine-tune (продуктовая интеграция PoC)

- **Статус:** в реализации (S1–S3 готовы: ядро, транспорт L1, интеграция в приложение; S0-метрики — в составе S3; далее S4 fine-tune — стрим владельца, S5 выкатка)
- **Тип:** FR
- **Приоритет:** важно (закрывает north-star гипотезы inline-автодополнения; решение владельца 2026-09-28: «гибрид с Laya имеет смысл, требуется её fine-tune»)
- **Владелец:** агент-сессия (Super Z), план согласует владелец
- **Источник:** решение владельца по итогам трёх волн PoC Laya — `docs/dev-researches/laya-poc-wave3-results.md` §9 (вердикт: к green только через H8 fine-tune + домен-детектор)
- **Связанные задачи:** `docs/dev-researches/inline-ai-autocomplete-hypothesis.md` (ред. 2.1, §8–14), `laya-poc-report.md` §12 (blueprint встраивания), `laya-poc-wave3-hypotheses.md` (H8), FR-021 (попап подсказок), FR-018/019/020 (шаблоны), FR-014 (value-flow), ADR-0007

## Описание

По канвасу, на котором пользователь строит расчётную модель, продукт в момент
редактирования/создания ноды предлагает релевантные шаблоны из каталога
(62 builtin + custom): ИИ-строки в существующем попапе подсказок FR-021 и
карточки «следующие ноды» у свежесозданной шаблонной ноды. Решатель — гибрид
`score-fusion(lex v1, laya-mm; α=0.85, min-max)`, доказанный PoC (три волны,
226+75 фикстур): p@1 0.468 на замороженном test против 0.319 у чистой лексики;
на расчётных доменах с домен-детектором ожидание ≈ 0.47. Zero-shot Laya до
продуктового гейта green доводится fine-tune'ом decision-head (H8, авторский
ноутбук Kaggle 2×T4: референс 0.362 → 0.766 на домене авторов; наш вход
0.309 пул). Фича полностью офлайн: L1 — sidecar-процесс `laya-serve`
(localhost), без сетевых вызовов в хосте; web-версия — деградация до lex.

Выполнение по правилу PoC-отчёта §12: «дёшево выпилить — дёшево дорабатывать» —
новый крейт `canvas-suggest` за feature-флагом, ноль изменений ядра, откат =
удаление крейта + флага + конфиг-ключа.

## Анализ (что существует и чего не хватает)

Готово (см. гипотеза §3.1): фаннел триггеров (`update_hints()` — единая точка
ввода/каретки), попап FR-021 (`HintItem`/`HintContext`/`sync`), паттерн воркера
(`canvas-scene/src/worker.rs`: поток + double buffer + `EventLoopProxy`),
прецедент управления сторонним процессом (`canvasdesk mcp`: spawn/health/
таймауты), каталог шаблонов (`templates.rs` + манифесты), вставка
(`instantiate_template_at`, `graph_apply`).

Отсутствует: (а) движок — сериализатор контекста, lex-ранжирование, fusion,
калибровка, show-гейт, домен-детектор существуют только в Python-harness PoC;
(б) транспорт к sidecar (HTTP-клиент, lifecycle, smoke); (в) асинхронный
воркер в приложении; (г) UI-представление ИИ-подсказок; (д) метрический слой;
(е) пайплайн fine-tune (экспорт train/dev, hard negatives, возврат весов).

## Требуемые изменения (стадии и гейты)

Детальный технический план — `docs/plans/fr-079-suggest-engine.md`
(архитектура, контракты, конфиг, оценка трудоёмкости). Суммарно:

| Стадия | Содержание | Выходной гейт |
|---|---|---|
| S0. Метрический слой | события suggest_*, jsonl-журнал, HUD латентностей (dev, F3) | события пишутся, L0 не затронут |
| S1. `canvas-suggest` (чистое ядро) | типы, сериализатор контекста v0 (порт `serialize.py`), LexEngine v1/v2, fusion α, Platt, show-гейт, домен-детектор; golden-тесты на фикстурах PoC | lex p@1 ≥ 0.38 pool (CI-регресс); fusion ≥ 0.46 (офлайн-пробы); wasm-check |
| S2. Транспорт L1 | HTTP-клиент `/v1/systemone`, lifecycle sidecar (spawn/health/idle-shutdown), smoke-фикстура, деградация → lex | smoke-гейт; cold start < 60 с; p50 инференса на стенде |
| S3. Интеграция в приложение | SuggestWorker + запросы из `update_hints` + ИИ-строки + карточки С3 + настройки + i18n | L2-браузерный стенд (lex-режим); ручная приёмка владельца |
| S4. Fine-tune H8 | экспорт train/dev + hard negatives → Kaggle 2×T4 → чекпойнт (sha256) → Platt re-fit → перегейт | p@1 ≥ 0.60 green / 0.50–0.60 yellow; решение о конфиге по гейту |
| S5. Выкатка | дефолт по гейту, user-docs, онбординг-вопрос, приёмка | acceptance ≥ 25% (2 нед владельца); p50 < 500 мс CPU |

S4 стартует параллельно S2–S3 (подготовка данных не блокирует продукт):
продукт при этом работает на zero-shot mm с ожиданием p@1 ≈ 0.47 на
расчётных доменах; fine-tuned-чекпойнт подключается заменой конфига
(протокол тот же, код не меняется).

## Продуктовые решения, выносимые на ревью (владелец)

1. **Дефолт OFF до гейта S4/S5** — предложение: после S3 фича доступна
   в настройках (opt-in, lex по умолчанию), полный дефолт ON — только после
   приёмки S5. Альтернатива: ON с lex сразу после S3.
2. **C2/C5 вне v1** — согласовать (см. таблицу скоупа).
3. **Web-паритет**: в web только lex-режим (sidecar в браузере недоступен);
   серверный L1 — отдельное решение позже.
4. **Догрузка весов mm (~650 МБ) при первом включении L1** — явное согласие
   пользователя в настройках (размер + новая компонента).
5. **Телеметрия качества** — журнал локальный, opt-out; анонимизированная
   отправка (если понадобится для S5+) — отдельное решение.

## Проверка (Verification)

- **CI-регресс золотом PoC**: фикстуры eval-сета (source_a/b + расширенный
  test) кладутся в `canvas-suggest/tests/fixtures/` (JSONL, детерминированные);
  тесты: LexEngine p@1 ≥ 0.38 pool / ≥ 0.319 test; fusion на приложенных
  mm-пробах ≥ 0.46 test-old; show-гейт acc ≥ 0.90; домен-детектор — 33
  framework-фикстуры → Verdict::Framework.
- **Пороги из гейта PoC сохраняются**: p95 инференса ≤ 500–800 мс (yellow),
  RSS sidecar ≤ 2.5 ГБ — S2-гейт на стенде; latencies HUD в dev-режиме.
- **Приёмка продукта** (S3, S5 — владелец): сценарии C1/C3/C4 вручную;
  acceptance ≥ 25% по suggest-log за 2 недели; edits-after-accept контроль
  (гипотеза §15: атрибуция авторства).
- **Выпиливаемость**: сборка без feature `l1-laya` и без крейта в
  workspace-members компилируется и проходит тесты — фиксируется тестом
  конфигурации сборки в CI (или ручной чек-лист в RELEASE).
- Стандартные гейты проекта: `cargo test --workspace`, clippy -D warnings,
  fmt, `scripts/wasm_gate.sh --check` (чистая часть), L2-стенд для UI-правок.
