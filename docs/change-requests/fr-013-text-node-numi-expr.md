## Описание (What)

Архитектор/техлид/системный аналитик рисует на канвасе ландшафт сервиса: ноды =
компоненты (gateway, queue, replica, DB), рёбра = поток запросов. В каждой ноде он
пишет параметры «человеческим языком» в стиле Numi — например:

```
rps = 1000
latency = 50 ms
replicas = 3
cpu_per_request = 0.5 ms × 1000 rps / 3 replicas = 166.7 ms-equivalent
```

CanvasDesk парсит формулу, считает результат и показывает его отдельной строкой
ниже текста ноды. В v1 (FR-013) вычисления **локальные** — формула в ноде видит
только свои переменные; поток значений между нодами приходит в FR-014. Цель FR-013 —
дать базовый «движок формул» и точку сериализации `canvasdesk.expr` в `.canvas`,
которую FR-014..017 будут расширять.

## Анализ (Root Cause)

В текущей реализации вычислительной ноды нет. Точки встраивания:

- **`Node.canvasdesk`** (`crates/canvas-core/src/model.rs:150`) — `Option<CanvasdeskExt>`,
  где `CanvasdeskExt` (`model.rs:113-119`) — структура только для виджет-ноды
  (`widget_id`, `props`). Использовать её же для calc-ноды — ломает семантику.
  Решение: хранить `expr` в `Node.extra` (round-trip через `extra: Map<String, Value>`,
  `model.rs:152-153`) под ключом `canvasdesk: { expr: "..." }` — Obsidian и иные
  сторонние редакторы сохранят неизвестное поле без потерь. В runtime — accessor
  `Node::expr() -> Option<&str>`, читающий `extra["canvasdesk"]["expr"]`. Образец
  работы с `extra` — `json_canvas_io.rs` (тесты round-trip).
- **Парсера/eval формул нет.** Новый модуль `crates/canvas-core/src/expr.rs`
  (или `expr/mod.rs` с подмодулями) — Numi-base грамматика:
  - литералы: числа (`5`, `3.14`, `1k`, `2M`), единицы (`ms`, `sec`, `min`,
    `MB`, `GB`, `req/s`, `rps`, `$`, `%`),
  - операторы: `+ - * /`,
  - переменные: `name = expr`,
  - функции v1: `sum, avg, max, min, percentile(p, …)` (доменные функции
    `mm1, mmc, littles_law, utilization` — FR-015),
  - результат: `Value { num: f64, unit: Unit }` (Unit — композитный
    `{base: Vec<Dimension>, exp: i8}` для `ms·req/s` и т.п.).
- **Рендер результата.** `crates/canvas-render/src/cards.rs` — для `NodeKind::Text`
  рендерит текст; нового блока `result` нет. Добавить инстанс «строка результата»
  ниже текста (или в шапке) — по образцу подсветки `brokenLink` (`cards.rs`).
- **Редактирование.** `begin_editing` (`main.rs:1058`) открывает инлайн-редактор
  (glyphon + cosmic-text) для текста ноды. Для calc-ноды — отдельный input для
  формулы (или смешанный редактор с поддержкой блока `= ...`).
- **MCP.** `node_edit` (FR-005, `mcp_dispatch` `main.rs:2872+`) — добавить ветку
  `expr` (string/null), как уже сделано для `label`/`color`.
- **Undo.** `push_undo`/`undo` (`main.rs:311-330`) — снимок `Canvas` целиком;
  commit формулы = один шаг, как у `node_set_color`. Live-пересчёт downstream
  (FR-014) — НЕ undo-able, только исходная правка.

## Требуемые изменения (Changes)

1. **`canvas-core/src/model.rs`** — accessor для `expr` без новой struct:
   - `impl Node { pub fn expr(&self) -> Option<&str> }` — чтение из
     `self.extra.get("canvasdesk")?.get("expr")?.as_str()`.
   - `pub fn set_expr(&mut self, expr: Option<String>)` — мутация `extra` с
     удалением ключа при `None` (round-trip чистый: пустого поля нет).
   - Runtime-only поле результата — НЕ в `.canvas`, в `SceneState`:
     `expr_results: HashMap<String /*node_id*/, Value>` (`main.rs:193`, SceneState).

2. **`canvas-core/src/expr.rs`** — новый модуль (чистый Rust, без I/O):
   - `pub struct Value { num: OrderedFloat<f64>, unit: Unit }`
   - `pub enum Unit { Scalar, Composite(Vec<(Dimension, i8)>) }` (`Dimension`:
     `Time, Rate, Count, Bytes, Money, Percent, Custom(String)`).
   - `pub fn parse(input: &str) -> Result<Expr, ParseError>`
   - `pub fn eval(expr: &Expr, env: &Env) -> Result<Value, EvalError>` (`Env`:
     карта переменных; для FR-013 — только локальные, для FR-014 — `$in`/`$1`/`$2`).
   - Парсер: `pest` (грамматика в `expr.pest`) или `chumsky` — решение на этапе
     реализации; критерий — <200 строк грамматики, нулевые внешние side-эффекты.

3. **`canvas-app/src/main.rs`** — `begin_editing` (`1058`) + `mcp_dispatch`
   (`2872+`):
   - При commit формулы → `expr::parse` + `expr::eval` → сохранить `Value` в
     `SceneState.expr_results[node_id]`; `mark_dirty()` (`277`) для автосейва
     `canvasdesk.expr`.
   - Один undo-шаг: `push_undo` перед изменением, как у `node_set_color`
     (паттерн FR-006).
   - MCP `node_edit`: поле `expr` (STR/null); null — сброс, валидация: при ошибке
     парсинга — `isError: true` с диагностикой, нода не меняется.

4. **`canvas-render/src/cards.rs`** — для `NodeKind::Text` с непустым `expr`:
   - Новый инстанс «строка результата» под текстом (или в футере ноды) —
     формат `{num} {unit}` (`1000 ms·req/s`).
   - LOD `≥ 0.6` — полный текст; `< 0.6` — индикатор `=` в углу (образец:
     иконка `brokenLink`).
   - Ошибка парсинга — строка с красным акцентом + тултип.

5. **`canvas-mcp/src/lib.rs`** — расширить `ToolSpec node_edit` (FR-005) полем
   `expr` (STR/null). Описание: «Numi-style формула; результат рендерится под
   текстом ноды. null — сброс calc-режима».

6. **`canvas-core/src/expr/units.rs`** (опционально как подмодуль) — таблица
   единиц и conversions: `1 sec = 1000 ms`, `1 GB = 1024 MB`, `1 min = 60 sec`.
   Без этого — единицы «нескладываемые», но v1 можно с минимальным набором.

## Архитектура тестируемости (инварианты FR-013)

Чтобы каждое последующее FR (014–017) можно было тестировать независимо,
FR-013 фиксирует **4 инварианта**:

1. **Чистый парсер.** `expr::parse` — `(input: &str) -> Result<Expr, ParseError>`,
   без I/O, без глобального состояния. Тестируется unit-тестами на литералы,
   операторы, единицы, переменные, функции.
2. **Чистый eval.** `expr::eval(expr, env)` — `(Expr, &Env) -> Result<Value, EvalError>`,
   без side-эффектов. Тестируется свойствами: `eval(parse("5 ms + 10 ms")) == 15 ms`,
   `eval(parse("1k rps")) == 1000 rps`.
3. **Сериализация.** `Node::expr()` / `Node::set_expr()` — round-trip через
   `extra`. Тест `json_canvas_io.rs` дополняется: создание text-ноды с
   `canvasdesk.expr` → сохранить → прочитать → поле сохранено.
4. **Runtime-результат не в `.canvas`.** `expr_results` в `SceneState` —
   вычисляется из `expr` при загрузке/правке, не сериализуется (источник
   истины — формула, не результат). Это позволяет FR-014 (поток значений)
   и FR-017 (what-if) не плодить дублирующие поля в `.canvas`.

## Проверка (Verification)

### Юнит-тесты (обязательные, зелёные до перевода FR-013 в `выполнено`)

- `expr::parse("5") == Ok(Expr::Num(5.0, Unit::Scalar))`
- `expr::parse("5 ms × 200 req/s") == Ok(...)` (композитный unit `ms·req/s`).
- `expr::eval(parse("1 sec + 500 ms"), Env::empty()) == Ok(Value { 1.5 sec })`.
- `expr::eval(parse("avg(10 ms, 20 ms, 30 ms)"), …) == Ok(20 ms)`.
- `expr::parse("= invalid @#$")` → `Err(ParseError { pos, msg })`.
- `expr::parse("5 ms + 3 rps")` → `Err(EvalError::UnitMismatch)` (единицы не
  складываются).
- `Node::set_expr(Some("5 ms"))` → `Node::expr() == Some("5 ms")`; сериализация
  в `.canvas` и чтение обратно — поле сохранено; `Node::set_expr(None)` →
  поле отсутствует в JSON (round-trip чистый).

### Интеграционные тесты

- `crates/canvas-core/tests/json_canvas_io.rs` — fixture `text_with_expr.canvas`:
  text-нода с `canvasdesk.expr = "5 ms × 200 req/s"`; round-trip через
  `serde_json::to_string` → `from_str` — поле сохранено, Obsidian-формат валиден
  (extra сохраняется, `model.rs:152-153`).
- `crates/canvas-app/tests/integration_expr.rs` — создание text-ноды с `expr`
  через MCP `node_edit { id, expr: "5 ms" }` → `expr_results` обновлён,
  `mark_dirty` сработал, undo восстанавливает пустой `expr`.

### Ручная приёмка

- ПКМ по text-ноде (меню FR-009) → пункт «Режим вычислений» → появляется инпут
  формулы (или mixed-редактор с поддержкой блока `= ...`).
- Пишем `5 ms × 200 req/s` → под текстом ноды — строка `1000 ms·req/s`.
- Пишем `avg(10 ms, 20 ms, 30 ms)` → `20 ms`.
- Пишем синтаксически некорректное (`5 ms +`) → красная строка с тултипом
  ошибки, `expr_results` не меняется.
- Закрытие/открытие канваса — формула и результат сохранены (через
  `.canvas` + пересчёт при загрузке).
- MCP: вызов `node_edit { id, expr: "1k rps" }` из внешнего AI-клиента →
  результат `1000 rps` виден на канвасе.
- Undo (`Ctrl+Z`) после правки формулы — формула возвращается к предыдущему
  значению; redo — восстанавливает.

## Открытые вопросы дизайна

> **Решения при реализации (2026-09-15):**
>
> - **Редактор** — выбран СМЕШАННЫЙ вариант: строки текста ноды,
>   начинающиеся с `=`, — утверждения формулы (commit выводит их в
>   `canvasdesk.expr` и пересчитывает результат). Инлайн-редактор не
>   сломан, новый UI-компонент не нужен.
> - **Парсер** — рукописный рекурсивный спуск (лексер с окном на один
>   токен), без внешних зависимостей (`pest`/`chumsky` не добавлялись);
>   критерий coverage выполнен юнит-тестами expr.rs (22 теста).
> - **Хранение** — документ предлагал `extra["canvasdesk"]["expr"]`, но
>   ключ `canvasdesk` в `extra` коллизирует с типизированным полем
>   `Node.canvasdesk: Option<CanvasdeskExt>` (serde требует `widgetId`).
>   Реализация: `CanvasdeskExt` расширен опциональным полем `expr`
>   (`widget_id`/`props` стали Option/default — объект один на виджет-
>   и calc-ноды). Формат JSON прежний: `canvasdesk: { expr: "..." }`.
> - **Композитные единицы** — упрощённый вывод реализован (`1000 ms·req/s`):
>   положительные степени через `·`, отрицательные через `/` (`B/s`),
>   нормализация `Count/Time → Rate` (`50 req/s`).
> - **Кириллические единицы** — отложены до v2 (как и планировалось).

- **Смешанный редактор vs отдельный input.** Первый — единый редактор, где
  блок после `=` трактуется как формула; второй — отдельное поле под
  текстом. Решение на этапе прототипа; критерий — не ломает существующий
  редактор текста (`begin_editing`, `main.rs:1058`).
- **Парсер `pest` vs `chumsky`.** `pest` — декларативная грамматика в `.pest`,
  проще тестировать; `chumsky` — больше контроля над ошибками. Решение на
  этапе реализации; критерий — coverage грамматики unit-тестами ≥ 90%.
- **Композитные единицы (`ms·req/s`).** В Numi — конкатенация размерностей.
  v1 — поддержать, но выводить в упрощённом виде (`1000 ms·req/s`, не
  `1000 ms·req·s⁻¹`).
- **Кириллические единицы.** Numi — латиница; в CanvasDesk — сохранить
  латиницу (`ms`, `rps`, `req/s`), но позволить синонимы (`мс`, `запр/с`)
  — open question, отложить до v2.

## Правка 1 — обратная связь владельца (авто-детект, правое выравнивание)

Проверка владельцем показала: формула «не работает, ничего дополнительно
не отображается». Диагностика (headless-рендер пиксель-тестом) показала:
конвейер рендера строки результата исправен; причина — контракт «формула
только в строках с префиксом `=`»: выражение, набранное Numi-стилем
(`1000 rps`, `2+2`) без префикса, формулой не признавалось вовсе.

Исправления (коммит `fix(app,render): FR-013 правка`):

- **Авто-детект формулы (Numi-семантика).** Если явной формулы
  (`canvasdesk.expr`) нет, последняя непустая строка текста, содержащая
  цифру и разбирающаяся как выражение (`auto_formula_line`), считается
  формулой. **Тихий режим:** любые ошибки (синтаксис, вычисление) строку
  результата не создают — проза («Встреча в 15:00») не краснеет.
  Авто-формула — runtime-вывод: в `canvasdesk.expr` не материализуется
  (инвариант 4 не нарушается), единственный источник истины для рендера —
  `expr_results`. Префиксный путь (`= …`, ошибки показываются красным)
  сохранён без изменений и имеет приоритет.
- **Правое выравнивание результата.** Строка результата в футере карточки
  выравнивается по ПРАВОМУ краю ноды: ширина зашейпленной строки
  замеряется из layout-рана (`Run.line_w`), `TextArea.left =
  правая_граница_футера − ширина`. Проверено пиксель-тестом
  (`expr_result_smoke.rs`): глифы у правого края, левая половина футера
  чиста.
- `fit_note_size` и `recompute_all_expr` используют общий предикат
  `has_formula_candidate` (явная формула ИЛИ авто-детект) — футер
  резервируется и при наборе без префикса, авто-ноды пересчитываются при
  загрузке/undo.

## Правка 2 — обратная связь владельца (паника редактора, результаты Numi-стиля)

Два сообщения владельца: (1) паника при удалении всех строк ноды; (2) «выводи
результат отдельно, в стиле numi, для каждой строки».

### Паника cosmic-text (editor.rs:303, index out of bounds)

Причина: `Buffer::set_rich_text` (используется `refresh_styles` при каждом
изменении текста) дробит текст через `BidiParagraphs` — параграфы UAX#9 — и
ТЕРЯЕТ хвостовую пустую строку: «текст\n» хранится одной линией, тогда как
Editor и `buffer_plain()` держат две («текст», «»). Буфер сжимался, а курсор
и выделение ссылались на несуществующую строку; следующая правка
(`delete_range`) читала `buffer.lines[end.line]` за границей. Сценарий
владельца: стирание второй строки многострочной ноды оставляет «раз\n» →
схлопывание → курсор (1,0) устаревает → следующий Backspace паникует
(«len is 1 but the index is 1»).

Исправление (`edit.rs`): `pad_trailing_lines` после каждого `set_rich_text`
восстанавливает число линий буфера до `plain.split('\n').count()` (round-trip
buffer_plain ↔ plain), плюс `clamp_cursor_to_buffer` — страховка курсора и
выделения (линия ≤ последней, индекс ≤ длины строки). Регресс-тесты:
`delete_all_lines_no_panic`, `trailing_newline_edits_no_panic`.

### Построчные результаты Numi-стиля

Результат формулы теперь показывается для КАЖДОЙ формульной строки — у
правого края ЕЁ строки (Numi), а не одной строкой в футере:

- **canvas-core `expr::eval_lines(source)`** — построчное вычисление текста
  как одного сценария с общим окружением: переменные, объявленные выше,
  видны ниже; присваивание (`rps = 1000`) связывает переменную и возвращает
  присвоенное значение; внутри код-фенсов формулы не вычисляются. Строка с
  префиксом `=` — явная формула (ошибки видны); чистая строка-выражение —
  авто-формула (тихий режим: ошибки строки не создают, проза не краснеет).
- **`SceneState.expr_line_results`** — второй runtime-кэш
  (`HashMap<id, Vec<Option<ExprOutcome>>>`, инвариант 4). Построчные
  результаты вытесняют программный итог; если построчных нет, а
  `canvasdesk.expr` задан (MCP `node_edit { expr }`) — программный итог
  в футере карточки (прежний рендер сохранён как фолбэк).
- **Рендер** (`text.rs`): формульная строка — самостоятельный блок тела
  (`body_items` сегментирует текст, `BodyBlock.source_line`); результат
  строки шейпится в кэше ноды и рисуется правым краем на ряду своего блока
  (вертикальное центрирование, успех — акцентный, ошибка — красный).
  Пиксель-тест `expr_line_results_draw_on_own_rows`. Кэш-ключ `results`
  покрывает и программный итог, и построчные результаты.
- `fit_note_size` резервирует футер только для программного итога —
  построчные результаты места не требуют (ложатся на свои строки).

## Правка 3 — обратная связь владельца (Numi-паритет листа расчёта)

Фидбек: из листа результаты выдают только чистые выражения (`123 + 23`,
`1k rps × 50 ms`); присваивания, ссылки на переменные, `x`-умножение и `*` —
нет. Диагностика скратч-тестом `eval_lines` выявила три независимых корня:

1. **Хвостовое присваивание не разбирается** — `123 + 5123 = a`:
   после полного утверждения токен `=` давал «неожиданный оператор».
2. **Форма «в обе стороны»** — `b = 235 + 2323 = b`: то же ограничение;
   каскадом ломало и `c = a + b` (b не был определён).
3. **Кириллица в именах** — лексер принимал только ASCII-буквы:
   `х = 200`, набранное в русской раскладке, давало «неподдерживаемый
   символ» — ссылки (`200 + х`, `с = а + b`) и `х`-умножение молча не
   выдавали результат (авто-строки тихи).

Исправления (`canvas-core/src/expr.rs`):

- **Хвостовое присваивание** (`expr = name`): токен `=` на верхнем уровне
  после полного утверждения связывает имя с его результатом (Numi «сохранить
  результат»); имя обязано завершать утверждение (`2 = 3 + 1` — тихая
  ошибка); повтор то же имени (`b = 235 + 2323 = b`) игнорируется.
- **Unicode-идентификаторы**: сканирование по чарам (`is_alphanumeric`) —
  имена переменных латиницей и кириллицей (`х = 200`, `с = а + х`); юниты
  по-прежнему только из таблицы (кириллические синонимы юнитов — v2).
- **`x`/`х` — умножение между операндами** (Numi): `35 x 20` = 700,
  `25 + 35 х 20` = 725, `latency х 3`, `(2+3) x 4`, `$5 x 3`, `5 ms x 3`;
  в конце строки, после оператора и перед именем — переменная (`200 + x`,
  `latency х y`). Реализовано в лексере (флаг `operand_ended` + lookahead
  `operand_starts_ahead`: цифра/`.`/`(`/`$`).
- **Доп. знаки умножения**: `⋅` (U+22C5), `✕` (U+2715), `⨯` (U+2A2F) —
  к уже поддержанным `*`/`×`/`·`.

Тесты: 4 новых (`trailing_assignment_saves_result`,
`x_between_operands_is_multiplication`, `cyrillic_variable_names`,
`eval_lines_owner_sheet` — точный лист владельца построчно) — всего 703,
clippy 0. Рендер/app без изменений: строки получили результаты —
существующий построчный конвейер их показывает.

## Правка 4 — обратная связь владельца (живые результаты, бейдж ошибки, тултип)

Фидбек: листы с присваиваниями и ссылками «так ничего и не показывают и не
выдают»; требования — (1) результат у КАЖДОЙ строки, включая чистые
присваивания, (2) при ошибке расчёта — наглядный индикатор с тултипом,
показывающим ошибку при наведении. Диагностика: ядро правки 3 вычисляло
листы владельца верно (тест `eval_lines_owner_sheet` зелёный), но в
конвейере оставались две дыры восприятия — пока нода редактируется, тело
рисует EditingSession и построчные результаты НЕ эмитились вовсе
(`body_text` пуст → кэш без блоков → эмиссия мимо); ошибки авто-строк были
всегда немы (пользователь не видел, ЧТО сломалось).

Исправления:

- **Живые результаты по ходу набора (Numi)** (`canvas-app/main.rs`,
  `canvas-render/{renderer,text}.rs`): приложение на каждый кадр считает
  `expr::eval_lines` из текста СЕССИИ и передаёт через
  `SceneView.expr_editing_results` → `TitleFrame.editing_line_results`;
  рендер привязывает результат к ряду буфера редактора через
  `LayoutRun.line_i` → первый визуальный ряд (`line_top`/`line_height`,
  перенос длинной строки игнорируется), правый край — правая граница
  строки ноды. Успешные строки — акцентный цвет, ошибки — красный бейдж.
- **Индикатор ошибки — красный бейдж «!»** (`text.rs`): и кэшированные, и
  живые строки с ошибкой рисуют компактный красный `!` у правого края
  СВОЕЙ строки вместо длинного текста диагностики (он не влезал в строку
  ноды и обрезался). Полный текст ошибки переносится в тултип. Футер
  программного итога (MCP-expr) не изменён.
- **Тултип ошибки при наведении** (`text.rs` + `canvas-app/main.rs`):
  prepare_titles собирает расширенные зоны наведения бейджей
  (`LineErrorHit { rect [x,y,w,h] в логических px, message }`, паддинг
  ±10 лог. px — глиф «!» слишком мал для точного попадания); приложение
  вычитывает `Renderer::line_error_hits()` после кадра, hit-тестит курсор
  и рисует screen-space тултип у курсора (паттерн тултипа битой ссылки
  T10, ширина TOOLTIP_WIDTH). Отставание зон на один кадр незаметно.
- **Видимость ошибок авто-строк (правила «заслуженности»)** (`expr.rs`):
  Numi-принцип «проза не краснеет» сохранён, но сломанный расчёт — не
  проза. Авто-строка показывает ошибку вычисления: несовместимость единиц
  (`5 ms + 3 rps`), деление на ноль, битый вызов — всегда (строка
  вычислилась как чистая арифметика); `UnknownVariable` — только если имя
  ОБЪЯВЛЕНО строкой выше (даже ошибочной: скан `имя = …` / `… = имя` в
  `scan_declared_names`). Ошибка парсинга видна у строк, ПОХОЖИХ на
  присваивание (`assignment_shaped`: `x = (2+`), — пользователь явно
  описал связывание. Примеры: `x = 1 sec + 2 req` → обе строки с ошибкой;
  `- 5 яблок` → тихо (слово не объявлено); «Встреча в 15:00» → тихо.
- Присваивания показывают значение (уже в правке 2/3: `eval_statement`
  возвращает присвоенное) — требование владельца «результат даже там, где
  это просто присвоение» выполняется: `x = 200` → `200`.

Тесты: 6 новых (core `auto_error_visibility_rules`; app
`per_line_results_owner_sheets_v4` — точные листы владельца из фидбека,

## Правка 5 — обратная связь владельца (КОРЕНЬ: экранирование «=» в канонике)

Фидбек: «выражения с присвоением переменным и математические выражения
с переменными так и не выводятся как результаты, ошибки тоже не
выводятся» — примеры: `x = 200` / `c = a + b` / `200 + x` и
`a=25+35x20` / `b = 2` / `a+b`. Все предыдущие правки (2–4) не находили
причину, потому что ядро и конвейер были исправны на чистом тексте;
компонентный разрыв был между ними — в markdown-канонике.

**Корневая причина** (найдена интеграционным тестом РЕАЛЬНОГО флоу:
`EditingSession::new` + `insert_text` + `session.text()` — тот же вызов,
что в RedrawRequested/commit): `markdown::emit` экранировал КАЖДОЕ
одиночное `=` как `\=` (защита литеральных пар `==` подсветки в
диалекте CanvasDesk), поэтому канонический текст заметки, сохраняемый в
модель, содержал `x \= 200`. Далее каскад: `expr::parse` падал на
«\» (неподдерживаемый символ) → авто-строка тиха; переменные не
объявлялись (`scan_declared_names` не видел имя) → ссылки на них тоже
молчали; ошибка парсинга не показывалась (строка не распознавалась как
`assignment_shaped`). Итог — лист владельца молчал ЦЕЛИКОМ и в
редакторе, и на карточке, а простые `123 + 23` (без «=») работали —
точное совпадение со всеми фидбеками от правки 2. MCP-тесты этого не
ловили: `node_update_text` кладёт в модель чистый текст, минуя
markdown-канонику.

Исправления:

- **Парное экранирование** (`canvas-render/markdown.rs`): `=` и `~`
  экранируются ТОЛЬКО ПАРАМИ целиком (`==` → `\=\=`, `~~` →
  `\~\~`) — маркеры-одиночки не существуют в этом диалекте, значит
  одиночные `=` (`x = 200`) защищать не нужно. Экранирование `*`
  (одиночный маркер italic) сохранено всегда. Маска строится по ВСЕМУ
  plain (`escape_mask`), а не по чанку: пара, разрезанная границей
  спанов, экранируется в обоих чанках. Round-trip пар точен; каноника
  подсветки/strike не пострадала.
- **Совместимость со старыми заметками** (`canvas-core/expr.rs`):
  `eval_lines` снимает `\=`-экранирование перед расчётом (одна строка,
  единая точка для live/commit/MCP/загрузки) — заметки прежних сборок
  с `x \= 200` в модели оживают БЕЗ пересохранения.
- **Видимая ошибка необъявленной переменной в присваивании**
  (`canvas-core/expr.rs`): `auto_error_visible` показывает
  `UnknownVariable`, если строка сама — присваивание (`c = a + b` без
  объявленных `a`) — пользователь явно описал связывание, это расчёт,
  а не проза (требование «ошибки тоже не выводятся»). Проза и
  не-присваивания (`- 5 яблок`, `2 + слово`) молчат как раньше.
- **Слитное умножение** (`canvas-core/expr.rs`, лексер): `25+35x20`
  без пробелов (и кириллической `х`) — `x` после операнда с цифрой
  СРАЗУ за ним — знак умножения (`35x20` → 700); раньше слитный
  идентификатор `x20` съедался целиком → «неизвестная переменная: x20».
- **Регресс реального флоу** (`canvas-app/main.rs`):
  `live_typing_flow_owner_sheets` — сессия редактирования + ввод +
  `session.text()` → живые результаты → commit → `recompute_expr`; точные
  листы владельца (латиница и кириллица), включая заметку в старой
  канонике `\=`. Закрывает компонентный разрыв, из-за которого правки
  2–4 казались зелёными.

Примечание для владельца: заметки, набранные прежними сборками,
отображаются на карточке с бэкслешами (`x \= 200`) до первого
пересохранения (это предсуществующее поведение GFM-карточки для
экранированных символов); расчёты при этом уже работают (eval снимает
экранирование), а после пересохранения текст карточки станет чистым.

Тесты: +6 (markdown: `emit_keeps_single_equals_for_expr_lines`,
`emit_escapes_literal_pairs_whole`, `emit_escapes_pair_split_across_spans`,
обновлены `emit_escapes_literal_markers`/`emit_escapes_literal_tilde`;
core: `eval_lines_escaped_equals_from_canonical_text`,
`eval_lines_unknown_variable_visible_on_assignment`, слитные случаи в
`x_between_operands_is_multiplication`; app: `live_typing_flow_owner_sheets`)
— всего 715, clippy 0, fmt своих строк чист.
