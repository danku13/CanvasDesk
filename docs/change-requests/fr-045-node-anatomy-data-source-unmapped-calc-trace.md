## Описание (What)

Четыре вводных владельца о прозрачности данных внутри нод + одно нотационное
требование из фидбэка по прототипу. Все проверены на интерактивном прототипе
(решения закреплены в §Решения). Постановка — расширение контракта анатомии
ноды PRD-0004 и его LOD-логики.

1. **R-1. Текстовая информация в нодах.** Нода должна нести текст-описание /
   контекст (историческая вводная, назначение), который виден в теле ноды и
   не вмешивается в расчёт.
2. **R-2. Нода «Входные данные».** Новый тип ноды-источника данных с
   индикатором источника — **DAC-DB / CSV / база данных**; поля источника
   становятся выходами, к которым можно подключать расчётные ноды.
3. **R-3. Состояние «значение не подставлено».** Связь передаётся, но
   значение ещё никуда не подставлено — отдельное видимое состояние слота
   (не ошибка, не молчаливая пустота).
4. **R-4. Прозрачность расчёта.** Пользователь видит, что именно считается
   внутри ноды: конкретные значения переменных и формулы с результатами.
5. **R-5. Квалифицированная адресация «Объект.Поле».** Входные параметры
   отображаются как обращение к полю объекта в коде — `Заявки.Средний_чек`,
   `Заявки.Конверсия` — вместо позиционных `$1, $2…`; амендмент нотации
   лейблов PRD-0004 F-5 и постоянных слотов F-14.

Скоуп: анатомия ноды, её LOD-уровни и семантика адресации. Отображение путей
и подсветка зависимостей **в main stage** — FR-044; движение значений по
рёбрам — FR-014/FR-029 без изменений.

## Анализ (Root Cause — чего нет в коде)

Якоря — по аудиту FR-042 (main 2026-09-20) и PRD-0004 §2.3/§7.3.

1. **Описания нет.** `Node` (`model.rs:210` `extra`; структура ноды
   `model.rs`) не несёт контекстного текста: text-нода хранит расчётный body,
   template — `lines` манифеста; отдельного «описания назначения» нет.
   Зона C по PRD-0004 §7.1 определяет «Numi-лист / параметры шаблона /
   тамбнейл» — слоя описания в контракте нет.
2. **Data-ноды нет.** Типы нод: text/template/file/widget/group; категорийный
   чип хедера (PRD-0004 F-2, обобщение полосы шаблона `cards.rs:349`) не
   имеет категории «данные». Источники данных определены PRD-0001
   (`DataInspectorBackend`, снапшот-ноды с проливом агрегатов), но UI-тип
   «нода входных данных» с портами-на-колонки и qualified-именами полей не
   оформлен; CSV/DAC-DB-бэкендов нет.
3. **Состояния слота «не подставлено» нет.** Поток вычисляет
   `inbound_slots` (`crates/canvas-core/src/flow.rs:518`) и `inbound_values`
   (`flow.rs:579`) — модуль в canvas-core, не в canvas-scene (сметчено
   2026-09-21: постановка FR-045/FR-044 ошибочно указывала canvas-scene);
   случаи «ребро подключено, значения нет» (`fromLine` пуст или вне
   диапазона, источник не отдал запись) сегодня дают молчаливую пустоту.
   Статусный слой E (PRD-0004 F-7) знает `selection > analysis > broken >
   hover` — pending-состояния в стопке нет.
4. **Группировки расчёта нет.** Построчные результаты L2 (PRD-0004 зона C)
   планируются единым списком; значения переменных видны только итогом в
   полосе D (F-6). Разделения «входящие значения / формулы» и
   qualified-путей в подстановках нет (отображение в stage — FR-044).
5. **Нотация позиционная.** Лейблы слотов — `$1..$N`, `to:<param>`,
   `out:<имя>` (PRD-0004 F-5); постоянные слоты F-14 — те же `$1..$N`.
   Сборки пути «Объект.Поле» нет (единственная точка сборки вводится
   настоящим FR и переиспользуется FR-044).

## Решения (зафиксированы по результатам проверки на прототипе)

- **Р-1. Описание — необязательный слой тела C.** Хранение:
  `canvasdesk.desc: String` в `Node.extra` (паттерн опциональных
  `canvasdesk.*` PRD-0004/§Non-goals). Отображение: строка курсивом с
  маркером «i» под хедером; LOD-1 — кламп 1 строки, LOD-2 — до 3 строк,
  полный текст — тултип (и в main stage — полностью). Высота тела
  резервируется геометрией анатомии (`anatomy.rs`, PRD-0004 §7.3). Описание
  не участвует в расчёте, не входит в Numi-лист, в hit-тест входит как часть
  тела.
- **Р-2. Нода «Входные данные» — расчётная нода с категорией «данные».**
  Хедер A: чип категории «данные» (на прототипе `#5aa2ff`) + иконка роли +
  имя; пометка источника рядом с именем: «CSV · 24 записи», «DAC-DB ·
  projects». Выходы: value-порт **на каждое поле источника** (колонку);
  qualified-имя поля = `<Объект>.<Поле>` (R-5). Полоса D: состояние
  источника — число записей / ошибка чтения. В пучках и main stage — обычный
  участник (исток). Хранение: `canvasdesk.data { kind: csv|dacdb|db, ref,
  fields[] }` в `Node.extra`. Бэкенды PoC: **CSV — живая реализация**
  (чистый Rust-парсер в `canvas-core`, фикстуры-тесты, allowlist ADR-0008);
  **DAC-DB и БД — по интерфейсу PRD-0001** (`DataInspectorBackend` →
  снапшот полей): настоящий FR фиксирует анатомию и контракт отображения,
  исполнение запросов — за PRD-0001/ADR-0013. Создание — из палитры/меню
  создания нод; редактирование списка полей — v2 (перезагрузка источника
  обновляет порты).
- **Р-3. Unmapped — производное pending-состояние.** Определение: ребро
  подключено к слоту приёмника, но пролитого значения нет (источник
  pending/ошибка, `fromLine` пуст/вне диапазона, колонка отсутствует в
  снапшоте). Вычисляется в `recompute_flow` (canvas-scene) как множество
  unmapped-слотов; **не сериализуется**. Визуал: порт — полый пунктирный
  контур (тип «открытый», на прототипе `◌`) в рейле; лейбл слота —
  плейсхолдер «не подставлено»; ребро — пунктир с янтарным акцентом;
  статусный слой E — бейдж в analysis-приоритете (ниже broken, выше hover);
  полоса D — «не рассчитано: <слот>» вместо ложного итога. Нода с unmapped
  входом **не падает** в broken: расчёт показывается как не выполненный
  полностью. В main stage — блок «Входы без привязки» (FR-044 Р-8/Р-4).
  Подстановка значения снимает состояние автоматически (следующий
  `recompute_flow`).
- **Р-4. Прозрачность расчёта — две группы построчных результатов.** Тело C
  на LOD-2 (и в main stage — FR-044 Р-4) показывает расчёт двумя
  визуально разделёнными группами: **«Переменные · входящие значения»** —
  qualified-адрес + текущее значение (+ единица); unmapped — пунктирная
  строка «не подставлено»; **«Расчёт · формулы»** —
  `<имя> := <формула с путями операндов> = <результат>`, маркер `ƒ`.
  Порядок: переменные — в порядке слотов, формулы — в порядке строк тела.
  Движок не трогается: рендер читает готовые `inbound_slots`/`inbound_values`
  (`flow.rs:518/579`) и результаты выражений; группы — раскладка рендера.
- **Р-5. Нотация «Объект.Поле» — display-level, единая точка сборки.**
  Правила: объект = имя ноды-истока (data-нода — имя объекта/листа
  источника); поле = имя выхода (`fromOutput`) | «строка N» (`fromLine`)
  | имя колонки источника; разделитель «.»; отображение имён — **дословное**
  (нормализация/транслитерация не выполняется; рекомендация авторам —
  идентификаторы без пробелов). Амендмент PRD-0004: **F-5** — лейблы слотов
  показывают `Объект.Поле` вместо `$N` (короткая форма «Поле» на канвасе
  при плотности, полный путь — в тултипе и в stage; компромисс проверен на
  прототипе); **F-14** — постоянные слоты при N ≤ порога отображают пути.
  Тексты формул в теле и в stage — display-подстановка путей вместо `$N`
  (исходник выражений не переписывается; именованный синтаксис — v2,
  см. FR-044 Q1). Коллизии имён (две ноды «Заявки») — fallback
  «Имя (node_id).Поле» (§Открытые вопросы Q2).

## LOD-матрица (требования к LOD-логике новых элементов)

Пороги — PRD-0004 F-8 (`node_lod_level`): L0 < 0.6, L1 0.6–1.5, L2 > 1.5;
main stage запрашивает L2 независимо от зума (PRD-0004 F-10, FR-042).

| Элемент | L0 (силуэт) | L1 | L2 | main stage |
|---|---|---|---|---|
| Описание (R-1) | скрыто | строка-кламп + маркер «i» | до 3 строк + тултип | полностью |
| Нода данных (R-2) | чип + имя + «N записей» | + индикатор источника | + поля-порты рейла выхода | L2-анатомия; поля-истоки — подписиqualified-путями (FR-044) |
| Слот «не подставлено» (R-3) | бейдж-стек E: счётчик unmapped | пунктирный порт-контур | порт + плейсхолдер лейбла + пунктирное ребро | блок «Входы без привязки» (FR-044) |
| Прозрачность расчёта (R-4) | полоса D: итог / «не рассчитано» | скрыто (тело кламп) | две группы в теле C | панель «Как считается» (FR-044 Р-4) |
| Нотация (R-5) | — | короткая форма «Поле» | короткая форма + полный путь в тултипе | всегда полный путь |

Инвариант матрицы: переходы LOD не меняют семантику (одни и те же данные,
разная плотность); при L0 нода данных неотличима по силуэту от прочих
расчётных (контракт «силуэт несёт 3 сигнала» — PRD-0004 §7.1-3), кроме
значения в полосе D.

- MCP: без изменений (v2 при спросе — `canvasdesk.data` в `node_create`).

## Инварианты тестируемости

1. `canvasdesk.desc` не влияет на поток: расчёт ноды с описанием и без —
   идентичен (тест на identical `expr_results`).
2. Round-trip `.canvas` с `canvasdesk.desc`/`canvasdesk.data`: поля Obsidian
   не тронуты, опциональные поля восстанавливаются (паттерн node.md §8).
3. Data-нода генерирует ровно `|fields[]|` выходных value-портов; qualified-
   адрес каждого разрешается через `display_ref` на её рёбрах.
4. Unmapped-состояние — производное: не сериализуется; ставится/снимается
   только `recompute_flow` (тест: подать значение — состояние снято).
5. Нода с unmapped-входом не в broken: полоса D — «не рассчитано: <слот>»,
   бейдж — analysis-приоритет (порядок стопки F-7 сохранён).
6. Unmapped-ребро — пунктир; value/control-кinds остальных рёбер не меняют
   отрисовку (регресс-щит).
7. Группы расчёта детерминированы: порядок переменных = порядок слотов,
   формул = порядок строк тела (двойной рендер — идентичный).
8. Переходы LOD (0.6/1.5) переключают только плотность описания/полей —
   данные и hit-цели портов согласованы между уровнями (матрица §LOD-матрица).
9. CSV-парсер: фикстуры (кавычки, разделители, пустые значения, BOM) —
   зелёные; лимит размера не превышен.
10. wasm-гейт (ADR-0011) зелёный: `dataref.rs`, CSV-парсер, раскладки —
    чистый Rust без платформенного кода.
