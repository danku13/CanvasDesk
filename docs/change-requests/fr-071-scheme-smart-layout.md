# FR-071: Умная раскладка нод при инстансировании шаблонных сцен (схем)

- **Статус:** выполнено
- **Тип:** FR
- **Приоритет:** важно
- **Владелец:** агент (Super Z, сессия 2026-09-25), запрос владельца
- **Источник:** запрос владельца 2026-09-25: «Нужно продумать умный подход к расстановке нод при шаблонных сценах, чтобы ноды минимально пересекались edge-ами, и группировались по смыслу»
- **Связанные задачи:** FR-049 (схемы), FR-010 (авто-раскладка связанных карточек — образец), FR-012 (явные группы), CR-008 (умные порты/стороны рёбер), ADR-0011 (wasm-гейт ядра)
- **Создан:** 2026-09-25
- **Обновлён:** 2026-09-26

## Описание

Шаблонные сцены (схемы FR-049, `assets/canvas-schemes/*/scheme.json`) хранят
координаты всех нод вручную: автор пакета расставляет каждую ноду числами
`x`/`y`. Это трудоёмко для новых схем, не защищает от пересечений рёбер с
карточками (edge проходит сквозь чужую ноду) и не масштабируется: при правке
состава схемы раскладку приходится передвигать заново.

Требуется: при инстансировании схемы раскладывать ноды автоматически —
детерминированным алгоритмом, который (1) группирует ноды по смыслу
(явные группы, расчётная цепочка, standalone-подсказки) и (2) минимизирует
пересечения рёбер с нодами. Координаты из `scheme.json` перестают быть
источником правды о геометрии (остаются в пакете — формат JSON Canvas не
расширяется — и используются только как семантические подсказки порядка).

| Объект | Что меняется | Где в документации |

## Анализ

Что отсутствует (нет API):

- В `canvas-core` есть только FR-010 `plan_related_layout` (`layout.rs`) —
  раскладка окрестности ноды-семени (tree/radial). Для схем целиком — нет ничего.
- `instantiate_scheme` (`canvas-scene/src/scheme_apply.rs:63`) копирует
  `node.x + dx, node.y + dy` без анализа графа: пересечения рёбер с нодами и
  плотность упаковки зависят целиком от аккуратности автора пакета.
- Группы схем: рамка группы задаётся вручную (`x/y/width/height` группы) —
  при автораскладке детей рамку нужно пересчитывать.

Ограничения, учтённые в решении:

- Инстансер — чистая функция над `(манифест, &Canvas, origin)`; wasm-гейт
  (ADR-0011) запрещает I/O и платформенное — алгоритм обязан быть чистым.
- Лимиты схем: ≤ 200 нод / ≤ 400 рёбер (`schemes.rs` MAX_NODES/MAX_EDGES) —
  O(n²·e) локальная оптимизация допустима, тяжёлые солверы не нужны.
- Порты value-рёбер при инстансировании — right→left (`scheme_apply.rs:158`):
  чтение потока слева направо, истоки — слева. Алгоритм обязан сохранять
  эту конвенцию.
- Детерминизм (образец FR-010): сортировка по `id`/индексу, никаких
  итераций по `HashMap` в порядковых решениях, никакой рандомизации.
- Рендер рёбер: Безье + detour-огибания (`edgegeom.rs` `edge_polyline`,
  `AVOID_MARGIN = 12`) — цель алгоритма: чтобы огибать было нужно редко.

## Требуемые изменения (замысел алгоритма)

Новый модуль `crates/canvas-core/src/scheme_layout.rs` — чистые функции,
зависимости: только `model.rs`. Образец стиля — `layout.rs` (FR-010).

Вход: `&Canvas` (инстансированные ноды/рёбра схемы, до сдвига к origin).
Выход: план раскладки — целевые top-left для всех нод + новые размеры рамок групп.

Этапы алгоритма (все детерминированы):

1. **Семантические кластеры** — union-find по (а) явным группам
   (`Node.children`: дети одной группы — один кластер), (б) связности
   неориентированного графа рёбер. Результат: 1..N кластеров потока +
   standalone-ноды (без рёбер: подсказки, вердикты).
2. **Слоистая DAG-раскладка кластера** (Sugiyama-lite):
   - слои: longest-path от истоков (in-degree 0 → слой 0, дальше
     `max(слои предков) + 1`); циклы — защита BFS-фолбэком (образец
     `layout.rs` `visited`);
   - колонка = слой (истоки левее — конвенция right→left);
   - порядок внутри слоя: barycenter-проходы (2 вперёд + 2 назад),
     стабильная сортировка по средней позиции соседей; seed-порядок —
     по исходным координатам пакета (семантика автора), тай-брейк по id;
   - позиции: x — кумулятивно по максимальной ширине колонки + `LAYER_GAP`;
     y — стек рядов + `ROW_GAP`, колонка центрируется на среднем центре
     родителей (компактный поток).
3. **Минимизация пересечений edge×node** — локальная оптимизация:
   - стоимость ребра: число пересечений отрезка порт→порт (right-центр →
     left-центр) с bbox нод (инфляция на `AVOID_MARGIN`), кроме концов
     ребра; проверяются только ноды промежуточных колонок;
   - ход: перестановка соседних нод внутри одной колонки; ход принимается,
     если суммарная стоимость затронутых рёбер строго падает; проходы
     слева направо по колонкам, максимум 8 проходов (детерминизм);
   - tie-break стоимости — суммарная длина отрезков (компактность).
4. **Рамки групп** — bbox детей + `GROUP_PAD` (рамка не участвует в графе:
   у групп схем нет рёбер); дети геометрически внутри рамки (инвариант FR-012).
5. **Standalone-ноды** (без рёбер) — аннотационные колонки слева/справа от
   потока: исходный `x` из пакета левее центра bbox потока → левая колонка,
   иначе правая; порядок в колонке — по исходным (x, y, id); колонка
   центрируется по вертикали на bbox потока.
6. **Сборка** — кластеры потока стыкуются по горизонтали с `CLUSTER_GAP`;
   план сортируется по индексу ноды (образец FR-010).

Интеграция: `instantiate_scheme` строит временный `Canvas` из
инстансированных нод/рёбер, применяет план ДО сдвига к `origin`; bbox
считается от финальных прямоугольников. Контракт `SchemeInstance` и MCP
инструмента не меняется.

### Что сознательно не входит (v1)

- Перекрёстные пересечения самих рёбер (edge×edge) — только edge×node.
- Группы с рёбрами (в built-in схемах их нет) — участвуют как обычные ноды
  графа, рамка по детям; ограничение зафиксировано тестом-документацией.
- Раскладка при перетаскивании/правке уже вставленной схемы — вне рамок
  FR (это FR-010/будущие CR).
- Эстетика: рамки соседних групп в одной колонке могут соприкасаться
  краями (ROW_GAP = 2×GROUP_PAD); разделение рамок — отдельная правка
  по решению владельца.

## Точки входа

- `docs/interface-objects/scheme-gallery.md` — раздел «Инстансирование»:
  раскладка вычисляется алгоритмом FR-071.
- `docs/interface-objects/node.md` — группы: рамка пересчитывается по детям
  при инстансе схемы.
- `docs/interface-objects/edge.md` — заметка: раскладка схем минимизирует
  пересечения рёбер с нодами (detour остаётся фолбэком).
- `crates/canvas-core/src/scheme_layout.rs` — док-комментарий модуля = сводка.
- `crates/canvas-scene/src/scheme_apply.rs` — док-комментарий инстансера.

## Проверка

Юнит-тесты `canvas-core/scheme_layout.rs` (10, все зелёные):

- [x] chain a→b→c: колонки слева направо, a левее b, b левее c (конвенция right→left);
- [x] раскладка без пересечений bbox нод (в т.ч. ветвления);
- [x] барицентр: узлы с общим родителем стоят рядом (смысловая группировка);
- [x] явная группа: дети рядом, рамка покрывает bbox детей + паддинг;
- [x] standalone-нода уходит в аннотационную колонку (лево/право по исходному x);
- [x] цикл a↔b не зависает (фолбэк слоения);
- [x] детерминизм: два вызова на одном входе — идентичные планы;
- [x] рёбра не пересекают чужие ноды после оптимизации (длинная диагональ
  через среднюю колонку устраняется shift/swap-оптимизацией);
- [x] пустой канвас / поток из одних standalone — одна колонка;
- [x] изолированная группа (дети без рёбер) — рамка следует за детьми.

Oracle-тесты `canvas-scene/scheme_apply.rs` (4 новых, все зелёные):

- [x] 0 пересечений bbox нод (6 built-in схем);
- [x] 0 пересечений value-рёбер с чужими нодами (прямой отрезок порт→порт;
  до FR-071 у ручных раскладок было 1–4 пересечения в каждой схеме);
- [x] дети каждой группы геометрически внутри рамки группы;
- [x] bbox по-прежнему центрирован на origin (контракт zoom-to-fit);
- [x] значения формул oracle-ов не изменились (раскладка не трогает контент);
- [x] детерминизм: два инстанса одной схемы — идентичные позиции.

Гейты: `cargo test -p canvas-core -p canvas-scene -p canvas-app` — зелено
(415+ тестов), `cargo clippy --workspace -- -D warnings` — чисто,
`cargo fmt --check` — чисто, wasm-гейт `cargo check -p canvas-core
-p canvas-scene --target wasm32-unknown-unknown` — чисто (ADR-0011).
