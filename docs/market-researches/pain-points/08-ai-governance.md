# Боль 08: ИИ ломает архитектурные нормы

> Суть: генеративный ИИ производит код быстрее, чем архитектура успевает
> его проверять и документировать; ручной governance перестаёт масштабироваться.

**Матрица:** тяжесть 4/5 · распространённость 3/5 (растёт) · готовность платить 3/5 ·
доказательность: средняя (категория формируется на наших глазах)

## 1. Механизм боли

ИИ-ассистенты и агенты генерируют PR, соответствующие *локальной* задаче
и нарушающие *глобальные* инварианты: обходит кэш, создаёт прямой доступ к
БД, дублирует сервис, тянет тяжёлую зависимость. Человек-ревьюер не может
держать в голове все правила всех доменов; правила есть в документации,
которую ИИ не читает, а человек не помнит. В результате дрейф архитектуры
(боль 01) ускоряется на порядок, а ADR-дисциплина (боль 03) окончательно
теряет смысл, если записи не машинно-читаемы.

## 2. Доказательства и цитаты

> «We built Architect MCP to close the feedback loop at code generation
> time; Results: 80% pattern compliance vs 30–40% with documentation alone» —
> dev.to, 12.10.2025 (сниппет; восстановить прямую ссылку —
> [quotes-bank](../quotes-bank.md)). Первая публичная цифра разрыва:
> документация обеспечивает 30–40% комплаенса, автоматическая петля — до 80%.

> «AI-based architecture checkers have been prototyped for integration into
> CI/CD pipelines to detect architectural drift caused by SDK evolution» —
> Bucaioni et al., ACM, 2026. Академическое направление уже обозначено:
> проверка архитектуры переходит из ревью в конвейер.

> «Transform enterprise architecture to drive innovation, productivity, and
> agility… embrace AI…» — Gartner, Leadership Vision for EA 2025
> (цит. по [timoelliott, 07.02.2025](https://timoelliott.com)): вендоры и
> аналитики синхронно переводят EA в режим «governance для ИИ-потока».

> «How Enterprise Architecture is evolving in 2025: AI, people, and growth» —
> LinkedIn, 28.08.2025 (сниппет). Сама профессия формулирует сдвиг роли.

Обратная сторона (смягчение боли): «84% of architects see AI as augmenting
their work, not replacing it» — Monograph, 23.12.2025 (обзор строительной
аудитории; переносим на ИТ-архитекторов осторожно, только как фон настроений).

## 3. Как решают сегодня

- **Lint-стек и ArchUnit-тесты** — детерминированные правила; работают,
  пока правила выразимы кодом и кто-то их пишет.
- **AI-ревьюеры** (Copilot-ревью и аналоги) — проверяют качество кода,
  а не архитектурные инварианты системы.
- **MCP-серверы архитектуры** — ранний паттерн: дать агенту инструменты
  чтения/правки модели (CanvasDesk `canvas-mcp` с 23 инструментами —
  прямой участник паттерна).
- **Policy-as-code** (OPA) — на уровне политик деплоя, не дизайна.

## 4. Разрыв рынка

Правила архитектуры существуют в трёх несовместимых видах: проза в документах,
код в тестах, молчание в головах. Для ИИ-агента нужен *машинно-читаемый
контракт системы*: модель с инвариантами (нагрузка, стоимость, границы),
которую агент может читать до генерации и проверять после. Окно возможности:
паттерн MCP только формируется — тот, кто определит формат «архитектурного
контракта» для агентов, станет стандартом де-факто. Признак срочности:
команда dev.to уже публикует комплаенс-цифры (80% vs 30–40%).

## 5. Следствия для продукта (гипотезы)

- **Г1.** CanvasDesk-модель как источник контекста для ИИ-агента: агент
  спрашивает MCP «какие инварианты действуют на этот компонент» до
  генерации кода. Ближайшая проверка — эталонные модели уже собираются
  агентом через MCP (ADR-0005/0006).
- **Г2.** Guardrails-отчёт: после PR — какие инварианты нарушены; метрика
  «комплаенс %» как у пионеров категории.
- **Г3.** Опасность: MCP-стандарт может приватизировать крупный вендор
  (GitHub/Atlassian); стратегия — открытый формат поверх JSON Canvas.
