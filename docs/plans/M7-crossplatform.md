# M7. Кроссплатформенность (Windows / Linux / macOS) — план и рефакторинг

ЗАДАЧА (директива владельца, 2026-09-14): приложение перестаёт быть
Windows-only — целевые платформы Windows 10/11, Linux (X11/Wayland) и
macOS; сборка и гейты — на всех трёх. Milestone объединяет три потока:
(1) платформенная матрица и архитектура портирования, (2) аудит и чистка
зависимостей, (3) инкрементальное закрытие платформенных разрывов.

Источники истины: `docs/SPEC.md` §1/§3/§4 (обновлены под M7),
`AGENTS.md` (правила платформенного кода), `docs/ENVIRONMENT.md` (сборка
на трёх ОС), `docs/devlog/M5-widgets.md` §6–§7 (уроки cfg(windows) и
FSEvents — мотивация матрицы CI).

---

## 1. Принцип и границы

**Принцип:** ядро уже кроссплатформенно (canvas-core/render, shell-кэш,
вотчер, поиск — компилируются и тестируются на Linux/macOS с первого
коммита по правилу AGENTS «core обязан собираться на Linux»). M7 не
переписывает ядро — он достраивает платформенные реализации там, где
сейчас стоят Windows-реализации или заглушки.

**Границы v1.2 (осознанные):**
- **Desktop-режим (WorkerW, «вместо рабочего стола») остаётся
  Windows-only.** Это глубоко платформенная фича; юникс-эквиваленты
  (X11 `_NET_WM_WINDOW_TYPE_DESKTOP`, Wayland layer-shell, macOS
  NSWindow-level) — отдельное исследование после v1.2, не входит в M7.
- **Виджеты на юниксах — отложено до после T22.** WebView2-хост — самая
  молодая часть кода; абстракция под три движка (WebKitGTK/WKWebView)
  размажет усилия SDK. v1.2: на Linux/macOS виджет-нода рендерится
  снапшотом/плейсхолдером, как при недоступном рантайме (код уже умеет).
- Замена shell, облачная синхронизация — как прежде, вне объёма.

**Чего M7 НЕ делает:** не меняет формат `.canvas`, не трогает UI-слой
приложения, не меняет пакеты виджетов. Платформенные отличия остаются
ЗА трейтами и cfg — прямой платформенный код в canvas-app не появляется.

## 3. Архитектура портирования

### 3.1. Слои и правила (расширение правил AGENTS)

1. Платформенный код живёт в `canvas-shell` (как сегодня) и в
   `cfg(windows)`-секциях `canvas-widgets`/`canvas-mcp`. В `canvas-app`
   платформенных веток становится МЕНЬШЕ, не больше: ветка app должна
   выбирать реализацию трейта, а не ветвиться по `cfg` на каждом вызове.
2. Каждая платформенная способность — это трейт из canvas-core
   (паттерн `ThumbnailProvider` уже существует и проверен
   `NoopThumbnailProvider`): реализация Windows/Linux/macOS + заглушка по
   умолчанию. Тесты гоняются против заглушки и чистых частей на любой ОС.
3. Эквивалентные механизмы ОС собираются в одну таблицу решений ДО
   реализации (как RECIPES для Windows) — чтобы «а как на Wayland?»
  решался по документу, а не по памяти агента.

### 3.2. Решения по разрывам

| Разрыв | Решение | Обоснование |
|---|---|---|
| Drag-drop | **winit-события** `HoveredFile`/`DroppedFile` на Linux/macOS; Windows-путь (IDropTarget) остаётся — он даёт данные CF_HDROP с папками и модификаторы | winit 0.30 уже отдаёт дроп-пути на всех трёх ОС; классификация дропа (`plan_drop`/`expand_drop_paths`) — чистые функции, переиспользуются как есть; призрак-план и ghost-UI — общий код |
| Тамбнейлы | Реализация `ThumbnailProvider` для юниксов: изображения — декод через `image` (уже в дереве), прочее — MIME-тип → имя иконки; чтение/запись кэша по [спецификации freedesktop thumbnails](https://specifications.freedesktop.org/thumbnail-spec/) (`~/.cache/thumbnails/{normal,large}`), общий с `cache.db` mtime-инвалидацией | кэш FDO общий с Dolphin/Nautilus/GNOME-файлами — системные тамбнейлы «бесплатно»; macOS (QLThumbnail) — отдельно, после Linux (порядок по числу пользователей) |
| MCP-транспорт | `~/.canvasdesk/mcp.sock` — Unix domain socket; протокол (line-framing JSON) идентичен named pipe; `canvasdesk-mcp` детектит ОС и коннектится к сокету | UDS — юникс-эквивалент pipe с теми же свойствами (локальный, права через fs); код канвас-mcp уже имеет `cfg(not(windows))`-ветки — транспорт расширяется, протокол нет |
| Автозапуск | Linux: `~/.config/autostart/canvasdesk.desktop` (XDG Autostart); macOS: LaunchAgent plist `~/Library/LaunchAgents/` | стандарты окружений, без прав root |
| Виджеты (после T22) | кандидат — `wry` (WebView2/WebKitGTK/WKWebView) за трейтом `WidgetHostBackend`; LOD/bridge/registry — уже платформонезависимы | оценка ТОЛЬКО после T21/T22 — сначала протокол на Windows, потом носители |

### 3.3. CI: три ОС как авторитет

Матрица гейтов готова: ветка **`ci-matrix`** (коммит 12c5a89) — ci.yml
гоняет fmt/clippy/test/build на ubuntu/windows/macos, build-all.yml
освобождён от дублей гейтов (только release-артефакты). **Пат агента не
имеет scope `workflow`** — ветку пушит владелец вручную (как 196c1b4).
До этого windows-check в ci.yml остаётся авторитетом, а 3-ОС
сборка/тесты покрывает build-all (уже зелёный с 70783d1).

Уроки, зашитые в процесс (из devlog M5 §6):
- cfg(windows)-код в canvas-app невидим для Linux-гейтов → красный CI
  блокирует следующую задачу (протокол уже требует);
- локальная msvc-проба расширяется: `cargo clippy --target
  x86_64-pc-windows-msvc -p canvas-widgets -p canvas-core -p
  canvas-render` (clippy, не только check; canvas-app остаётся вне пробы
  до появления линкера — rusqlite C-dep).

## 6. Риски и митигации

| Риск | Митигация |
|---|---|
| Wayland-специфика (drag-drop, xdg-desktop-portal) | winit закрывает различия X11/Wayland; если портальная дроп-кривая — fallback: файл-меню импорта (не блокер) |
| FDO-кэш повреждён/чужие форматы | кэш пересоздаваемый по правилу SPEC §5.3; валидация PNG-заголовка при чтении |
| rusqlite bundled на macOS CI | уже зелёный (build-all macos с 70783d1) |
| notify-квестики macOS (остаточные после 70783d1) | burst-тест релаксирован документированно; любые новые — по логам CI, по образцу FSEvents-фикса |
| wry (виджеты) не даст airspace-контроль | решение принимается ПОСЛЕ T22 отдельным планом; v1.2 живёт с placeholder на юниксах |
| Расползание cfg по app | правило §3.1: платформенные ветки только за трейтами; ревью каждого коммита M7 |

## 7. Критерии приёмки M7 (SPEC §10, дополнение)

1. Гейты CI зелёные на ubuntu/windows/macos (после C-1) — каждый пуш.
2. На Linux: drag папки из файлового менеджера разворачивается в ноды;
   тамбнейлы изображений видны (не заглушки); `canvasdesk mcp` работает
   через сокет с реальным AI-клиентом.
3. На macOS: то же T27/T28/T29-множество (порядок портирования может
   отличаться — фиксируется в TASKS-статусах).
4. Windows: нулевой регресс (приёмка §4–§15 проходит как перед M7).
5. Аудит зависимостей: R1/R6 закрыты или осознанно отложены записью
   сюда; `cargo tree -d` без неожиданных дубликатов версий.
