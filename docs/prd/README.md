# PRD — каталог требований продукта (`docs/prd/`)

PRD (Product Requirements Document) — документ требований продукта: **проблема → цели → пользователи и CJM → user stories → решение → non-goals → roadmap**. PRD отвечает на вопросы «**что и зачем**»; реализационный FR (`docs/change-requests/`) — на вопросы «**где и как**» в коде. Двухуровневая схема: PRD не меняется при каждой правке реализации, FR ведёт исполнение.

## Правила ведения каталога

1. **Файл и номер.** Имя — `prd-<NNNN>-<краткое-название>.md` (kebab-case). Номер — последовательный за максимальным существующим (переиспользование номеров запрещено; история задвоений уже была — см. ADR-0007). Заголовок документа: `# PRD-<NNNN>: <название>`.
2. **Шаблон обязателен.** Новый PRD создаётся копированием [`TEMPLATE.md`](TEMPLATE.html) с заполнением всех разделов. Каноническая структура — 17 разделов; допустимы локальные перестановки (например, «Терминология» рядом с «Контекстом»), но обязательный набор: Контекст с ссылками `file.rs:line` (§2), измеримые цели (§3), user stories + acceptance criteria (§5), **CJM (§6)**, решение с диаграммой и отвергнутыми вариантами (§7), F-таблица (§8), non-goals (§10), DoD (§15), источники истины (§17).
3. **CJM обязателен (§6 шаблона).** Два уровня: краткий (шаги: этап → действие → поверхность) и детальный (мысли, эмоции по шкале −2…+2, боли, **точки отвала**, возможности). Каждая точка отвала трассируется в требование/метрику/риск (§6.3) — точка отвала без митигации считается декоративной и снимается с документа.
4. **Статусная модель.** `черновик → в анализе → в работе (FR создан) → выполнено / отклонено`. Каждое изменение статуса и содержания — строка в «Истории изменений» (§16) и актуализация поля «Обновлён».
5. **Связь с реализацией.** При старте работ по PRD заводится FR-документ в `docs/change-requests/` (следующий свободный номер, шаблон `cr-template.md`) со ссылкой на PRD в поле «Источник». Тяжёлые/нативные зависимости и решения, меняющие правила архитектуры, — через ADR **до** реализации (`docs/adr/`, правило ADR-0001 и AGENTS.md).
6. **Фактура обязательна.** Контекст (§2) и решение (§7) ссылаются на конкретный код (`path/file.rs:line`) и документы; цели (§3) — измеримы; DoD (§15) — чек-лист с гейтами (`cargo test/clippy/fmt`, `scripts/wasm_gate.sh`, round-trip).
7. **Коммит.** Один PRD — один коммит по conventional commits (`docs(prd): …`); индекс в этом файле и `docs/index.md` обновляется тем же коммитом.

## Связи между PRD

- **PRD-0001 + PRD-0003** — полный цикл: импортированная топология архитектуры (0003) получает реальные вводные из данных (0001) и превращается в исполняемую мат.модель.
- **PRD-0002 + PRD-0003** — импортированные графы бывают плотными; агрегация пучков (0002) делает их читаемыми.
- **PRD-0002 + PRD-0004** — единая анатомия ноды (0004) — опора для LOD-агрегации и main stage (0002): main stage рендерит ноды в полном уровне L2, hover пучка подсвечивает типизированные порт-рейлы; этапы N6 (0004) и E-этапы (0002) сверяют контракт стыка.
- **PRD-0003 + PRD-0005** — замкнутый контур «репозиторий ↔ канвас»: Git-синхронизация (0005) приносит `.tf`/compose/диаграммы из реального репозитория на канвас, где их встречает всеядный импорт (0003); опубликованная модель живёт рядом с описанной ею системой (IaC) в одном PR-процессе.
- **PRD-0006 + PRD-0004** — единая система design-токенов (0006) — обобщение F-1 анатомии ноды (0004): `canvas-core::tokens` — одна точка правды для метрик и цветов, анатомия — её первый потребитель; этапы D2–D3 (0006) и N-этапы (0004) сверяют контракт стыка, чтобы не развести две системы.
- **PRD-0006 + PRD-0002/FR-042** — пучки рёбер и main stage (0002) получают цвета/состояния через слоты палитры (0006), а не новые константы — правило потока §7.1.
- **PRD-0007 + PRD-0004/fr-044/fr-045** — цепочка расчёта (0007) — частный случай связей и LOD: explain-дерево — LOD-фокус на подграфе потока значений; обобщает панель «Как считается» (fr-044) и группы прозрачности (fr-045 R-4) с одной ноды на произвольную цифру; LOD-пороги триггера «?» — по политике L0/L1/L2 (0004).
- **PRD-0007 + FR-017** — сценарии в моменте (0007) — контекстная надстройка над what-if движком (017): подмена листа дерева адресуется существующими `WhatIfOverrides`, дельты/таблица сравнения/Apply — без нового механизма.
- **PRD-0007 + PRD-0002/FR-042** — подсветка цепочки совместима с LOD-0 агрегацией (доминантное ребро пучка), а explain-панель входит в реестр взаимоисключимых модальностей (Q6 FR-042).
- **PRD-0007 + PRD-0006** — подсветка/дельты/панель берут цвета из `ThemeColors` v2 (0006), не из новых констант — правило потока §7.1.
- **PRD-0008 + FR-018/019/020** — третий слой шаблонной системы: шаблоны-ноды (FR-019) собирают одиночную ноду из манифеста, схемы (0008) — целую сцену; общий паттерн «реестр как данные» (`TemplateRegistry`), валидатор и инстансер схем переиспользуют инварианты тестируемости; композиция «схема содержит шаблонные ноды» — v2 0008.
- **PRD-0008 + FR-028** — схемы — контент для v2 демо-канваса онбординга: вместо хардкода турового канваса — чек-точки (резервация `action`, `onboarding_ui.rs:27`) поверх схемы-тура из библиотеки; empty-state 0008 и карусель 028 делят точку входа новичка без взаимных блокировок.
- **PRD-0008 + PRD-0003** — оба производят граф канваса из внешнего источника: всеядный импорт (0003) — из машиночитаемых описаний, схемы (0008) — из встроенного пакета; ремап id, валидация графа и лимиты — общие примитивы, контракты сверяются на этапе T0/T1 0008.
- **PRD-0008 + PRD-0006** — галерея схем, empty-state и карточки берут цвета из слотов `ThemeColors` v2 (0006), без новых констант — правило потока §7.1; hex-цвета в схемах запрещены валидатором (только пресеты JSON Canvas «1»..«6»).
- **PRD-0009 + PRD-0006** — каркас UI-слоёв (0009) потребляет дизайн-систему (0006): компоненты UI kit берут только слоты `ThemeColors` v2 (включая новые слоты состояний hover/active/disabled), отступы/радиусы — spacing/radius-scale из `design/tokens/dimensions.json`; контраст состояний проверяется существующей контраст-машиной 0006.
- **PRD-0009 + PRD-0007** — defense mode (0007) — первый внешний потребитель реестра поверхностей (0009): модальный оверлей объявляется одной записью (слой Modal, политика Block, keyboard-scope) вместо ручной вписки в цепочки ввода; контракт зафиксирован в US-5 0009.
- **PRD-0009 + PRD-0002/FR-042** — main stage и реестр взаимоисключимых модальностей (Q6 FR-042) обобщаются capture-политиками слоёв (0009); рендер мира (zorder-планировщик) сохраняется без изменений — слои 0009 строятся над ним, не вместо него.
