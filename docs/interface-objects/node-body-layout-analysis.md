## 1. Резюме

Жалоба/вопрос владельца раскладывается на три проектных решения:

1. **Текстовые описания — первый класс.** Сегодня описание шаблона — это
   поле манифеста (`description`, до 591 символа у `ue-*`), которое на ноде
   живёт в общем GFM-потоке без ранга. Тело ноды должно явно отвечать на
   вопрос «что это и почему» — до того, как глаз упадёт на числа.
2. **Дилемма Numi-строк:** сквозные (в общем потоке с прозой — как в
   Numi-приложении и как в текущей реализации `formula_lines`) **или**
   отдельным блоком снизу (текст сверху, ведомость расчёта снизу). Обе
   крайности имеют цену: поток разваливается на 11+ строках, блок
   добавляет «мёртвую зону» на пустых нодах и рвёт нарратив «текст →
   тут же формула».
3. **Оптимизации восприятия** нужны в любом случае: два шрифтовых слоя,
   правый желоб значений, приглушённые юниты, бейджи каскада Р-1,
   зебра/группы, Σ-строка, сворачивание.

Ответ анализа — **три варианта** (§5): Н-1 «Сквозной лист» (канон Numi,
эволюция сегодняшнего), Н-2 «Двухзонная нода» (текст сверху + ведомость
снизу), Н-3 «Адаптивная» (до порога T строк — лист, после — блок + кламп
описания). **Рекомендация — Н-3 с порогом T≈4** (§8): малое наполнение
читается как Numi-заметка, большое — как ведомость; пустая нода не несёт
мёртвых зон; диагностика (unmapped) не сворачивается никогда.

Тест наполнения — центральный инструмент решения: прототип гоняет одну и
ту же ноду (шаблон `com.canvasdesk.tcp-lb` — самый нагруженный в библиотеке:
6 параметров + 5 выходов с формулами) через уровни **L0 пустая → L1 лёгкая →
L2 средняя → L3 максимум**, во всех трёх вариантах, с каскадом Р-1
(проливание + what-if + unmapped).

## 2. Текущее состояние (факт-карта)

### 2.1 Как устроено тело сегодня

| Элемент | Где в коде/данных | Как выглядит |
|---|---|---|
| **GFM-поток** | `text.rs` `shape_body`/`push_gfm_blocks` | тело = markdown: заголовки, абзацы, списки |
| **Numi-строки** | `formula_lines: Vec<usize>` — индексы строк текста | **сквозные**: строка внутри GFM-потока получает CodeBg-фон, справа бейдж результата, справа построчный порт FR-025 |
| **Описание шаблона** | `TemplateManifest.description` (манифесты `assets/templates/*`) | 30–591 символ; на ноде выводится в общий поток, ранга не имеет |
| **Параметры шаблона** | `params[]` манифеста; якоря слева FR-050 Н2 (`text.rs:1656`) | строки параметров у левого края |
| **Выходы шаблона** | `outputs[]` (имя + `expr` + unit) | построчные результаты + узловой итог в футере |
| **Авто-строка приёмника** | FR-050 Р-4/Н10-а | строка-проекция «Объект.Поле = значение», верх тела, зона «входящие значения», oblique-моно Р-2 |
| **Полоса D** | `result_footer_y`, FR-013 | единая полоса итога внизу |
| **Итог** | программный итог + построчные (`text.rs:1197`) | футер карточки |

### 2.2 Самый сложный шаблон — эталон для теста

`com.canvasdesk.tcp-lb` (TCP-балансировщик, v1.2.0, категория network):

- **6 параметров**: `connections_per_sec` 800 rps, `server_rate` 400 rps,
  `servers` 3 (min 1, max 100), `auth_share` 0.15, `feed_share` 0.6,
  `media_share` 0.25;
- **5 выходов с формулами**: `out_gateway = $connections_per_sec`,
  `out_auth = $connections_per_sec × $auth_share`, `out_feed`, `out_media`,
  `utilization = utilization($connections_per_sec, $server_rate, $servers)`;
- узловая формула `mm1($connections_per_sec, $server_rate, $servers)`;
- описание «L4-балансировщик TCP-соединений по серверам».

Именно этот шаблон использован в прототипе как L3 «максимум»: 11 строк
данных (6 параметров + 5 формул) + описание + заметка пользователя +
авто-строка unmapped — верхняя граница наполнения одной ноды. (Замер по
всей библиотеке: 44 манифеста, медиана 2–3 параметра, tcp-lb — максимум
по параметрам и выходам; `ue-npv` — максимум по описанию, 529 символов.)

### 2.3 Дефекты текущей модели (по критериям восприятия)

1. **Нет ранга описания.** Проза и формулы — один поток с одним шрифтом
   (моно у формульных строк есть, но проза не образует «зоны смысла»):
   на L3-наполнении глаз не находит «что это» и «где числа».
2. **Значения не выровнены.** Бейдж результата у правого края есть, но
   между формулой и значением нет дорожки: на 5+ строках столбец чисел
   «пляшет» (разные длины формул).
3. **Каскад не читается строкой.** Проливание/what-if/unmapped сегодня —
   подсветки и тултипы; у строки нет бейджа источника, видимого без ховера.
4. **Нет управления плотностью.** 11 строк рендерятся как есть: ни зебры,
   ни групп, ни сворачивания; нода растёт до ~600 px.

## 3. Use case наполнения (одна нода растёт)

Формат: состояние ноды → что должен увидеть пользователь → риск.

| # | Состояние | Содержимое | Задача взгляда | Риск при ошибке layout |
|---|---|---|---|---|
| **L0** | только создана | заголовок + плейсхолдер | «сюда можно писать» | мёртвая зона пустого блока расчёта пугает «инженерностью» (R-12/SA-линза) |
| **L1** | лёгкая | 1 строка описания, 1–2 параметра, 1 формула | читается как заметка Numi | если сразу рисовать каркас блока — «форма без содержания» |
| **L2** | средняя | описание 2 строки, ~4 параметра (1 пролит), ~3 формулы, авто-строка | описание + первый скан чисел | числа теряются в тексте, если нет желоба значений |
| **L3** | максимум (tcp-lb) | описание + заметка, 6 параметров (проливание + what-if), 5 формул, Σ | скан чисел одним взглядом + итог | «стена текста»: без групп/зебры/свёртки глаз не собирает столбец значений |
| **Компакт** | F-9 | хедер + полоса D | семантика сохранена | потеря итога — единственная непростительная потеря |
| **LOD L0/L1** | зум | силуэт/кламп | категория/имя/результат | — (контракт PRD-0004, не меняется) |

Каскад Р-1 (FR-050) ортогонален наполнению и включён во все уровни теста:
проливание (`server_rate ← Профиль нагрузки`), what-if (`servers 3▸4` →
загрузка 67%→50%), unmapped (`Отчёт_q3.медиа_доля = — не подставлено`).

## 4. Оптимизации восприятия (применимы ко всем вариантам)

Прототип подсвечивает каждую оптимизацию прямо на ноде (ховер по пункту
списка в панели).

| # | Оптимизация | Механика | Зачем |
|---|---|---|---|
| O-1 | **Два шрифтовых слоя** | проза — sans; все строки данных — mono | тип строки опознаётся до чтения; канон Numi/калькуляторов |
| O-2 | **Лидеры-дорожки** | пунктир от формулы к правому краю (паттерн чека/оглавления) | глаз ведёт по строке; столбец значений собирается в «желоб» |
| O-3 | **Табличные цифры + правый желоб** | `tabular-nums`, значения в одной вертикали | вертикальный скан чисел без горизонтальных саккад |
| O-4 | **Юниты приглушены** | мельче и тусклее числа | число читается первым, единица — вторым |
| O-5 | **Синтаксическая подсветка + алиасы** | переменные/функции/операторы — разными весами; в формулах короткие имена (`cps`, `auth`), полные — в строках параметров | формула ≤ 30 символов, читается целиком |
| O-6 | **Бейджи каскада Р-1** | `← Источник` (проливание), `what-if` (переопределение), янтарная строка unmapped | происхождение числа видно без ховера; Р-2 различение шрифтом сохраняется |
| O-7 | **Зебра строк** | чередование фона в прогонах ≥ 4 строк | строка не теряется при вертикальном скане |
| O-8 | **Микро-группы** | заголовки «параметры · N» / «расчёт · N» (или группы в блоке) | якоря сканирования: глаз прыгает по группам, не по строкам |
| O-9 | **Σ-строка + полоса D** | последний акцент листа + всегда-видимый итог | итог доступен на любом наполнении и в компакте |
| O-10 | **Диагностика не сворачивается** | unmapped-строка всегда развёрнута | янтарная проблема не прячется за сворачиванием |
| O-11 | **Пустое состояние без блока** | на L0 блока расчёта не существует | нет мёртвых зон, порог входа SA не растёт |
| O-12 | **Компакт/LOD** | хедер + D; порты у рядов деградируют по контракту PRD-0004 | плотная сцена и дальний зум |

## 5. Три варианта

Общее для всех: хедер-идентичность A (чип категории + имя + статусный
диагностический индикатор), полоса итога D, оптимизации O-1…O-12,
построчные порты FR-025 у рядов и якоря параметров FR-050 Н2 — **ряды
остаются точками привязки рёбер в любом варианте** (в свёрнутом виде Н-3
ребро снапится к заголовку блока/превью).

### 5.1 Н-1 «Сквозной лист» (канон Numi — эволюция сегодняшнего)

**Концепция.** Тело — одна колонка, как в Numi-приложении: проза и строки
данных идут одним потоком. Порядок потока: входящие значения (авто-строки
FR-050, верх тела — как специфицировано) → описание → параметры → расчёт →
Σ. Идентичность строки — шрифтом (O-1), значение — правым желобом (O-2/O-3).
Группы — только микро-метками (O-8), не блоками.

- **Плюсы:** нода читается как документ (сильнее всего на L1/L2);
  текст и формула живут рядом — нарратив «почему → считаем» не рвётся;
  миграция минимальна (сегодня `formula_lines` уже сквозные — это
  typographic-апгрейд, не перестройка); пустое состояние естественно.
- **Минусы:** на L3 — «стена» из 11 строк: без зебры/меток глаз
  проседает (VLM-ревью прототипа подтвердило: «на грани комфортного
  восприятия»); описание не имеет ранга — при длинном тексте числа
  уезжают вниз; нет режима «только числа».

### 5.2 Н-2 «Двухзонная нода» (текст сверху, ведомость снизу)

**Концепция.** Тело делится на две зоны: **C-текст** (описание, заметки,
проза — sans, без чисел) и **C-ведомость** — блок, припёртый к полосе D:
тёмный фон, группы «входящие значения / параметры / расчёт», строки-строки
таблицей с общим желобом значений, Σ-строка. Пустое состояние: блока нет
(O-11).

- **Плюсы:** числа сканируются одним взглядом (сильнейший вертикальный
  скан); описание получает ранг и всегда на месте; текст «не спорит» с
  расчётом — разная типографика зон; лист-структура готова к пучкам/стейджу
  (R-стабильность концов рёбер).
- **Минусы:** нарратив «текст → тут же формула» рвётся (числа всегда
  внизу); на L1 блок из 1–2 формул — «форма ради формы» (лечится O-11,
  но зона всё же появляется раньше, чем нужна); правка «текст ↔ формула
  вперемешку» требует работы в двух зонах; миграция средняя (новая зона
  в анатомии, пиннинг к D).

### 5.3 Н-3 «Адаптивная» (порог выноса — рекомендация)

**Концепция.** Дилемма «сквозные vs блок» решается **не выбором, а
порогом**. Считаем строки данных (параметры + формулы, авто-строки не в
счёт — они диагностика):

- **строк ≤ T** → сквозной лист (Н-1): малое наполнение читается как
  Numi-заметка, нода компактна, блоков нет;
- **строк > T** → система выносит расчёт в ведомость-блок снизу (Н-2),
  а описание **клампится** до 2 строк («⋯ описание целиком ▾»): при
  большом наполнении приоритет взгляда — числа, не проза;
- свёрнутый блок показывает превью: «▸ расчёт · 7 строк · Σ out_gateway =
  800 rps» (клик разворачивает); авто-строки/unmapped остаются снаружи —
  диагностика не сворачивается (O-10);
- порог T — настройка (в прототипе слайдер 2…6; рабочее значение **T=4**:
  L1 (3 строки) — лист, L2 (7) — блок).

- **Плюсы:** каждый уровень наполнения получает свой оптимальный layout;
  пустых мёртвых зон нет; «стены» на L3 нет (блок + кламп описания);
  совместимо с LOD-контрактом (компакт — вырожденный случай того же
  сворачивания).
- **Минусы:** два режима = две механики чтения у пользователя (переход
  происходит при правке — нужен мягкий motion-переход, токены motion.json);
  «правило порога» надо объяснять (обучение: сворачивание происходит
  предсказуемо при добавлении 5-й строки — само объясняет себя);
  миграция = Н-2 + состояние свёрнутости; в свёрнутом виде построчные
  порты недоступны → разворачивание при начале drag от кромки (В-C).

## 6. Матрица сравнения

| Критерий | Н-1 лист | Н-2 двухзонная | Н-3 адаптивная |
|---|---|---|---|
| Читается как документ/заметка (L1/L2) | ✓✓ | ~ | ✓ (до порога) |
| Скан чисел одним взглядом (L2/L3) | ~ | ✓✓ | ✓✓ |
| Пустая нода без мёртвых зон | ✓ | ✓ (O-11) | ✓ |
| L3 не разваливается | ~ (стена) | ✓ | ✓✓ (блок + кламп) |
| Нарратив «текст → тут же формула» | ✓✓ | ~ | ~ (до порога) |
| Построчные порты FR-025 у рядов | ✓ | ✓ | ✓ (свёрнутый — к превью/блоку) |
| Ранг описания «что это» | ✗ (в потоке) | ✓✓ (зона) | ✓ (кламп с разворотом) |
| Диагностика всегда видима | ✓ | ✓ | ✓✓ (O-10 вынесена) |
| Миграция с GFM-потока | низкая | средняя | средняя |
| Новые UI-состояния | нет | зона/пусто-зоны | + свёрнуто/развёрнуто/переход |
| Совместимость с В-А/В-B/В-C | любая | любая | любая (ортогонально) |

## 7. Что показал тест наполнения (прогон прототипа)

Прототип прогнан headless-браузером по всем 3 вариантам × 4 наполнениям,
с каскадом Р-1 и порогом; VLM-ревью скриншотов подтвердило отсутствие
обрезаний/наложений. Наблюдения, которые стоит учесть в решении:

1. **L1 везде хорош** — различия вариантов начинаются с L2. Значит,
   решение «сквозные vs блок» — это решение о **среднем и большом**
   наполнении (L2+), что и делает порог Н-3 содержательным, а не
   косметическим.
2. **L3 в Н-1** — честный предел потока: 11 строк + проза; зебра и
   микро-метки спасают, но «стены» не избегают. VLM: «на грани
   комфортного восприятия; нужны разделители/свёртывание» — это и есть
   эмпирическое обоснование выноса расчёта в блок.
3. **L3 в Н-2/Н-3** — колонка значений собирается, Σ читается, описание
   не мешает. Кламп описания в Н-3 дополнительно возвращает приоритет
   числам (разворот — по требованию).
4. **Каскад Р-1 на плотном теле** — бейджи источника видны без ховера
   (O-6), строка servers `3 ▸ 4` + «what-if»-бейдж + пересчёт utilization
   67%→50% читаются в одну строку; янтарная unmapped-строка не теряется
   среди 11 строк — потому что диагностический цвет сильнее зебры.
5. **Ширина строки данных** — с алиасами (O-5) самая длинная формула
   (`utilization = mm1(cps, rate, srv)`) влезает в 384 px вместе с
   значением и бейджем; без алиасов — не влезает. Алиасы обязательны.

## 8. Рекомендация и открытые вопросы

**Рекомендация:** **Н-3 «Адаптивная» с порогом T=4** — прямое решение
дилеммы владельца: Numi-строки **сквозные, пока их мало** (Numi-канон,
нарратив, компактность), и **отдельным блоком снизу, когда их много**
(ведомость, скан чисел, кламп описания). Н-1 — режим по умолчанию внутри
Н-3; Н-2 — его продолжение. Вливается в любую из порт-моделей В-А/В-B/В-C
(ортогонально) и в анатомию A–E PRD-0004 (зона C получает под-контракт
C-текст/C-ведомость вместо «Numi-лист»).

Открытые вопросы (решение владельца):

## 10. Связь с другими документами и следующий шаг

- **PRD-0004 §16:** анатомия A–E дополняется под-контрактом зоны C
  (C-текст / C-ведомость, порог T, кламп описания) — после выбора Q1–Q7.
- **Редизайн портов (node-edge-redesign-analysis.md):** полностью
  ортогонально; Н-3 × В-C — совместимая пара (свёрнутый блок разворачивается
  drag'ом от кромки — Q7).
- **PRD-0009 / FR-053 (U3-пилоты):** контракт тела нужен кит-этапу U4 —
  Row-виджеты (ведомость), бейдж-виджеты (каскад), кламп-текст (TextMeasurer
  F-6 уже даёт Ellipsis/Clip).
- **FR-050:** позиция авто-строк сохранена (верх тела); Р-2 различение
  шрифтом не конфликтует с O-1 (oblique-моно пролитых поверх mono-слоя).
- Следующий шаг: решение Q1–Q7 → обновление PRD-0004 §16 + FR по
  cr-template (миграция `text.rs`: зона C, кламп, бейджи каскада, зебра,
  Σ-строка; порог T — в settings).
