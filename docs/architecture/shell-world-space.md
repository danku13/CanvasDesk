# Шелл карточки — world-space: архитектура рендера

- **Статус:** документация (по запросу владельца, сессия web-77d836dd, 2026-09-26).
- **Область:** как устроен world-space GPU-путь «шелла» карточек нод, чем он
  отличается от screen-space домена `canvas-ui`, где проходит граница владения
  и почему она именно такая.
- **Связанные:** `docs/plans/fr-061-template-node-kit-alignment.md` (аудит
  вёрстки шаблонных нод, §4 — та же граница кратко), FR-068 W3 §9.4
  (владельческое решение «не мигрировать: канвас-домен»), PRD-0009 (слои UI),
  `docs/ui-kit.md` (инвентарь кита), FR-046 (design-токены).
- **Код:** `canvas-render/src/{camera,cards,zorder,renderer}.rs`,
  `canvas-render/src/shaders/cards.wgsl`, `canvas-ui/src/{paint,frame,layer}.rs`,
  `canvas-app/src/kit_ui.rs`.

---

## 1. Резюме

Карточка ноды рендерится **мимо компонентной модели `canvas-ui`** — это
осознанное архитектурное решение, а не долг миграции. Шелл карточки живёт в
**world-space**: позиция и размер берутся из данных `.canvas`-файла, камера
(zoom/pan) переводит мир в пиксели окна, скругление/тень/рамка считаются SDF во
фрагментном шейдере, а весь кадр карточек — **один instanced draw**. Кит
`canvas-ui` — **screen-space** модель: полосы окна в логических пикселях,
`Painter` собирает примитивы как данные, крейт не знает ни про GPU, ни про
камеру. Перенос шелла на кит означал бы смену системы координат (либо вторую
систему координат внутри кита) — то есть смену архитектуры, а не рефакторинг;
владельческое решение FR-068 W3 §9.4 фиксирует: «не мигрировать: канвас-домен».

При этом граница проведена не «кит против канваса», а **«геометрия против
исполнения»**: чистые геометрические решения табличного тела (направляющие
колонок, замер ячеек, лидер-пунктир, зебра-прогон) принадлежат киту и
потребляются рендером; исполнение (glyphon-текст, GPU-квады, цвет темы)
остаётся у рендера. Экранные поверхности при этом рисуются тем же GPU-пайплайном
— их screen-инстансы конвертируются в world-координаты текущей камеры
обратным преобразованием.

## 2. Два домена координат

| | World-space (канвас) | Screen-space (экран) |
|---|---|---|
| Что измеряет | координаты канваса из `.canvas`-файла | логические px от угла окна |
| Зависит от камеры | да (zoom/pan) | нет (размер константен при любом зуме) |
| Кто владеет | `canvas-render` (+ данные `canvas-core`) | `canvas-ui` (модель) + потребители |
| Исполнение | instanced SDF-квады + glyphon world-текст | Painter-items → сконвертированные инстансы + scissor + TextBounds |
| Примеры | карточки, связи, полосы категорий, иконки, тамбнейлы, таблица тела, порты | панели, модали, тосты, палитра, wheel-меню (геометрия), миникарта (рамка) |

Единицы: camera хранит **логические** screen-пиксели (SPEC §6.5); GPU
работает в **физических**, поэтому шейдеры получают
`effective_zoom = zoom × scale_factor` (`CameraUniform::new`, viewport — тоже
физический). Клампы зума: `MIN_ZOOM = 0.05`, `MAX_ZOOM = 4.0` (SPEC §8).

## 3. Камера: чистая математика world↔screen

`canvas-render/src/camera.rs` — без зависимостей от winit/wgpu, полностью
юнит-тестируемый модуль. Ядро — две взаимно-обратные функции:

```text
world → screen:  (world − camera.position) × zoom + viewport / 2
screen → world:  camera.position + (screen − viewport / 2) / zoom
```

- `position` — мировая точка в центре viewport; `pan(delta_screen)` сдвигает
  центр на `delta / zoom` world-px.
- `zoom_at(factor, anchor, viewport)` — зум к курсору: мировая точка под
  якорем неподвижна (тест `zoom_at_keeps_anchor_fixed`).
- `visible_world_rect(viewport)` — видимый прямоугольник мира; источник
  прямоугольника для culling (T5) и миникарты.
- `set_center` / `set_zoom` — полёт камеры (T14 поиск, T13 миникарта).

Всё остальное в GPU-пути — производные этой пары функций.

## 4. Что входит в «шелл» карточки

«Шелл» — хром карточки, рисуемый **вне** текстового тела. В кадре ноды
(шаблонной или обычной text) шелл составляют:

| Элемент | Строитель (`cards.rs`) | Геометрия |
|---|---|---|
| Карточка: заливка, радиус, тень, рамка selected/broken/group | `card_instance` | `node.x/y/w/h`, радиус `tokens::CARD_CORNER_RADIUS` |
| Рамка серьёзности (FR-016) | `card.border` / `analysis_ring_instance` (внешнее кольцо +3 px) | LOD: рамка ≥ `0.25` zoom, бейджи ≥ `0.6` эффективного zoom |
| Полоса категории шаблона | `template_band_instance` | `TEMPLATE_BAND_H = 6` world-px, цвет — hex-снимок `canvasdesk.template.color` |
| Квад-иконка роли | `template_icon_rect` + `template_icon_quads` | 16×16 world-px у правого края шапки; композиция плоских квадов на сетке `u = w/16` (коды `lb/db/cache/http/queue/gateway/worker/…`) |
| Хром тела | `body_quad_instance` (renderer) | GFM-квады, пилюли бейджей, Σ-линия, авто-строки; радиус/размер делятся на `entry_zoom` — масштаб тела «заморожен» на влёте ноды |
| Порты/якоря | `line_ports` / `param_ports` (text.rs) → world-«хвост» кадра | точки на краях ноды |

**Отдельного «шаблонного» пути вёрстки нет.** Базовый шелл шаблонной ноды
байт-в-байт равен шеллу обычной text-ноды — это пинит регрессионный оракул
`card_instance_template_node_equals_plain_text_node` (cards.rs); полоса и
иконка — декоративные оверлеи поверх `card_instance`, добавляемые в кадре
рендерера (renderer.rs ~1518–1543) при `node.template().is_some()`.

## 5. GPU-путь: instanced SDF-пайплайн

### 5.1 Инстанс

`CardInstance` — 16 f32: `pos` (world), `size` (world), `fill`, `border`,
`params` (`x` — радиус world-px; `y` — selected; `z` — broken; `w` — флаг
«без тени» для мелких квадов связей/портов, T8). Инстансы кадра собираются
чистыми функциями-строителями в `Vec<CardInstance>`, сегментируются по
z-плану и заливаются одним `queue.write_buffer` в instance-буфер
(стартовая ёмкость 256, рост `next_power_of_two`).

### 5.2 Вершинный шейдер (cards.wgsl)

Единичный квад из 6 вершин на инстанс; тень выступает за край, поэтому квад
расширяется на `margin = 12 / effective_zoom` (тень фиксированной ширины на
экране при любом зуме). Далее вершинный шейдер повторяет формулу камеры:

```wgsl
fn world_to_screen(world) { return (world − camera.position) × effective_zoom + viewport × 0.5; }
clip = screen / viewport × (2, −2) + (−1, 1)
```

### 5.3 Фрагментный шейдер

SDF скруглённого прямоугольника `sd_rounded_box` в **физических** px:

- **слои**: тень → заливка → рамка, композит альф по `over`;
- **тень**: тот же SDF со смещением `(0, 2)` и размытием `smoothstep(−4, 6)`,
  сила `0.35`, гасится `params.w`;
- **антиалиасинг**: `aa = max(fwidth(sd), 1)` — производная SDF даёт ровную
  кромку на любом зуме без MSAA;
- **рамки** по приоритету: selected (полоса `|sd| ≤ 1.5` ≈ 2 px) → broken
  (`|sd| ≤ 0.75` ≈ 1 px) → оверлейная `border.a` (зоны дропа T9, пульс T14);
- радиус скругления `params.x × effective_zoom` — world-постоянство формы.

### 5.4 Почему один draw на весь кадр

Instancing: `CardsPipeline::draw_range(pass, range)` — один пайплайн, один
vertex-buffer, `pass.draw(0..6, range)`. Диапазоны инстансов вырезает z-план
(§6), поэтому карточки, тамбнейлы и текст чередуются по z без смены пайплайна.
Альтернатива «геометрия на ките → покадровая конвертация» потеряла бы и
instancing, и SDF-хром (см. §9).

## 6. Порядок кадра: z-сегменты и хвосты

`zorder.rs` — чистая логика, z-порядок = порядок нод в `Canvas.nodes`
(выдача spatial index отсортирована; group-ноды стабильно выносятся вперёд).
Проблема, которую решает сегментация: сплошные проходы «все карточки → все
тамбнейлы → весь текст» клали тамбнейл фоновой ноды поверх карточек
переднего плана. Решение — кадр бьётся на сегменты:

```text
кадр (один render pass)
├─ сетка (grid.wgsl, world)
├─ связи (инстансы карточек-линий: edges_end)
├─ для каждого z-сегмента:  карточки → тамбнейлы → текст-группа (glyphon)
├─ world-хвост: порты hover-ноды, резиновая линия, подложки лейблов
├─ screen-полосы (kit-поверхности): инстансы → scissor-бакет → текст TextBounds
├─ main stage (FR-042/044), wheel-сектора (FR-022)
└─ минимапа, SVG-иконки (FR-ICONS), HUD
```

Хвостовые диапазоны планирует `zorder::plan_tail_ranges` — регрессия 136e9fb
(квады, не вошедшие ни в один диапазон, исчезали) пинится тестами.

## 7. Текст: world-space glyphon и screen-space полосы

Текст тела нод — world-space: шейп cosmic-text → glyphon-буферы, кэш по нодам
(T5), покадрово рисуются только видимые. Кегли заданы в world-px — заголовок
пропорционально зумится вместе с карточкой. Текст-группы z-плана (пул
`TextRenderer`) рисуются посегментно между карточками.

Тексты экранных полос — отдельная overlay-группа: origin в логических px,
клип — `TextBounds` (scissor на текст не тратится, renderer.rs §band_scissor_rect).

## 8. Screen-space домен и мост в единый пайплайн

`canvas-ui` — **модель экрана** (PRD-0009 U1): реестр поверхностей
(`SurfaceRegistry`, слои `UiLayer`, capture-политики), `HitStack`,
`KeyboardRouter`, layout-примитивы, `TextMeasurer`, `Painter`. Инварианты:
**G7** — ноль внешних/GPU-зависимостей (всё headless-тестируемо) и **F-8** —
кит не рисует и не смешивает цвета; он выдаёт данные.

Мост «модель → пиксели»:

```text
компоненты кита (canvas-app)
  → PaintItem-журнал Painter (Rect/Text/Icon/ClipRect/ZGroup)
  → KitDraw (kit_ui.rs) конвертирует: Rect → CardInstance в ЛОГИЧЕСКИХ px окна
  → renderer: screen_instance_to_world(camera, viewport, inst)
      pos = screen_to_world(pos); size / zoom; params.x / zoom
  → тот же cards-пайплайн, те же SDF-шадеры
```

Обратная конвертация (renderer.rs:209) даёт ровно обратное свойство: экранная
полоса имеет **постоянный размер на экране при любом зуме** — деление на zoom
компенсирует world→screen-масштаб шейдера. Клипы полос исполняются
`band_scissor_rect` (ceil сверху/слева, floor снизу/справа — scissor никогда не
расширяет видимое, FR-056). Wheel-меню (FR-022) идёт тем же мостом:
hit-test — screen-space, рендер секторов — `screen_sector_to_world`.

Итог: **исполнение (GPU) — одно на оба домена; домен различается тем, кто и в
каких координатах строит инстансы**.

## 9. Почему шелл не пересобирается на kit (владельческое решение)

Краткий ответ — FR-068 W3 §9.4: «карточки … канвас-домен
(`canvas-render::cards`), рендерятся квадами по нодной геометрии; компонентная
модель — для экранного UI, не для world-space контента». Разъяснение
(fr-061 §4, §5):

1. **Система координат.** Кит — полосы окна в логических px; карточка —
   данные мира под камерой. «Пересобрать на kit» = завести в ките вторую
   систему координат (world-слоты, камера, LOD) или конвертировать каждый квад
   через камеру на стороне потребителя — в обоих случаях это новая
   архитектура, а не перенос.
2. **Контракт кита.** Кит не владеет исполнением: ноль GPU-зависимостей (G7),
   цветовая арифметика — у потребителя (F-8). World-band рендер внутри кита
   нарушил бы оба инварианта.
3. **Перф/семантика.** Один instanced draw на кадр карточек; SDF-хром
   (тень/AA) без покадровой геометрии; кэш glyphon-текстов по нодам; LOD по
   мировому зуму (`ANALYSIS_BORDER_MIN_ZOOM 0.25`, `ANALYSIS_BADGES_MIN_ZOOM
   0.6`, `THUMB_MIN_ZOOM`). Кит-путь всё это дублировал бы без визуальной
   разницы.

Что потребовала бы полная миграция (non-goal до решения владельца):
**camera-aware kit** (world-слоты + камера + LOD внутри UI-крейта), **world-band
Painter-бэкенд** (кит начал бы владеть GPU), **перенос текста тела** на
экранную модель (потеря кэшей и мировых кеглей).

## 10. Граница владения: «единая геометрия, разные исполнения»

Срез не «кит ↔ канвас», а «геометрия ↔ исполнение». Кит владеет чистыми
геометрическими решениями, рендер и экранные поверхности — исполнением и
цветом:

| Решение | Владелец (геометрия) | Потребители |
|---|---|---|
| Направляющие колонок таблицы (проход A/B) | `canvas_ui::row_guides::RowGuides` | `row_grid.rs`/`text.rs` (world) и kit-Table v2 (screen) |
| Замер ячеек | `row_guides::measure_row_cells` + `TextMeasurer::width_of_weighted` | оба домена |
| Лидер-пунктир | `canvas_ui::kit::leader_dash_rects` | оба домена |
| Зебра-прогон | `canvas_ui::kit::zebra_run_flags` | `text.rs` (цвет — тема рендера, F-8) |
| Пад бейджа, ellipsis | `kit::ROW_BADGE_PAD_H`, `TextMeasurer::ellipsis_weighted` | оба домена |
| Радиус/шапка/акценты карточки | design-токены `canvas_core::tokens` | кит и рендер (единый источник, FR-046) |

Исполнение (glyphon-буферы, GPU-квады, SDF, цвет темы) — у потребителей:
canvas-render для канваса, canvas-app (KitDraw → renderer) для экрана.
Эта граница зафиксирована аудитом fr-061 и уточнением §9.4 каталога
миграции: правило «не мигрировать» касается **шелла** (world-space, камера +
instanced SDF); **геометрия тела ноды** при этом живёт на ките.

## 11. Инварианты, которые держит архитектура

- **I-z (z-порядок)**: текст/тамбнейл ноды никогда не поверх карточек
  переднего плана — сегментация z-плана (тесты zorder.rs).
- **I-шаблон (оракул равенства)**: шаблонная нода не имеет собственного
  шелл-пути — равенство с text-нодой пинится тестом.
- **I-экран (константность)**: screen-полосы не зумятся — `size/zoom` в
  `screen_instance_to_world` компенсирует шейдерный масштаб.
- **I-scissor (FR-056)**: scissor только сужает видимое; пустое пересечение —
  полоса не рисуется.
- **I-LOD (FR-016)**: декор шелла гасится по мировому/эффективному зуму —
  логика живет рядом с мировыми константами, не в ките.
- **I-токены (FR-046)**: формы/цвета карточки — `canvas_core::tokens`, у кита
  и рендера один источник значений.
