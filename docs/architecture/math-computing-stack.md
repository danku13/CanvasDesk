- **Статус:** принято (решение владельца 2026-09-18 — вместе с ADR-0008; продуктовая последовательность внедрения этапов — `docs/plans/product-roadmap.md`)

- **Автор:** агент (анализ и проектирование, по прямому запросу владельца)
- **Связанные:** ADR-0007 (pivot — визуальная система математического моделирования), ADR-0002 (поток значений), ADR-0003 (порты значений), ADR-0004 (агентная композиция через MCP), ADR-0005/0006 (эталонные сценарии), CR-013, FR-013/014/015/025/027/029; `docs/SPEC.md` §3–4, §6.3
- **Краткая запись решения:** `docs/adr/adr-0008-math-computing-stack.md`
- **База аудита:** коммит `71f483b` (main), Cargo.lock репозитория; лицензии зависимостей и кандидатных библиотек проверены через crates.io API 2026-09-17 (скрипты аудита: `license_audit.py`, `candidate_licenses.py`)

## 1. Назначение и границы

Этот документ описывает вычислительную подсистему CanvasDesk — то, что делает продукт
**визуальной системой математического моделирования** (позиционирующий контракт ADR-0007):
применение математических и статистических библиотек, организацию параллельных вычислений
и лицензионную обвязку, необходимую для превращения сервиса в B2B-продукт и регистрации
в реестре российского ПО (Постановление Правительства РФ № 1236). Документ отвечает на три
вопроса: из чего состоит счёт сегодня (факты с код-ссылками), какой стек нужен концепту
(слои, библиотеки, параллелизм) и как при этом сохранить лицензионную чистоту.

Границы документа — расчётное ядро `canvas-core` (язык формул, единицы, доменные функции,
DAG-поток значений, шаблоны) и его обвязка. Вне границ: рендер (`canvas-render`),
shell-интеграция, UI-волны (палитры, онбординг), MCP-инструменты как таковые (адресация
портов — ADR-0003/FR-029). Документ не заменяет CR/FR: конкретные шаги внедрения
оформляются отдельными FR (нумерация — с FR-032, см. `docs/change-requests/index-cr-fr.md`).

Продуктовые требования, из которых исходит архитектура:

| Требование | Источник | Что диктует вычислительному ядру |
|---|---|---|
| «Один шаблон = один расчёт», композиция проливанием значений | ADR-0002, CR-013 | Чистые функции, DAG-семантика, отсутствие побочных эффектов в eval |
| Эталоны №1–№5 (system design, бюджет, P&L, value chain, unit economics) | ADR-0006 | Расширяемый реестр доменных функций, сценарность, чувствительность |
| What-if / сценарии / чувствительность | FR-017, ADR-0006 №2–№5 | Пакетное переисполнение графа → параллелизм уровня «сценарий» |
| Live-ревал в пределах кадра | FR-014, `SPEC.md` §6.3 | Бюджет пересчёта ≤ 1000 нод < 10 мс; вынос тяжёлых режимов с главного треда |
| B2B-продукт + реестр российского ПО | запрос владельца | Лицензионный allowlist без copyleft, SBOM, third-party notices, воспроизводимость сборки |

## 2. Текущее состояние расчётного ядра (факты на `71f483b`)

### 2.1. Состав и объём

Весь счёт — собственный код в `canvas-core` (не зависит от ОС и GPU, SPEC §4):

| Модуль | Строк | Назначение | Ключевые факты |
|---|---|---|---|
| `src/expr.rs` | 2470 | Язык формул `canvasdesk.expr` (Numi-base): парсер, арифметика, единицы, переменные, `sum/avg/max/min/percentile` | Чистый Rust без I/O и глобального состояния (инварианты 1/2 FR-013); `f64` + размерная система `Dimension`/`Atom`/`Unit` (Time, Rate, Count, Bytes, Money, Percent, Custom); композитные единицы (`ms·req/s`) |
| `src/expr/queueing.rs` | 467 | Доменные функции: `utilization`, `mm1`, `mmc`, `littles_law`, `erlang_c` (FR-015) + `npv`, `cagr`, `irr`, `cohort_ltv` (FR-027 v1) | Чистые функции `(&str, &[Value]) -> Result<Value, EvalError>`; перегрузка ρ ≥ 1 → `EvalError::Overload`; лимит `MAX_SERVERS = 1000` |
| `src/flow.rs` | 1076 | DAG-движок потока значений (FR-014): топосортировка, детект циклов (SCC), позиционные слоты `$in`/`$1..$N`, построчные выходы `FlowSolutions.lines` (FR-025) | Полный пересчёт `propagate_with_lines` за один обход; live-инвариант — пересчёт в пределах кадра |
| `src/templates.rs` | 1304 | Реестр шаблонов: манифесты `params` + `expr`, снапшоты `TemplateRef` | 45 builtin-манифестов вшиты `include_dir!` (15 инфраструктурных + 18 UE + 12 PA) |
| `src/model.rs` | 1500 | Модель канваса: `Node`/`Edge`, `Edge::from_line` (FR-025), сериализация `.canvas` | Value-рёбра отделены от обычных связей (`FlowKind`) |

Прямые зависимости `canvas-core` (Cargo.toml): `include_dir`, `rstar` (R-tree для
пространственного индекса), `serde`, `serde_json`, `thiserror`, `toml`, `tracing`.
**Математических библиотек нет — вся математика написана с нуля** и остаётся собственным
кодом продукта. Это исторически сложившееся свойство, и оно стратегически ценно: ядро не
тянет ни одной транзитивной лицензии и ни одной C-зависимости.

### 2.2. Численные методы, уже реализованные

Ядро уже содержит нетривиальную численную работу, выполненную с оглядкой на устойчивость:

- **Erlang-C через рекуррентную Erlang-B** (`queueing.rs:194-201`): `B(n, a) = a·B(n−1, a)/(n + a·B(n−1, a))`,
  `B(0) = 1`; `C = B / (1 − ρ·(1 − B))`. Рекуррентность выбрана вместо факториалов —
  численно устойчива при любом `c` (решение FR-015 «Открытые вопросы»).
- **Newton-Raphson для IRR** (`queueing.rs:335-389`): старт r₀ = 0.1, клампинг шага ±0.5,
  защита r ≤ −0.99, лимит 100 итераций, допуск 1e-7; предусловие смены знака потоков.
- **Интерполяция retention-кривой** для `cohort_ltv` (`queueing.rs:396-453`): линейная
  интерполяция между опорными точками d0/d1/d7/d30 + экспоненциальное затухание после d30.
- **Размерная алгебра**: конверсия единиц через `scale`, символическое слияние/сокращение
  размерностей при умножении/делении, проверка одной размерности в доменных функциях.

### 2.3. Модель исполнения: однопоточность на главном треде

Полный пересчёт выполняется синхронно на главном (UI) треде после любой мутации формул
или топологии: `canvas-app/src/main.rs` → `recompute_flow` (строки ~607–641) — комментарий
в коде фиксирует бюджет «полный пересчёт ≤ 1000 нод < 10 мс (SPEC §6.3)». В `canvas-core`
нет ни `std::thread`, ни `rayon`, ни каналов; параллелизм в дереве зависимостей присутствует
только транзитивно: `rayon@1.12.0` попадает в Cargo.lock через `cosmic-text` (шейпинг текста),
продуктовый код его не использует. Для текущей нагрузки (эталонные модели — десятки нод,
эксплуатационный предел — 1000) этой модели достаточно; она перестаёт быть достаточной
для сценарных/Monte-Carlo режимов (§5.4–5.5), поэтому параллелизм закладывается как этапная
эволюция, а не немедленная переделка.

### 2.4. Что уже đúng по лицензионной части

- `Cargo.lock` закоммичен — версии воспроизводимы (`cargo build --locked`).
- Шрифты Noto Sans Display/Mono вшиты вместе с текстами лицензий SIL OFL 1.1
  (`assets/fonts/OFL-NotoSansDisplay.txt`, `OFL-NotoSansMono.txt`) — обязательства
  OFL при встраивании в ПО выполняются уже сейчас.
- Криптографических зависимостей в дереве нет (проверено по Cargo.lock: отсутствуют
  `ring`, `rustls`, `openssl`, `aes`, `hmac`, `rsa` и т. д.) — нет и повода для
  уведомительного порядка ФСБ в отношении средств криптографии.
- Единственная нативная библиотека — SQLite, вшита feature-флагом `bundled`
  (`rusqlite`); SQLite — public domain, обязательств не создаёт.

## 3. Целевая слоистая архитектура вычислений

Расчётная подсистема строится слоями; каждый слой может зависеть только от нижележащих.
Это позволяет внедрять библиотеки поэтапно и держать лицензионный периметр управляемым.

```
┌────────────────────────────────────────────────────────────────────┐
│  L5  Обвязка качества: детерминизм, golden-тесты, SBOM, лицензии,  │
│      third-party notices, воспроизводимая сборка (--locked)        │
├────────────────────────────────────────────────────────────────────┤
│  L4  Параллельный исполнитель: worker-тред + double buffer,        │
│      поярусный (topo-level) параллелизм, Monte-Carlo движок        │
├────────────────────────────────────────────────────────────────────┤
│  L3  Линейная алгебра (по потребности): ndarray / nalgebra / faer  │
├────────────────────────────────────────────────────────────────────┤
│  L2  Численно-статистический слой: распределения (statrs), RNG     │
│      (rand+rand_distr+rand_chacha), квадратуры (gauss-quad),       │
│      спецфункции (puruspe/special), корни и подгонка кривых        │
│      (argmin / levenberg-marquardt)                                │
├────────────────────────────────────────────────────────────────────┤
│  L1  Реестр доменных функций: queueing (FR-015) → finance (FR-027) │
│      → statistics / scenarios / Monte Carlo (этот документ)        │
├────────────────────────────────────────────────────────────────────┤
│  L0  Числовое ядро (собственный код): f64, размерная система,      │
│      парсер/eval `canvasdesk.expr`, DAG-поток (topo + SCC)         │
└────────────────────────────────────────────────────────────────────┘
```

- **L0 — числовое ядро** — остаётся собственным кодом и единственным исполнителем формул.
  Внешний DSL или embed-движок (Lua/Python/WASM-скрипты) отвергнуты (§4.3): это ломало бы
  «один шаблон = один расчёт» (чистота и анализируемость формул), тянуло бы рантайм и
  усложнило бы реестровую экспертизу. Изменения L0 минимальны: расширение реестра функций
  и (для сценариев) — способ передавать в `Env` набор параметров «сценарий» без мутации модели.
- **L1 — реестр доменных функций** — уже оформлен как `dispatch(func, &[Value])`
  (`expr/queueing.rs:37`): единая точка arity-проверки и диспетчеризации. Новые домены
  добавляются новыми модулями `expr/<домен>.rs` с тем же контрактом чистых функций
  (предложение FR-027 о `expr/finance.rs` остаётся в силе; следом — `expr/stats.rs`).
- **L2 — численно-статистический слой** — библиотеки, обёрнутые в чистые доменные функции
  реестра L1. Пользователь формул не видит крейтов — он видит функции `normal_quantile(...)`,
  `npv(...)`, `lpmc(...)`. Обёртки обязаны сохранять семантику единиц L0 (аргументы
  в размерностях, ошибки — `EvalError`).
- **L3 — линейная алгебра** — подключается только при появлении задач, которые не
  выражаются скалярной алгеброй: многомерная чувствительность (Якобианы), подгонка
  кривых регрессией, марковские модели доступности. До такого запроса — не тянуть.
- **L4 — параллельный исполнитель** — этапная модель (§5): сначала вынос пересчёта с
  главного треда, затем поярусный параллелизм, затем Monte-Carlo движок. Требование ко всем
  этапам одно: результат исполнения не зависит от числа потоков (детерминизм, §5.6).
- **L5 — обвязка качества** — сквозные процессы (§7–§8): контроль лицензий в CI, генерация
  third-party notices, SBOM, golden-тесты чисел эталонов (практика ADR-0006 «Валидация»).

## 4. Реестр отбора математических и статистических библиотек

### 4.1. Критерии допуска зависимости в вычислительный контур

1. **Лицензия** — только из пермиссивного allowlist (§7.2); copyleft в любом виде
   (GPL/AGPL/LGPL как обязательная лицензия) — отказ. Дуальные лицензии допустимы, если
   пермиссивная опция выбирается явно и фиксируется в реестре зависимостей.
2. **Pure Rust / без нативных C-зависимостей** — сборка не должна требовать системных
   библиотек или компилятора C (кроме уже принятого `rusqlite`/`bundled` и toolchain-
   -level `cc` для сборки SQLite). Нативные C-библиотеки (BLAS/LAPACK и пр.) — отказ:
   усложняют воспроизводимую сборку, кросс-компиляцию и экспертизу кода.
3. **Без криптографии** — библиотеки с криптографическим ядром не допускаются в продукт
   (политика §7.5).
4. **Транзитивная чистота** — дерево зависимостей кандидата проверяется на копyleft и
   нативные зависимости до принятия (инструменты §7.6, практика: настоящий аудит).
5. **Поддерживаемость** — живой репозиторий, семверные релизы; кандидат без релизов
   в сопровождении принимается только как временный с фиксацией версии в `Cargo.lock`.
6. **Прописка в workspace** — версии всех новых зависимостей централизуются в
   `[workspace.dependencies]` корневого `Cargo.toml` (конвенция SPEC §3, уже соблюдается);
   включение — через cargo-фичи, чтобы B2B-сборка могла отключить неиспользуемые слои.

### 4.3. Отвергнутые варианты (и почему)

| Вариант | Причина отказа |
|---|---|
| Внешние embed-движки формул (Lua, Python/PyO3, WASM-скрипты) | Чужой рантайм в продукте; разрыв контракта «один шаблон = один расчёт» (формулы перестают быть статически анализируемыми); лицензионная и реестровая нагрузка; недетерминированность окружений |
| C/C++ численные библиотеки: `nlopt` (LGPL), `Ipopt` (EPL), OpenBLAS/netlib BLAS | Copyleft или слабый копyleft; системные нативные зависимости → хрупкая сборка, сложность экспертизы кода реестром |
| Python-ядро (numpy/scipy поверх PyO3) | Иностранная среда исполнения в составе B2B-продукта, удвоение стека, лицензионная обвязка дистрибутива CPython, невозможность single-exe (FR-008) |
| GPU-вычисления (compute-шейдеры wgpu) для матмоделирования | Недетерминизм плавающей точки между GPU-вендорами ломает воспроизводимость эталонов; CPU-потребности домена (≤1000 нод, аналитические формулы) на порядки ниже доступного параллелизма; wgpu остаётся только рендером |
| `polars` / табличные движки | Продукт не работает с табличными датасетами; возвращаться к вопросу только при появлении домена «данные» |
| Копyleft-зависимости «с изоляцией в процессе» | Для статически линкуемого Rust-продукта изоляция копyleft-кода процессом не снимает обязательств раскрытия производной программы; усложнение дистрибуции без лицензионной выгоды |

## 5. Параллельные вычисления

### 5.1. Принцип: чистота функций делает параллелизм безопасным по построению

Оценка одной ноды — чистая функция `(&Expr, &Env) -> Result<Value, EvalError>`: без I/O,
без глобального состояния, без мутации графа. Значит, узел уровня конкурентности — не
строка кода, а **узел графа**: любые два узла одного яруса топологической сортировки
независимы по построению, их можно считать в любом порядке и в любом числе потоков с
одинаковым результатом. Отсюда же требование детерминизма (§5.6): порядок обхода и
приведение результатов фиксируются, чтобы число потоков влияло только на время, а не
на числа на канвасе.

### 5.2. Этап P1 — вынос пересчёта с главного треда (worker + double buffer)

**Статус: реализовано (FR-064 P1/P2, 2026-09-24 — `canvas-scene/src/worker.rs`,
`SceneState::recompute_flow`/`apply_flow_pair`, `AppEvent::FlowReady`).**
Этап не добавляет зависимостей (только std):

- вычислительный воркер (один `std::thread` + `mpsc`) получает immutable-снимок графа
  (`Arc<Canvas>`) и подмены, исполняет `propagate_with_lines` и возвращает
  `Result<FlowSolutions, CycleError>`; паника вычисления ловится (`catch_unwind` —
  воркер жив), wake-up UI-треда — существующий паттерн `EventLoopProxy<AppEvent>`
  (`AppEvent::FlowReady { solutions, kind }`, desktop-only; на wasm — sync-путь);
- результаты публикуются двойной буферизацией `Arc<RwLock<FlowSolutions>>` v1
  (без `arc_swap`; `arc_swap` — опция v2 по бенчмарку): публикацию снимков и выводку
  O(N) выполняет конвейер пересчёта на UI-треде атомарно (единый редактор —
  `apply_flow_pair`), что исключает torn-frame — рендер никогда не видит свежий
  снимок со старыми производными кэшами; запросы несут поколение — устаревшие
  ответы воркера отбрасываются;
- live-инвариант сохраняется: правка формулы → депеша на воркер → публикация в пределах
  1–2 кадров при текущем бюджете (<10 мс на 1000 нод); таймаут 3 с → sync-фолбэк;
- деградация при отказе/таймауте/панике воркера — возврат к синхронному пересчёту на
  главном треде + `warn` (правило AGENTS «фолбэк + warn»; результат побитово
  идентичен — golden-тесты `worker_smoke.rs`).

### 5.3. Этап P2 — поярусный параллелизм DAG

Ярусы топосортировки (`flow::topo_sort`) — готовая карта независимости: уровень `k`
зависит только от уровней < `k`. Внедрение:

- v1 этапа — `std::thread::scope` на ярус (без новых зависимостей): узлы яруса
  распределяются по `n = min(cores, ярус)` потокам; барьер между ярусами.
- v2 этапа — `rayon` (`par_iter` по узлам яруса), когда профилирование покажет,
  что накладные расходы спавна потоков на типичных ярусах (десятки узлов) заметны.
  `rayon` уже находится в дереве зависимостей (транзитивно), поэтому прямое включение
  не добавляет новых лицензий.
- Оценка масштабируемости: для ≤ 1000 нод и аналитических формул полный пересчёт
  уже < 10 мс; поярусный параллелизм даёт выигрыш прежде всего тяжёлым режимам —
  сценарным пакетам и Monte Carlo, а не одиночному ревалу.

### 5.4. Этап P3 — сценарный движок и Monte Carlo (пакетное переисполнение)

Сценарность — прямое требование эталонов: what-if/override (FR-017), чувствительность
№3 (±20 % конверсии), сходимость экономики №5, цена бездействия №2 (ADR-0006). Пакет
прогонов — «embarrassingly parallel» задача: M независимых исполнений одного графа
с разными наборами параметров:

- **Сценарии (v1):** сетка override-наборов (например, rps × {1000, 1500, 2000}) →
  M полных пересчётов → таблица deltas. Полный пересчёт чист и иммутабелен к графу,
  поэтому прогоны распределяются по потокам без синхронизации.
- **Monte Carlo (v2):** параметры с распределениями (L2: `statrs`/`rand_distr`) →
  N ≥ 10⁴ прогонов → квантили выходов (P50/P90/P99) как новые типы результатов нод.
  Для чувствительности — QMC-последовательности Соболя (`sobol_burley`) при том же N
  дают меньшую дисперсию оценок.
- **Стабильная память/нагрузка:** прогоны чанкуются (например, по 256 прогонов на задачу),
  чтобы UI оставался отзывчивым и результаты публиковались прогрессом.

### 5.5. Инкрементальность

Между этапами действует правило: инкрементальность — оптимизация поверх того же
детерминированного исполнения, а не отдельная семантика. Механизм: грязное множество
узлов (правка формулы/параметра, изменение входов) → пересчёт только зависимого
подграфа по обратным рёбрам DAG; кэш результатов валидируется ключом
`(formula, params, inputs-hash)`. Полный пересчёт остаётся эталоном для тестов:
инкрементальный путь обязан давать побитово те же числа (golden-тесты ADR-0006).

### 5.6. Детерминизм — контракт уровня продукта

B2B-клиент и реестровая экспертиза должны получать одинаковые числа из одинаковой
модели. Контракт:

1. фиксированный порядок обхода рёбер (порядок `canvas.edges` — уже инвариант слотов `$1..$N`);
2. сидированная случайность: детерминированный вывод сида из хэша содержимого модели +
   seed сценария; один seed → одна выборка (воспроизводимость прогона);
3. отсутствие неблокирующих float-редукций: параллельные агрегаты собираются в
   фиксированном порядке (collect-then-reduce), а не через конкурентное накопление;
4. версия движка в метаданных модели (расширение формата `.canvas` — отдельный FR);
5. все числа эталонов ADR-0005/0006 закрепляются юнит-тестами и прогоняются в CI
   как на однопоточном, так и на параллельном пути исполнения.

### 7.2. Allowlist / Denylist

**Allowlist (разрешено в прод-зависимостях):** `MIT`, `Apache-2.0`, `BSD-2-Clause`,
`BSD-3-Clause`, `ISC`, `Zlib`, `Unicode-3.0`, `CC0-1.0`, `Unlicense`, `BSL-1.0`, `0BSD`,
и их OR-комбинации. Для OR-комбинаций с copyleft-опцией — выбор пермиссивной опции
фиксируется в реестре зависимостей.

**Denylist (запрещено в прод-зависимостях):** `GPL-2.0/3.0`, `AGPL-3.0`, `LGPL-2.1/3.0`,
`MPL-2.0`, `EPL-1.0/2.0`, `CDDL`, `EUPL`, а также «non-commercial»/«educational»
ограничительные лицензии (CC-BY-NC и производные). Для dev-зависимостей (тесты, бенчи)
Denylist тот же — дерево всё равно попадает в SBOM и будет предъявляться экспертизе.

### 7.3. Обязательства по пермиссивным лицензиям

Пермиссивность не означает «ничего не надо делать». Продукт обязан: (а) сохранять
уведомления об авторских правах и тексты лицензий всех распространяемых компонентов —
генерируемый `THIRD-PARTY-NOTICES` (§7.6) поставляется в дистрибутиве и прикладывается
к заявке реестра; (б) для Apache-2.0 — учитывать NOTICE-механику и патентную оговорку
(патентный грант отзывается при патентных исках — риск для продукта отсутствует,
пока CanvasDesk не судится по патентам с контрибьюторами); (в) для OFL-шрифтов —
не продавать шрифты как самостоятельный продукт и сохранять тексты лицензий
(уже выполняется, §2.4).

### 7.4. Шрифты и ассеты

`assets/fonts/NotoSansDisplay-*`, `NotoSansMono-*` — SIL OFL 1.1 с приложенными
лицензионными текстами. OFL явно разрешает встраивание и распространение шрифтов
в составе программного обеспечения (в т. ч. коммерческом) при сохранении лицензионного
текста — условия соблюдены. Новые ассеты (иконки, демо-данные) принимаются только
с совместимой лицензией, зафиксированной рядом с файлом.

### 7.5. Криптография

Политика: **не вводить криптографические средства в состав продукта без отдельного
решения владельца**. Причины: (а) в РФ применение/распространение средств криптографии
может попадать под уведомительный порядок ФСБ (ЭККО) — лишний контур для B2B и реестра;
(б) лицензионный периметр крипто-крейтов (`ring`: ISC-подобная с оговорками OpenSSL,
BoringSSL-наследие) требует отдельного разбора. Текущее дерево чисто (§2.4); если
появится потребность (например, лицензионные ключи B2B) — сначала ADR, потом зависимость.

### 7.6. Инструменты контроля (L5)

- **`cargo-deny`** в CI: `deny.toml` с allowlist §7.2 + запрет copyleft; проверка на
  каждый PR — регрессия лицензий становится невозможной молча.
- **`cargo-auditable`**: встраивание списка крейтов с версиями в релизный бинарник
  (SBOM-in-binary) — аудируемость B2B-инсталляций.
- **`cargo-about`** (или эквивалент): генерация `THIRD-PARTY-NOTICES` из дерева
  зависимостей; файл пересобирается релизным пайплайном и поставляется в дистрибутиве.
- **RustSec** (`cargo-audit`): контроль известных уязвимостей зависимостей — стандартное
  ожидание корпоративных покупателей.
- Правило принятия новой зависимости: PR обязан содержать проверку дерева кандидата
  (`cargo tree`/`cargo deny check`), фиксацию выбора опции для дуальных лицензий и
  запись в реестре зависимостей (раздел этого документа или отдельный реестр).

### 8.3. Что пермиссивные open-source зависимости дают заявке

Открытые компоненты не запрещены реестром — заявитель обязан подтвердить права на их
использование и (по запросу оператора) идентифицировать их в составе ПО. Пермиссивные
лицензии (MIT/Apache-2.0/BSD) это подтверждают тривиально: право использования,
модификации и коммерческого распространения предоставлено всем при минимальных
обязательствах (уведомления). Copyleft-компоненты формально тоже допустимы, но для
B2B-продукта с закрытой разработкой создают риск обязательства раскрытия производной
программы (в экосистеме Rust линковка практически всегда статическая — классическая
«слабая» LGPL-стратегия динамической линковки не работает) и потому исключены политикой.
Итог: лицензионная чистота дерева — прямое конкурентное преимущество и при регистрации,
и при продаже B2B-клиентам с аудитом поставщиков.

6. Составить описание функциональных характеристик в терминах реестра (класс ПО,

7. Проверить актуальную редакцию правил реестра и перечень требований заявки на
   reestr.digital.gov.ru на дату подачи.

## 9. Дорожная карта внедрения

Этапы не создают CR/FR сами по себе — каждый шаг оформляется отдельным FR (нумерация
с FR-032) и проходит обычные гейты. Порядок выбран так, чтобы лицензионная обвязка
(L5) и библиотеки (L2) вводились раньше параллелизма (L4): чистоту дерева выгодно
закрепить до роста числа зависимостей.

**Продуктовое время этапов** (решение владельца 2026-09-18, совместно с принятием
этого документа): M0–M1 — волна 0 / параллельный трек (без дедлайна); M2 — волна S;
M3 разделён — семантика сценарных сеток уходит в волну B (синхронный пересчёт,
дёшево), worker-тред с двойной буферизацией — в волну S; M4/M5 — волна S после
гейта востребованности «≥ 5 вернувшихся внешних пользователей». Технические
зависимости между этапами (M2 → M3 → M4/M5) сохраняются. Полная
последовательность и триггеры — `docs/plans/product-roadmap.md` (§5 — таблица
привязки).

| Этап | Содержание | Зависимости вводит | Критерий готовности |
|---|---|---|---|
| M0. Лицензионный каркас | `deny.toml` + cargo-deny в CI; THIRD-PARTY-NOTICES; `rust-toolchain.toml`; SBOM-рецепт | нет (только dev-инструменты) | CI падает на копyleft-зависимости; notices генерируются; сборка `--locked` документирована |
| M1. Реестр зависимостей + фича-флаги | Раздел реестра зависимостей в этом документе (или отдельный файл), cargo-фичи `stats`, `parallel` | нет | Все прямые зависимости `canvas-core` перечислены с лицензиями и выбором опций |
| M2. `expr/stats.rs` (L2) | `statrs` + `rand`/`rand_chacha`/`rand_distr`: нормальное/логнормальное/экспоненциальное/пуассоновское распределения, квантили, доверительные интервалы; детерминированный сид | `statrs`, `rand*` | Golden-тесты распределений; формулы доступны в шаблонах; все лицензии в allowlist |
| M3. Сценарный пакет (L4, v1) | Override-наборы FR-017 через пакетное переисполнение; вынос пересчёта с главного треда (P1 worker + double buffer) | нет | Что-if по 3 сценариям ≤ 1 кадра; UI не блокируется; деградация при отказе воркера |
| M4. Поярусный параллелизм (P2) | `std::thread::scope` → `rayon` по ярусам топосортировки | `rayon` | Числа эталонов ADR-0006 идентичны однопоточному пути (golden-тесты); ускорение ≥ 2× на тяжёлом графе при ≥ 4 ядрах |
| M5. Monte Carlo + QMC (L4, v2) | N-прогонов с распределёнными параметрами; квантили P50/P90/P99 как результаты нод; `sobol_burley` для чувствительности | `sobol_burley` | Воспроизводимость (фиксированный seed → идентичные квантили); прогон 10⁴ итераций на эталоне №5 < 1 с на 4 ядрах |
| M6. LA по потребности (L3) | Отложить до конкретного домена; кандидаты — `faer` (MIT) / `nalgebra` | по решению | Отдельный FR с обоснованием домена |
