## UR-001-01. `*` (умножение) в Numi-строке ломается

**Симптом.** «В numi строке неадекватно отрабатывает знак умножения в виде звёздочки, надо чтобы в numi строках он работал нормально без экранирования». В схеме владелец вынужденно написал `sum = $1 x $2` вместо `$1 * $2`.

**Корневая причина.** Движок Numi поддерживает `*` полностью: токен `Tok::Star` (`crates/canvas-core/src/expr.rs:1024-1029`), бинарный `BinOp::Mul` в `parse_mul_tail` (`expr.rs:1341-1390`), регресс-тесты `star_multiplication_eval` / `star_multiplication_variables_and_lines` (`expr.rs:3675-3732`, комментарий «регрессия вопроса владельца»). Ломается **не движок**, а канонизация markdown при сохранении текста заметки:

1. При коммите текст проходит `EditingSession::text()` → `markdown::emit` (`crates/canvas-render/src/edit.rs:597-604`).
2. Маска экранирования `escape_mask` (`crates/canvas-render/src/markdown.rs:427-441`) ставит `\` **перед каждым одиночным `*` безусловно** (markdown.rs:432); комментарий над функцией (markdown.rs:421-426) прямо фиксирует асимметрию: одиночное `=` оставлено живым, «иначе экранирование ломало expr-парсер», но «`*` — одиночный маркер (italic) — экранируется всегда». Это подтверждено тестом `emit_escapes_literal_markers` (markdown.rs:767-774): `emit("a*b=c") == "a\*b=c"`.
3. Модель получает `sum = 10 \* 2`; expr снимает **только** `\=` (`expr.rs:1593`), лексер падает на `\` — «неподдерживаемый символ '\'» (`expr.rs:1160-1167`). Для строки-присваивания ошибка видимая (красная диагностика), для авто-строки — молчаливое отсутствие результата.
4. Живые результаты при наборе считаются по `session.text()` (уже с `\*`) — ошибка появляется в момент ввода `*`, отсюда ощущение «неадекватной» реакции.

**Вторичная причина.** Парный italic-тоггл ищет закрывающий `*` по всему остатку текста, **переходя через `\n`** (`markdown.rs:44-46` `has_marker_ahead`, тоггл `markdown.rs:86-101`): две `*` в разных строках теряются обе при рендере/открытии в редакторе (`10 * 2` → `10  2`).

**Трассировка.** «Тихое» решение агента: коммит **d434c41** («FR-013 правка 5») чинил идентичный конфликт для `=`, осознанно оставив `*` «экранируется всегда» — и предупредил в комментарии, что экранирование ломает expr-парсер. Задокументированный контракт при этом нарушен: `user-docs/calculations.md:42` обещает «Умножение — звёздочкой `*`». Движок-часть (`*` — оператор) была согласована ранее (тест-регрессия на вопрос владельца), канонизация синхронизирована не была. В round-trip-тесте листа владельца `live_typing_flow_owner_sheets` (`app.rs:10767-10859`) кейса с `*` нет — потому баг не ловился.

**Решение владельца (Q&A, 2026-10-08).** Вопрос: «какой объём фикса звёздочки делать?» → Ответ: **«Полный фикс»** — не экранировать одиночный `*` в Numi-строках (детект через `expr::line_kind`), italic-пару ограничить строкой, expr снимать `\*` для уже сохранённых заметок.

**Что делать.** CR-019: правки `markdown.rs:427-441` (маска построчная, `*` не экранируется на Numi-строках), `markdown.rs:86-101` (парный тоггл без пересечения `\n`), `expr.rs:1593` и `expr.rs:2211` (снимать `\*` симметрично `\=`).

## UR-001-02. Ctrl+Backspace, Ctrl+A и базовые шорткаты редактора

**Симптом.** «Удаление по словам через ctrl + backspace не работает, ctrl+A (выбрать всё) и прочие базовые шорткаты».

**Разбор по слоям.**

1. **Ctrl+Backspace не реализован нигде** (ни натив, ни web): `map_key` игнорирует Ctrl для Backspace/Delete (`crates/canvas-render/src/edit.rs:346-347`), в `KeyCommand` (`edit.rs:306-323`) и `apply` (`edit.rs:765-811`) нет word-delete. При этом word-удаление **уже есть в двух других полях приложения**: панель поиска (`search_ui.rs:79-84, 135-169`, эвристика `is_word_separator`) и поле настроек (`app/input.rs:765-773`) — паритет-дыра редактора.
2. **Ctrl+A реализован полностью** — `map_key` (`edit.rs:372`, латиница+кириллица+`\u{1}`), `apply` (`edit.rs:792-802`), отрисовка выделения (`edit.rs:938`, `renderer.rs:1471-1549`), тесты (`edit.rs:1582-1585`). На нативе работает. Симптом владельца на web объясняется пунктами 3-5.
3. **Порядок событий winit-web (дефект платформы):** winit 0.30.13 web-backend шлёт `KeyboardInput` **раньше** `ModifiersChanged` и стирает модификаторы при blur канваса (`winit-0.30.13/…/web/event_loop/window_target.rs:148-166`, `:86-99`). Приложение обновляет модификаторы только по `ModifiersChanged` (`app/handler.rs:33-35`) → первая Ctrl-комбинация после смены фокуса обрабатывается с пустыми модификаторами и **печатает символ** («a» вместо выделения всего).
4. **Форвардер шима FR-095 не зовёт `preventDefault`** (`crates/canvas-web/src/ime.rs:292-337`): на coarse-указателях браузер параллельно выполняет своё default-действие (select all в input/странице). Фильтра «ctrl — не форвардить» нет (модификаторы копируются, `ime.rs:312-315`), но и гашения браузера тоже нет. Весь шим активен только на coarse-указателях (`ime.rs:83-85`).
5. **Потеря фокуса канваса:** winit-web слушает keydown только на канвасе (`winit/…/web_sys/canvas.rs:301, 475` — c `prevent_default` по умолчанию); после клика по DOM-элементам (тулбар хранилища, тур, about — `canvas-web/src/toolbar.rs:18-51`) клавиатура мертва до клика по канвасу.
6. **Super/Cmd-паритет:** `map_key`/редактор знают только Ctrl (`app/input.rs:461-462`); Cmd+A на macOS/iOS печатает «a».
7. **«Глушитель»:** несматченные клавиши редактор глотает с `return true` (`app/input.rs:502-513`) — Ctrl+Z/Y в редакторе — no-op (undo текста в редакторе нет вовсе; canvas-undo `input.rs:1007-1015` недостижим при правке).

**Трассировка.** Неполнота реализации: Ctrl+A реализован и обещан (`user-docs/interface.md:19`), Ctrl+Backspace/undo/PageUp/Tab ни в одном CR/FR не были в скоупе редактора (FR-004 — оверлей хоткеёв канваса, не редактор). Порядок событий winit-web и отсутствие `preventDefault` в шиме — «тихие» дефекты реализации FR-095 (шим проверялся на ввод текста, а не на chord'ы).

**Решение владельца (Q&A, 2026-10-08).** Платформа — **Web (wasm)**. Объём — **«Полный набор»**: базовый паритет (Ctrl+Backspace/Delete, Cmd-паритет, не глотать незнакомые Ctrl-комбинации) + редакторский undo/redo (Ctrl+Z/Y) + PageUp/PageDown + Tab-индент + умный Home (текст → начало строки).

**Что делать.** FR-100 (единый документ на весь набор): правки `edit.rs:346-347` + новые `KeyCommand`, `apply` (word-delete через `Motion::LeftWord`+extend, готовый образец `search_ui.rs:135-169`), `app/input.rs:461` (super-паритет), `input.rs:502-513` (пропуск незнакомых chord'ов вверх по лестнице), `canvas-web/ime.rs:292-337` (`preventDefault` для chord'ов), компенсация порядка событий winit-web (или апгрейд winit), возврат фокуса канвасу после DOM-интеракций.

## UR-001-03. Зона «Проверка цепочки расчёта» там, где нет результата

**Симптом.** «В блоке с расчётами даже там, где нет нижнего поля (где нода только с параметром), почему-то присутствует зона нажатия на "проверку цепочки расчёта". Надо убрать эту зону там, где нет расчётов, либо оставить её везде (но надо понять что выводить, если в одной ноде прописано сразу несколько значений — тогда получается дублёж)».

**Корневая причина.** Три предиката одного триггера разошлись:

| Поверхность | Условие | Место |
|---|---|---|
| Полоса результата + иконка-лупа (видимое) | `text.has_result(index)` **И** `expr_results == Ok` | `crates/canvas-render/src/renderer.rs:1768, 1786` (комментарий «Фикс 2026-10-05», `:1743-1748`) |
| Hit-зона клика | только `expr_results == Ok` | `crates/canvas-app/src/app.rs:8278-8292` (`result_band_root_at`) |
| Тултип «Проверка цепочки расчёта» | только `expr_results == Ok` | `crates/canvas-app/src/app/explain.rs:1559-1570` |

Для ноды `qty = 10` футер «ИТОГ» подавлен при наличии построчных результатов (`crates/canvas-render/src/text.rs:3270-3291` → `has_result == false`), но `expr_results[нода] = Ok(10)` — присваивание возвращает значение (`expr.rs:1568-1570`), узловой итог — последняя формульная строка (`flow.rs:793-797`). Итог: видимого ничего нет, а **невидимая hit-зона 16px на отрезке `[h−26, h−10]` ложится прямо на последнюю строку тела** — клик по `qty = 10` открывает explain вместо выделения/драга (перехват до canvas-pick — `app/input.rs:2839-2848`). Геометрия зон к тому же не совпадает с полосой D (`RESULT_LINE_HEIGHT=16` на `[h−26,h−10]` против `RESULT_STRIP_H=32` на `[h−32,h]`).

**Трассировка.** «Тихое» решение агента: «Фикс 2026-10-05» сузил **видимое** до `has_result`, не тронув hit-зону и тултип — прямое расхождение с контрактом FR-088 («иконка — у каждой ноды с `ExprOutcome::Ok` — та же зона, что hit-тест `result_band_root_at`»). Базовое согласование в PRD-0007 (AC-1.1, AC-1.4) явно включало константы («у цифры без входов панель показывает единственный узел “исходное значение”») — то есть показ у `qty = 10` был когда-то согласован; теперь владелец решение пересматривает.

**Решение владельца (Q&A, 2026-10-08).** Два вопроса:

- **Q2 «Что делать с зоной у нод без видимого результата?»** → **«Только у расчётов»**: триггер только у полосы «ИТОГ» и построчных результатов; у констант-присваиваний (`qty = 10`) убрать полностью.
- **Q3 «Что выводить при нескольких значениях в ноде?»** → **«Лупа на строку»**: мини-лупа у каждой строки-результата (предупреждение зафиксировано: при 5+ строках нода шумит — на приёмке проверить).

**Что делать.** CR-020 (пересматривает FR-088 и AC-1.1/AC-1.4 PRD-0007): паритет hit/render/tooltip по единому предикату «есть видимый результат» (зеркало `node_shows_result_footer`, `canvas-scene/src/scene.rs:1397-1410`), построчные мини-лупы, геометрия зон = видимой. Точки: `app.rs:8278-8292`, `explain.rs:1559-1577`, `renderer.rs:1764-1816`, `cards.rs:634-652`.

## UR-001-04. Входящие значения исчезают; расчёт выводится как «параметр»

**Симптом.** «Нода, в которую вошли 2 входящих значения (общая сумма корзины) — [входящие параметры] перестали отображаться после того, как я собрал расчёт из двух входов. Логично, что входящие параметры остаются видны, а расчёт выводится как расчёт; сейчас же он выводится как параметр».

**Корневая причина — две независимые.**

**(A) Авто-строки входов скрываются, когда формула читает слот.** `auto_rows_with_data` (`crates/canvas-core/src/flow.rs:1443-1463`): если строка формулы ссылается на `$N`/`$in`/qualified-адрес (сборщик ссылок `validate.rs:486-568`, `slot_references`), слот считается «читаемым» → авто-строка «входящее значение» не создаётся (`if read { continue }`, `flow.rs:1458-1463`). До ввода формулы `sum = $1 x $2` обе авто-строки отображались (`scene.rs:803-811` → `row_grid.rs:486-504`); после ввода — обе исчезли. Это **зафиксированное решение владельца** в fr-050 Р-4 («авто-строка — строка-проекция», fr-050:120-136) и зеркало W-UNUSED-SLOT (FR-032). Панель stage «Как считается» (`calc_panel_ui.rs:119-151`) входы показывает всегда — расхождение поверхностей.

**(B) Классификация строки: любое присваивание = «параметр».** `build_rows` (`crates/canvas-render/src/row_grid.rs:519-531`): `NumiLineKind::Assignment { name }` → `RowKind::Param`; RHS не анализируется — `line_kind` проверяет только левую часть (`expr.rs:2221-2227`). Строка `sum = $1 x $2` попадает в зону «ПАРАМЕТРЫ · N» (`text.rs:1070-1078`, `:1127-1161`). Одновременно в панели stage та же строка классифицируется **расчётом** (`calc_panel_ui.rs:152-163`, `dataref.rs:411-431` — все `Assignment`/`Expression` в «Расчёт · формулы») — двойная классификация одной строки на двух поверхностях. fr-045 R-4 описывает «Расчёт · формулы» именно как `<имя> := <формула> = <результат>` — реализация тела ноды расходится с документом.

**Трассировка.** (A) — согласованное решение (fr-050 Р-4), теперь пересматривается владельцем; (B) — «тихое» расхождение реализации с fr-045 R-4/fr-044 Р-4.

**Что делать.** CR-021: (1) пересмотр fr-050 Р-4 — авто-строки остаются видимыми и при читаемых слотах (правка `flow.rs:1453-1463` + пиннеры `flow.rs:3690-3960`, `validate.rs:678-748`, `scene.rs:3613+`); (2) классификация `Assignment` с RHS, ссылающимся на входы → `RowKind::Calc` (`row_grid.rs:523-531`, `text.rs:1070-1078`, `text.rs:1128-1130`); (3) единая точка классификации «параметр vs расчёт» для тела и панели stage (сейчас три копии).

## UR-001-05. В автодополнении нет `$параметр` — только номера `$N`

**Симптом.** «Входы именно как $параметр никак не предлагаются в автодополнении внутри ноды, предлагаются только номера входов $N».

**Корневая причина — трёхслойная.**

1. `HintContext` (`crates/canvas-app/src/app/overlays.rs:2137-2164`) физически не содержит имён входов: только **количество** value-рёбер и параметры **манифеста шаблона** самой ноды — ни имён выходов источников (`fromOutput`), ни имён проливания (`toParam` входящих рёбер), ни qualified-ключей.
2. Состав `$`-подсказок зашит на три формы (`hints_ui.rs:137-171`): `$in`, `$1..$N`, `$<параметры манифеста>`.
3. **Форма `$Купон.купон` из handtest не поддерживается грамматикой вообще:** `$`+кириллица лексер трактует как **валюту** (`dollar_param_ident` — только ASCII, `expr.rs:351-370`; fallback `Tok::Unit("$")`, `expr.rs:1098-1103`, `$` в `UNIT_TABLE` — Money, `expr.rs:298`), а `Купон.купон` — отдельный qualified-путь; парсер склеивает их неявным умножением «1 доллар × Купон.купон» (`parse_mul_tail`, `expr.rs:1352-1366`). Строка `Финальная корзина = $Купон.купон` к тому же **не парсится вовсе** — двухсловная LHS невозможна (`expr.rs:1236-1243`, `1686-1692`) и молча считается прозой. Рабочая форма именованной ссылки — **`Купон.купон` без `$`** при адресованном ребре (`fromOutput`/`fromLine` на строку-присваивание; ключи qualified: `dataref.rs:60-90`, `flow.rs:1490-1524, 1120-1129`); для неадресованного — `$in`/`$1`.

**Сайд-финд (баг).** Счётчик `ctx.inbound` (`overlays.rs:2144-2154`) считает все value-рёбра, включая `toParam`-рёбра, а рантайм-слоты их исключают (`flow.rs:942-959`, фильтр на `:955`) → попап может предложить `$2`, который в eval даст `MissingInbound`.

**Трассировка.** Неполнота FR-021 v1: согласованный скоуп подсказок включал `$in`/`$1..$N` (FR-014) и `$параметры` манифеста (FR-018) — именованные входы по фактическим рёбрам (ADR-0003) в документ не вошли; никто не решал «не подсказывать» — это пробел. Счётчик — «тихий» дефект реализации.

**Решение владельца (Q&A, 2026-10-08).** Q5 (совместно с UR-001-07) → **«Имя без $ + после $»**: ввод имени без `$` подсказывает входы; для кириллицы формат «Нода.параметр» (грамматика уже поддерживает), для ASCII — `$имя`.

**Что делать.** FR-101: наполнение `HintContext` именами (toParam-спиллы `flow.rs:1057-1066`, qualified-ключи `QualifiedNames::edge_keys`), фикс счётчика `inbound` (`&& edge.to_param.is_none()`), новые ветки `hint_items` (`$`-токен → матчинг по имени без `$`; идентификаторный токен → `$`-рефы и `Объект.Поле`), приоритизация при `HINT_LIMIT=8`. Рантайм-резолв `$<ASCII-имя>` и `Объект.Поле` уже работает — грамматика не меняется.

## UR-001-06. Предложение «поменять ноду на шаблон» при вводе значений

Гейта «строка каретки — Numi-значение» не существует; Numi-гейт (`overlays.rs:2117-2127`) закрывает только L0-строки, ИИ-мердж идёт безусловно. **Трассировка.** Согласованное решение плана FR-079 (`docs/plans/fr-079-suggest-engine.md` §4.2): C1 описан как «любой ввод, включая прозу — это и есть сценарий “печатаю имя шаблона”»; план сам называет навязчивость «продуктовым риском №1» (§9). Реализация соответствует плану; расхождение — с реальным опытом владельца. Пересмотр — за владельцем.

**Решение владельца (Q&A, 2026-10-08).** Q6 → **«Гейт Numi-строк»** + примечание владельца: «**UR-06 — вообще не надо триггерить**». Усиленная трактовка: ИИ-предложения шаблонов **не должны триггериться при вводе в ноде вообще** (ни на Numi-строках, ни на прозе) — попап подсказок при редактировании ноды остаётся только для L0-подсказок (переменные/входы/функции/единицы). C3-карточки «следующие ноды» (после instantiate шаблона) остаются вне попапа и не затрагиваются.

**Что делать.** CR-022 (пересматривает C1 плана FR-079): убрать ИИ-мердж из попапа полностью — точки `overlays.rs:2102-2115` (триггер), `overlays:2168-2169` + `app.rs:5946` (`suggest_remerge`), `hints_ui.rs:243-258` (`merge_ai_items`); приёмка — `price = 100 rub` без единой ИИ-строки; show-гейт/воркер/лог остаются для будущих поверхностей (C3+).

## UR-001-08. Автодополнение должно применяться разово (без повторного навязывания)

**Симптом.** «Применять автодополнение надо разово: если автодополнение уже было принято, например в строке 100 rub, автодополнение не должно принудительно показываться после ввода/применения ввода rub».

**Корневая причина.** Suppress-состояния нет: `accept_hint` после вставки **немедленно перевызывает `update_hints`** (`app.rs:5699-5722`, вызов на `:5717-5721`); замена токена = N backspace + вставка (`edit.rs:921-935`), токен перед кареткой = принятый текст (`rub`) → `hint_items("… 100 rub")` снова находит единицы по префиксу → `sync` открывает попап при любом непустом списке (`hints_ui.rs:284-291`, `self.open = !self.items.is_empty()`). Тот же путь — при наборе с клавиатуры (`app/input.rs:552-567`). В `HintPopup` (`hints_ui.rs:262-271`) и `SuggestState` (`suggest.rs:383-419`) поля «принято/подавлено» нет; Esc сбрасывает попап только до следующего символа.

**Трассировка.** «Тихое» решение агента / пробел контракта FR-021: клавиатурный контракт фиксирует Enter-accept и Esc, но не описывает повторное открытие после принятия.

**Решение владельца (Q&A, 2026-10-08).**

- **Q7** → **«До смены токена»**: после принятия подсказки попап не открывается, пока не изменится токен перед кареткой (ввод/удаление символа).
- **Примечание владельца:** «UR-08 — я не понял варианты, поясни». Пояснение (дублируется в CR-023): «до смены токена» означает — принятое автодополнение закрыло тему: попап сам не возвращается, сколько бы вы ни двигали каретку по этой строке. Как только вы **меняете текст перед кареткой** (допечатываете символ, стираете) — попап снова может открыться, если для нового токена есть совпадения. Пример: `100 rub|` → приняли `rub` → попап закрыт; каретку двигаем — тишина; дописали ` ` (пробел) или любой символ — попап оценивает заново. Ctrl+Space остаётся ручным способом открыть подсказки принудительно.

**Что делать.** CR-023: suppress-поле в `HintPopup` («принято на токене X — не открывать до смены токена»), учёт в `sync`/`reset`, взведение в `accept_hint` (`app.rs:5717-5721`), поведение keystroke/paste (`app/input.rs:546-567`), семантика Esc (dismiss до смены текста).

## UR-001-09. Тултип `out:…` на коннекторе простой связки

**Симптом.** «Не понятно, почему на коннекторе, который отвечает за простую логику связывания (без проливания данных), отображается out:... — сейчас это вводит в заблуждение. Информационный тултип нужно оставлять только для коннекторов с передачей данных».

**Корневая причина.** Тултип порта строится `port_tooltip_at` → `port_label_for`, и ветка стороннего порта `PortTarget::Out` **безусловно** печатает `out: {имя ноды}` (`crates/canvas-app/src/app.rs:4184-4203`; сборка текста `app.rs:4073-4088`; i18n `STAGE_OUT_LABEL` = `"out: {name}"`, `i18n.rs:1760` RU / `:2965` EN) — без анализа рода связи, которую этот порт создаёт. Обычный drag от стороннего порта = **control-связь** (`value_flow = shift_key()`, `app/input.rs:2972-2974`), т.е. это ровно «коннектор простой логики связывания», но тултип показывает дата-семантику. Гейт по `FlowKind::Value` в этом пути отсутствует — при том, что в stage-подписях у истока он есть (`app/stage.rs:886-889`: control — подписи «out:» нет). Тултип включается на hover без условий (`app/handler.rs:494-502`). Дата-порт `PortTarget::Line(None)` (футер шаблона) — исключение: drag с него всегда value (`input.rs:3291`), там `out:` оправдан.

**Трассировка.** «Тихое» решение агента: hover-тултип порта не проходил ревью рода связи; непоследовательность с stage-гейтом — след двух разных реализаций одного правила.

**Решение владельца (Q&A, 2026-10-08).** Q8 → **«Без тултипа»**: у контрольной связи тултипа нет вообще; адресная подпись остаётся только у value-связей (как в stage-подписях).

**Что делать.** CR-024: гейт ветки `PortTarget::Out` в `port_tooltip_at` (`app.rs:4189-4203`) по семантике потока; для control-порта — `None`; `PortTarget::Line(None)` не трогать; образец-инвариант — `stage.rs:886-889`.

## UR-001-10. Тултип value-коннектора: `нода.строкаN` вместо `нода.параметр`

**Симптом.** «Не понятно, почему коннектор, который выводит данные, в тултипе отображает не нода.параметр, а нода.строкаN, хотя мы делали, чтобы отображалось именно имя параметра».

**Корневая причина — вердикт (а) с узким (б)-хвостом.**

- **(а) Drag-созданные рёбра хранят только `fromLine` — `fromOutput` никогда не заполняется**, и тултип честно печатает то, что хранится. При этом правильное имя уже доставается для тултипа проливания: `spill_source_field` (`flow.rs:1513-1523`, `Assignment { name }` → имя) — поэтому `Трафик.peak_rps` показываетcя в одних поверхностях и `Трафик.строка 3` в других на одних и тех же рёбрах.

**Трассировка.** Неполнота реализации согласованного ADR-0003 (имя как канонический адрес; UI drag-механика сознательно оставлена на индексах — ADR-0003 Вариант C) + «тихая» несинхронизация display-слоёв (dataref против `spill_source_field`) + прямое противоречие кода ADR-0003 в приоритете полей.

**Решение владельца (Q&A, 2026-10-08).** Q9 → **«Имя + значение»**: в тултипе value-коннектора показывать `Нода.имя_переменной` (резолв через `spill_source_field`; drag от строки `price = …` → `Цена.price`), **дополнительно текущее значение**: `Цена.price = 100 rub`. Fallback «строка N» — только для безымянных строк.

**Что делать.** CR-025: display-резолв имени в `dataref.rs:145-153` (вместо литерала «строка N»), `app.rs:4076-4079`, `app.rs:4122-4128` (+ значение из `stage_edge_value_text`-пути); приоритет полей — привести `model.rs:630-632`/`flow.rs:934` к ADR-0003 (имя > индекс) или зафиксировать поправку в ADR-0003; опционально — заполнять `fromOutput` при drag (`input.rs:3336`, `app.rs:9215`, `app.rs:4501`).

## UR-001-11. Выделение текста невидимо в тёмной теме

**Симптом.** «В тёмной теме не видна зона выделения текста (видна только в светлой). Нужно светло-синим с прозрачностью 20-30%».

**Корневая причина.** Токен **одинаков в обеих темах** и номинально уже «светло-синий с α0.35»: `selection_fill = [ACCENT, ALPHA_35]` (`crates/canvas-render/src/theme.rs:306-311` dark, `:445-450` light; `ACCENT` ≈ #659CF7, `tokens.rs:35`; в JSON-пресетах `#7AA2F759`, `design/tokens/themes/*.json:39`). Проблема — **баг композитинга**: шейдер `cards.wgsl:134-141` выдаёт **premultiplied** цвет (`color = mix(vec3(0), in.fill.rgb, fill_alpha)` → `α×rgb`), а блендинг включён **straight** (`BlendState::ALPHA_BLENDING`, `cards.rs:1939`) → эффективная непрозрачность = **α² ≈ 0.12**. Числа: тёмная карточка #2B2E38 → итог ≈ rgb(50,59,80), Δ ≈ +7..24/255 — невидимо; светлая #FBFBFD → Δ ≈ −19/255 — видна. Дефект занижает яркость всех полупрозрачных квадов cards-пайплайна (зебра, `==highlight==`, what-if фон) — объясняет историю перекалибровок зебры в `design/contrast-audit-2026-10.md` (значения подобраны под straight-альфу, которая не достигается при α²). Каретка (α=1.0) не страдает — потому жалоба именно на выделение.

**Трассировка.** «Тихое» решение агента (дефект композитинга, не согласованный); токены CR-007/PRD-0006 ни при чём — значения соответствуют аудиту, аудит не учитывал фактический блендинг.

**Решение владельца (Q&A, 2026-10-08).** Q10 → **«Корневой фикс»**: чинить композитинг шейдера (`BlendState::PREMULTIPLIED_ALPHA_BLENDING` в `cards.rs:1939` — wgpu 22 поддерживает), токен остаётся светло-синий α0.35; заодно выравниваются зебра/подсветки. Визуальная приёмка зебры/меню/подсветок после смены — обязательна (зафиксировано). (Точечная калибровка тёмного токена α 0.20–0.30 не делается — после блендинг-фикса α0.35 станет фактически видимой; если на приёмке владельцу захочется светлее — точечная правка `theme.rs:306-311` + `theme_presets.rs:156` + JSON-пресеты.)

**Что делать.** CR-026: блендинг-фикс + регресс-тест дельты на тёмной карточке (`theme.rs:860-861` — по образцу `zebra_delta_post_gamma_is_visible_not_black`, с учётом фактического блендинга).

## Открытый вопрос (вне 11 пунктов, обнаружен при разборе UR-001-05)

**Двухсловные имена присваиваний.** Строка владельца `Финальная корзина = $Купон.купон` не парсится в принципе: грамматика допускает только однотокеновую LHS (`single_identifier`, `expr.rs:1686-1692`); двухсловная LHS уходит в хвостовое присваивание `выражение = имя` и падает («ожидалось имя после =», `expr.rs:1236-1243`) → строка молча считается прозой. Если владельцу нужен синтаксис «имя с пробелом = значение» (например, в кавычках: `"Финальная корзина" = …`) — это **отдельная фича грамматики**, не входит в скоуп UR-001; кандидат в новый FR по решению владельца. До того момента рабочая форма — однотоковые имена (`корзина_без_скидок = …`).
