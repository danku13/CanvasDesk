## 1. Резюме для руководителя
Настоящий документ — программа ручной приёмки функций CanvasDesk, разработанных и влитых в ветку main, но не подтверждённых в рантайме. На момент составления (9 сентября 2026 г., коммит 84cfdc2) кодовыми задачами закрыты T8–T17: связи, drag-drop из Explorer, файловый вотчер, миникарта, поиск, встройка в рабочий стол (--desktop), шина системных событий, а также оформление рабочего стола (иконки, меню, выход, краш-сейф). Задачи T11 и T12 (живые превью и preview host для Office) отложены владельцем на период после релиза v1.0 и в проверку не входят.
Автоматизированная часть проверки выполнена и зелёная: по каждой задаче прогнаны cargo fmt, cargo clippy, юнит- и интеграционные тесты всех крейтов workspace (canvas-core, canvas-shell, canvas-app, canvas-render), а также msvc-зонд win-check, компилирующий windows-only модули под целевую платформу. Этого достаточно для уверенности в типах и логике чистых функций, но принципиально недостаточно для подтверждения поведения продукта: иерархия окон Progman/WorkerW, перезапуски Explorer, сон и пробуждение, смена WTS-сессии, COM-взаимодействие с Shell и DPI-поллинг воспроизводятся только на живой системе Windows. Поэтому все критерии из разделов 9 планов задач и критерии готовности milestone'ов SPEC §10 остаются за ручной приёмкой владельца.
При подготовке сводки обнаружен и устранён дефект процесса: четыре последних коммита (07b9dd2, 9b698d5, d98a89a, abd3c06) стояли с красным CI на windows-latest. Причины — два дефекта в cfg(windows)-коде, невидимых для Linux-гейтов: lint doc_lazy_continuation в doc-комментарии shell_events/regs.rs и ошибка заимствования E0382 в create_text_file_node (main.rs). Оба исправлены коммитами 065e39b и 84cfdc2. Статус CI на коммите 84cfdc2: зелёный — все шаги workflow пройдены, включая clippy на windows-latest; авторитетный гейт восстановлен.
Итоговый объём программы: около 80 проверочных пунктов, сгруппированных в семь функциональных блоков, плюс сквозная регрессия на связность всех подсистем в режиме --desktop. Оценка чистого времени прохождения — 2,5–4 часа; порядок и разбиение на сессии приведены в разделе 11. Результатом приёмки должны стать решение о постановке тегов v0.2 (M2) и v0.3 (M3), подтверждение готовности режима десктопа и допуск к задаче T18 (энергосбережение), точки входа для которой уже подготовлены шиной T16.

Отдельно подчеркнём границу между автоматической и ручной частями. Ручная часть покрывает всё, что требует живого Shell: перетаскивание из реального Explorer, реакцию на перезапуск Explorer, режим блокировки сессии, переходы сна и пробуждения, восстановление после аварийного завершения, реестровый автозапуск и корректность Z-порядка рабочего стола. Именно эти сценарии собраны в разделах 4–9.

## 3. Подготовка стенда и включение логов
### 3.1. Сборка и варианты запуска
Приёмка выполняется на release-сборке: cargo build --workspace --release из корня репозитория (требуются Rust stable 1.80+ и Windows SDK). Исполняемый файл — target\release\canvas-app.exe. Проверки M2 и M3 достаточно проводить в оконном режиме: canvas-app.exe с путём к .canvas или без аргумента (откроется default.canvas). Проверки T15–T17 и сквозная регрессия требуют режима canvas-app.exe --desktop. Нагрузочные сценарии миникарты используют canvas-app.exe --stress 5000.
Рекомендуется запускать приложение из консоли (Windows Terminal или PowerShell), чтобы журнал трассировки был виден в реальном времени, и сохранять его в файл на каждый прогон: командой canvas-app.exe --desktop 2>&1 | Tee-Object -FilePath log_t17.txt (PowerShell). Журналы каждого прогона — основной артефакт приёмки: к ним привязываются формулировки дефектов и отметки о прохождении.
### 3.2. Уровень логирования
По умолчанию приложение пишет в стандартный вывод уровень info с фильтром внутренних крейтов wgpu (wgpu_hal=warn, wgpu_core=warn). Для большинства пунктов этого достаточно: маркеры встраивания, сессий, Explorer-рестартов и краш-восстановления идут на уровне info/warn. Единственный пункт, требующий отладочного уровня, — clipboard-канал шины T16 (п. 8 раздела 7): событие ClipboardUpdated логируется на debug. Включается переменной окружения перед запуском: в PowerShell — $env:RUST_LOG = "debug,wgpu_hal=warn,wgpu_core=warn"; в cmd — set RUST_LOG=debug,wgpu_hal=warn,wgpu_core=warn. После прогона переменную следует сбросить, чтобы журнал не разбухал.
### 3.3. Тестовые данные
Заранее подготовьте: (1) папку с 10 фотографиями, одну из которых скрыть командой attrib +h — для сценария дропа папки из T9; (2) наблюдаемую папку с 20 файлами разных типов — для массового переноса из T16; (3) файл с кириллическим именем «смета_2026.xlsx» и пару текстовых файлов .txt/.md с русским текстом — для поиска по имени и по содержимому (T14); (4) изображение и PDF — для двойного клика из T17; (5) отдельную тестовую директорию вне OneDrive и вне сетевых дисков — синхронизаторы и SMB искажают тайминги файлового вотчера (ограничение T10 описано в разделе 10).

## 4. Чек-лист M2: связи, drag-drop и файловый вотчер (T8–T10)
Блок M2 проверяется в оконном режиме на обычном окне приложения. Три подсистемы связаны между собой: drag-drop создаёт файловые ноды, вотчер следит за их каталогами, связи соединяют ноды между собой. Проходите таблицы по порядку — сценарии нарастают по сложности и переиспользуют данные друг друга. Критерий milestone'а M2 из SPEC §10 формулируется так: заметки редактируются инлайн, связи рисуются и сохраняются, drop папки из Explorer раскладывает файлы, переименование файла в Explorer обновляет карточку за время меньше одной секунды.
### 4.1. T8 — связи между нодами
Источник критериев — задача T8 в docs/TASKS.md (детального плана с разделом 9 для связей нет, код влит коммитом 6759ffd вместе с фиксом z-порядка рёбер и тамбнейлов). Обратите внимание на последний пункт — round-trip через Obsidian: он защищает совместимость формата .canvas, которую проект обещает в README.
**Таблица 3. T8: связи (edges)**

|---|---|---|---|
| 1 | ☐ | Наведите курсор на карточку или заметку | Появляются четыре порта соединения: верхний, правый, нижний, левый |

## 5. Чек-лист M3: миникарта и поиск (T13–T14)
Блок M3 также проходит в оконном режиме. Чистая математика обеих подсистем (масштабирование сцены в обзорный кадр, аффинные преобразования, анимация полёта камеры, bm25-запросы) покрыта юнит-тестами, поэтому ручная часть сосредоточена на визуальных критериях и навигационной точности. Нагрузочный сценарий миникарты использует генератор --stress 5000 и HUD клавишей F3. Критерий milestone'а M3 после переупорядочивания (T11/T12 отложены) формулируется так: миникарта навигационна, поиск находит по имени файла и по тексту (FTS5).
### 5.1. T13 — миникарта
Критерии — план T13, разделы 1 и 6. Пороговые значения вынесены в конец списка: два сценария требуют нагрузочной сцены. Если клик по миникарте попадает с систематическим смещением (больше пары пикселей), фиксируйте дефект с приложением журнала — round-trip преобразований должен держать точность не хуже 1 px.

| № | ☐ | Шаг | Ожидаемый результат |
|---|---|---|---|
| 1 | ☐ | Откройте канвас с несколькими нодами разных типов | Миникарта 220×140 лог. px в правом нижнем углу (отступ 16 px), полупрозрачный тёмный фон, скруглённые углы |
| 2 | ☐ | Сравните содержимое миникарты со сценой | Упрощённые прямоугольники без текста и текстур; цвет по типу ноды; битые ссылки выделяются красным |

## 10. Известные ограничения и отложенные функции
Перед прохождением важно отделить дефекты от зафиксированных ограничений: перечисленное ниже не является ошибкой реализации и не должно заводиться как дефект приёмки. Ограничения взяты из планов задач (разделы 7 и 8) и зафиксированы в журнале работ; часть из них закрывается последующими задачами дорожной карты.
**Таблица 12. Ограничения, не являющиеся дефектами**
| Область | Ограничение | Перспектива |
|---|---|---|
| T10, вотчер | Перенос файла между несмежными каталогами (наблюдаемая папка → ненаблюдаемая) виден как Remove+Create: карточка становится битой, новая нода не создаётся | Полное решение — вотчинг общего родителя; вне v1 |
| T10, вотчер | Сетевые диски (SMB): ReadDirectoryChangesW нестабилен — деградация до отсутствия обновлений, без падения | Принято проектом (рецепт R14) |
| T10 → T16 | Удаление в корзину из Explorer в T10 покрыто косвенно (файл исчез → битая карточка) | Полностью закрыто SHChangeNotify-мостом T16 — проверяется в разделе 7 |

| T15, платформы | Ручная приёмка v1 — только Windows 11 25H2 build 26200; сборки 24H2 и младше — по мере доступа | Вне обязательного объёма v1 |
Отдельная категория — точки, где ожидаемое поведение зависит от недокументированных механизмов Windows (Z-порядок WorkerW, реакция DefView на команды скрытия иконок, поведение TaskbarCreated при смене DPI). Если наблюдение расходится с ожиданием, но приложение не падает и деградирует управляемо (warn в журнале, фолбэк), оценивайте серьёзность по пользовательскому эффекту, а не по внутреннему механизму: в этих зонах дорожная карта сознательно допускает вариативность.

## 11. Порядок прохождения и учёт результатов
Рекомендуемый порядок: сначала подготовка по разделу 3 (около 15 минут), затем оконный режим — M2 (раздел 4), затем M3 (раздел 5), примерно 60–90 минут суммарно; далее режим --desktop — T15 (раздел 6), T16 (раздел 7), T17 (раздел 8), ещё 60–90 минут; и в завершение сквозные сценарии раздела 9 — 30–60 минут. Разрыв на несколько сессий допустим и даже полезен: сценарии сна, блокировки и перезапуска оболочки лучше не «склеивать» в один прогон, чтобы журнал каждой сессии оставался читаемым.
По каждому пункту ставится отметка: «пройдено», «пройдено с ограничением» (с описанием) или «дефект». Дефект фиксируется минимальным набором полей — идентификатор, пункт чек-листа, шаги воспроизведения, ожидание, факт, серьёзность по четырёхуровневой шкале (блокер / критично / важно / желательно) и фрагмент журнала. Шаблон учёта — таблица 13. Дефекты обрабатываются отдельными исправляющими сессиями (conventional commits, как это уже принято в проекте), после исправления пункт чек-листа проходится повторно.
**Таблица 13. Журнал учёта дефектов приёмки (шаблон)**

|---|---|---|---|---|
