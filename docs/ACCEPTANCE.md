## 1. Резюме для руководителя
Настоящий документ — программа ручной приёмки функций CanvasDesk, разработанных и влитых в ветку main, но не подтверждённых в рантайме. На момент составления (9 сентября 2026 г., коммит 84cfdc2) кодовыми задачами закрыты T8–T17: связи, drag-drop из Explorer, файловый вотчер, миникарта, поиск, встройка в рабочий стол (--desktop), шина системных событий, а также оформление рабочего стола (иконки, меню, выход, краш-сейф). Задачи T11 и T12 (живые превью и preview host для Office) отложены владельцем на период после релиза v1.0 и в проверку не входят.
Автоматизированная часть проверки выполнена и зелёная: по каждой задаче прогнаны cargo fmt, cargo clippy, юнит- и интеграционные тесты всех крейтов workspace (canvas-core, canvas-shell, canvas-app, canvas-render), а также msvc-зонд win-check, компилирующий windows-only модули под целевую платформу. Этого достаточно для уверенности в типах и логике чистых функций, но принципиально недостаточно для подтверждения поведения продукта: иерархия окон Progman/WorkerW, перезапуски Explorer, сон и пробуждение, смена WTS-сессии, COM-взаимодействие с Shell и DPI-поллинг воспроизводятся только на живой системе Windows. Поэтому все критерии из разделов 9 планов задач и критерии готовности milestone'ов SPEC §10 остаются за ручной приёмкой владельца.
При подготовке сводки обнаружен и устранён дефект процесса: четыре последних коммита (07b9dd2, 9b698d5, d98a89a, abd3c06) стояли с красным CI на windows-latest. Причины — два дефекта в cfg(windows)-коде, невидимых для Linux-гейтов: lint doc_lazy_continuation в doc-комментарии shell_events/regs.rs и ошибка заимствования E0382 в create_text_file_node (main.rs). Оба исправлены коммитами 065e39b и 84cfdc2. Статус CI на коммите 84cfdc2: зелёный — все шаги workflow пройдены, включая clippy на windows-latest; авторитетный гейт восстановлен.
Итоговый объём программы: около 80 проверочных пунктов, сгруппированных в семь функциональных блоков, плюс сквозная регрессия на связность всех подсистем в режиме --desktop. Оценка чистого времени прохождения — 2,5–4 часа; порядок и разбиение на сессии приведены в разделе 11. Результатом приёмки должны стать решение о постановке тегов v0.2 (M2) и v0.3 (M3), подтверждение готовности режима десктопа и допуск к задаче T18 (энергосбережение), точки входа для которой уже подготовлены шиной T16.

Именно эти сценарии собраны в разделах 4–9.

## 3. Подготовка стенда и включение логов
### 3.1. Сборка и варианты запуска
Приёмка выполняется на release-сборке: cargo build --workspace --release из корня репозитория (требуются Rust stable 1.80+ и Windows SDK). Исполняемый файл — target\release\canvasdesk.exe. Проверки M2 и M3 достаточно проводить в оконном режиме: canvasdesk.exe с путём к .canvas или без аргумента (откроется default.canvas). Проверки T15–T17 и сквозная регрессия требуют режима canvasdesk.exe --desktop. Нагрузочные сценарии миникарты используют canvasdesk.exe --stress 5000.
Рекомендуется запускать приложение из консоли (Windows Terminal или PowerShell), чтобы журнал трассировки был виден в реальном времени, и сохранять его в файл на каждый прогон: командой canvasdesk.exe --desktop 2>&1 | Tee-Object -FilePath log_t17.txt (PowerShell). Журналы каждого прогона — основной артефакт приёмки: к ним привязываются формулировки дефектов и отметки о прохождении.
### 3.2. Уровень логирования
По умолчанию приложение пишет в стандартный вывод уровень info с фильтром внутренних крейтов wgpu (wgpu_hal=warn, wgpu_core=warn). Для большинства пунктов этого достаточно: маркеры встраивания, сессий, Explorer-рестартов и краш-восстановления идут на уровне info/warn. Единственный пункт, требующий отладочного уровня, — clipboard-канал шины T16 (п. 8 раздела 7): событие ClipboardUpdated логируется на debug. Включается переменной окружения перед запуском: в PowerShell — $env:RUST_LOG = "debug,wgpu_hal=warn,wgpu_core=warn"; в cmd — set RUST_LOG=debug,wgpu_hal=warn,wgpu_core=warn. После прогона переменную следует сбросить, чтобы журнал не разбухал.
### 3.3. Тестовые данные
Заранее подготовьте: (1) папку с 10 фотографиями, одну из которых скрыть командой attrib +h — для сценария дропа папки из T9; (2) наблюдаемую папку с 20 файлами разных типов — для массового переноса из T16; (3) файл с кириллическим именем «смета_2026.xlsx» и пару текстовых файлов .txt/.md с русским текстом — для поиска по имени и по содержимому (T14); (4) изображение и PDF — для двойного клика из T17; (5) отдельную тестовую директорию вне OneDrive и вне сетевых дисков — синхронизаторы и SMB искажают тайминги файлового вотчера (ограничение T10 описано в разделе 10).

## 4. Чек-лист M2: связи, drag-drop и файловый вотчер (T8–T10)
Блок M2 проверяется в оконном режиме на обычном окне приложения. Три подсистемы связаны между собой: drag-drop создаёт файловые ноды, вотчер следит за их каталогами, связи соединяют ноды между собой. Проходите таблицы по порядку — сценарии нарастают по сложности и переиспользуют данные друг друга. Критерий milestone'а M2 из SPEC §10 формулируется так: заметки редактируются инлайн, связи рисуются и сохраняются, drop папки из Explorer раскладывает файлы, переименование файла в Explorer обновляет карточку за время меньше одной секунды.
### 4.1. T8 — связи между нодами
Источник критериев — задача T8 в docs/TASKS.md (детального плана с разделом 9 для связей нет, код влит коммитом 6759ffd вместе с фиксом z-порядка рёбер и тамбнейлов). Обратите внимание на последний пункт — round-trip через Obsidian: он защищает совместимость формата .canvas, которую проект обещает в README.
